# 内部文档（不发布、不上传）

> **这个文件夹里的东西不进插件包、不上传到 PrivHub、不上传 GitHub，
> 但必须纳入 git 版本控制（要留版本历史）。**

## 目录结构

```
内部文档/
├─ README.md              ← 本文件
├─ 功能说明.md             ← 这个插件要做什么（需求与功能说明书）
├─ 架构说明.md             ← 架构事实与设计约束（开发前必读）
├─ 流程_写入.md            ← 写入链路的执行细节
├─ 流程_读取.md            ← 读取链路的执行细节
├─ 流程_整理.md            ← 整理链路的执行细节
├─ 待查证问题.md           ← 技术问题的查证结论与遗留
├─ 开发计划.md             ← 分阶段开发计划
├─ 版本记录.md             ← 定稿节点与决策留档（含版本号规则）
└─ 工具/
   ├─ privhub-init.ps1    ← 同步到 PrivHub + 看板写进度
   └─ privhub-sync.ps1    ← 单向同步说明文件到 PrivHub
```

## 不放什么（根目录只留这些）

插件仓库根目录**只保留将来要打包进插件的文件**：

```
<插件根>/
├─ 标签字典.md        ← 每轮注入给模型的运行时资产，将来随插件打包
├─ .gitignore
└─ .npmignore
```

**`标签字典.md` 留在根目录**，因为它是**每轮注入给模型**的运行时资产
（将来落到 `lib/engine/templates/`），跟说明书性质不同——它必须跟着插件走。

开发开始后，根目录会陆续出现 `index.js` / `cordis.patch.yml` / `preset/` / `lib/` / `client.js` 等。

## 工具脚本说明

`内部文档/工具/` 下两个 PowerShell 脚本是**开发期的维护工具**，跟插件运行无关：

| 脚本 | 用途 |
|---|---|
| `privhub-init.ps1` | 登录 PrivHub → 推 `标签字典.md` → 清掉站上残留的旧说明文件 → 看板建开发进度卡 |
| `privhub-sync.ps1` | 只有同步部分（推文件 + 清旧），不动看板 |

**用法**（口令只走环境变量或交互输入，绝不落脚本）：

```powershell
# 在插件根目录执行
powershell -ExecutionPolicy Bypass -File 内部文档\工具\privhub-init.ps1
powershell -ExecutionPolicy Bypass -File 内部文档\工具\privhub-init.ps1 -DryRun   # 只看不写
```

> 脚本内部按 `$PSScriptRoot` 往上两级定位插件根目录，移动到别处会失效。

## 为什么单独放

这些文件是**给人和开发者看的说明书**，不是插件运行时需要的东西。混在插件根目录会有两个风险：

1. 被 `package.json` 的 `files` 通配进去，跟着插件一起发布；
2. 被误传上去后成为对外可见的项目内部设计。

## 怎么保证不被带出去

三重保险：

1. `.npmignore` 明确排除 `内部文档/`；
2. `package.json` 的 `files` 白名单**只列必要文件**，不用通配；
3. `privhub-init.ps1` 的清单只推 `标签字典.md`，并会清掉站上残留的旧说明文件。

> 改本文件夹内容后，记得在 `版本记录.md` 里记一笔，并提交 git。

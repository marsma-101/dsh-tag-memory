# 整理与合并的模型化改造方案

**日期**：2026-11-16
**范围**：`dtm_merge`（合并外来记忆库）、整理（tidy）的模型参与、整理 loop 的工具注入与提示词
**核心结论**：用户要的「合并调用模型」**现在根本不存在**——当前是纯程序字段搬运。这不是参数没调好，是**功能定位错了**。

---

## 一、现状：三件事的边界完全不对

### 1.1 现在各是什么

| 功能 | 现状 | 模型参与 |
|---|---|---|
| `dtm_merge` | 读对方 CSV → 按编号去重 → 同号按时距/稳定性取舍 → 整体写回 | **零** |
| `runTidy` | 读台账 → `planTidy()` 状态机算稳定性演进 → 写回 | **零** |
| `dtm_review` | 只读列出条目 | 模型可调，但只是「看」 |

### 1.2 `dtm_merge` 的实际代码（`mergeInto`）

```js
for (const rec of incomingRecords) {
  const existing = byId.get(id);
  if (!existing) { byId.set(id, rec); added++; continue; }   // 直接塞进去
  if (recordNewerThan(rec, existing)) { byId.set(id, rec); changed++; }  // 按时距/稳定性取舍
}
```

**它只做两件事**：编号去重、同号取舍。对「内容讲了什么」「该打什么标签」「该算什么形态」**完全没有能力**。

### 1.3 这导致的真实问题

**问题 A：外来库的脏字段原样落地**

2026-11-10 那次 merge 的 `tidy.jsonl`：`added=154, changed=0, conflicts=0`。

结果库里多了：
- 7 个项目名（`privhub-1` / `PrivHub` / `AI_treaning` / `dsh-tag-memory` / `.dsh` …）
- 4 个身份名
- 9 条空标签条目（**这些条目除浏览外永远召不回**）
- 纯数字标签 12 个、来源标记标签 30 个

现有《记忆合并规则》的处置是「**只产出体检报告，不自动改库**」——所以这些脏数据**至今还在库里**。

**问题 B：只能合并「自家格式」**

`readLibraryCsv` 要求九列表头。别的智能体的 `memory.md`、SQLite、JSON 导出、Markdown 清单——**一个都合并不了**。

而用户的诉求是「不论什么格式/什么软件/什么智能体的记忆文件」。

**问题 C：整理 loop 不存在**

`runTidy` 是纯程序状态机，只做「稳定性演进」这一件事。它不会：
- 补空标签
- 拆过长的条目
- 合并重复条目
- 修正形态判错

这些**都需要理解语义**，程序做不了。

### 1.4 根因

**把「需要理解语义的事」交给了程序，把「程序该做的机械事」留给了人。**

- 合并外来库 = 需要读懂内容 → 必须模型做
- 整理库 = 需要判断「这两条是不是同一件事」→ 必须模型做
- 而程序该做的是：**格式解析、字段校验、原子写入、备份、台账**——这些现在反而做得不够（只支持一种格式）

## 二、目标设计：程序管管道，模型管判断

### 2.1 职责重新划分

```
┌─────────────────────────────────────────────────────────┐
│ 程序（确定性、可测试、不调模型）                          │
│  · 格式嗅探与解析（CSV / Markdown / JSON / SQLite ...）    │
│  · 把解析结果**标准化成候选条目**（内容 + 来源元信息）      │
│  · 分批喂给模型，收集模型产出                            │
│  · 字段校验（复用 validateWriteInput + isUsefulTag）      │
│  · 备份 → 原子写入 → 台账                                │
│  · 拒绝/失败的结构化报错                                 │
└─────────────────────────────────────────────────────────┘
                          ↕ 候选条目 / 结构化产出
┌─────────────────────────────────────────────────────────┐
│ 模型（理解语义、做判断）                                  │
│  · 一条外来记录到底在讲什么 → 主要内容                     │
│  · 该算什么形态（技能/流程/规则/偏好/事实/模板）           │
│  · 该打什么自由标签（**高区分度**，用户特别强调）          │
│  · 两条是不是同一件事 → 要不要合并/取代                   │
└─────────────────────────────────────────────────────────┘
```

**关键设计原则**：模型**不直接写库**。它产出「候选条目」，程序校验后再落库。
这样模型判错了，程序还能拦（标签不合规、形态非法、内容为空）。

### 2.2 用户定的三条规则怎么落地

| 用户规则 | 落地方式 |
|---|---|
| **① 不论什么格式，都以记忆内容为主题，严格参照写入规则** | 程序负责**格式无关的解析**（输出统一的「候选条目」），模型负责**按写入规则重新表达**（形态 + 自由标签），最后走 `validateWriteInput` 同一套校验 |
| **② 固定标签按写入规则执行** | `项目`/`智能体` **直接复制来源原值**（用户明确要求）；`形态` 由模型按写入规则判；`稳定性` 恒为 `观察`（首次落库规矩）；`时距` 归 1（写入初值）；`状态` = `生效` |
| **③ 自由标签按写入规则，尽量详细、尽量可区分** | 模型生成，但**加一条硬性约束**：与库中已有条目标签重合度不得过高（见 §3.3 的区分度校验） |

## 三、具体设计

### 3.1 合并：改成「两阶段 + 模型在中间」

```
阶段 1（程序）：解析来源 → 候选条目
  输入：任意路径
  输出：[{ 来源序号, 原始内容, 原始元信息, 格式 }]

阶段 2（模型）：逐批理解 → 结构化产出
  输入：候选条目 + 现有标签网络 + 写入规则
  输出：[{ 序号, 主要内容, 形态, 自由标签 }]

阶段 3（程序）：校验 → 合并 → 落库
  校验：validateWriteInput（复用写入规则）+ isUsefulTag（标签质量）
  合并：编号去重（同号保留较新，规则不变）
  落库：备份 → 写回 → 台账
```

**为什么分阶段而不是「一次让模型看全库」**：
- 库大时（367 条 × 平均 300 字）全塞给模型不现实
- 分批可以控制 token，且**单批失败不影响其他批**
- 每批独立校验，坏批可以只跳过那一批

**批量大小**：默认 20 条/批。可配（`mergeBatchSize`）。

### 3.2 格式解析：先支持三种，按需扩展

| 格式 | 判定方式 | 解析策略 |
|---|---|---|
| **本插件 CSV** | 首行含九列表头 | `readLibraryCsv`（已有） |
| **Markdown** | 扩展名 `.md` | 按 `#`/`##` 标题切块，每块 = 一条候选；代码块内不切 |
| **JSON** | 首字符 `{` 或 `[` | 找数组，逐元素取 `content`/`text`/`memory`/`主要内容` 等常见键 |
| **其他** | 兜底 | 按空行分块，每块 = 一条候选；**在报告里明说「按纯文本切块，可能不准」** |

**设计取舍**：不追求「支持所有格式」。先覆盖三种最常见的，其余用「纯文本切块」兜底并**如实告知**。
比假装支持、结果解析出一堆垃圾强。

> ⚠️ **不做的事**：不读 SQLite（要引入依赖，违反「零运行时依赖」硬约束）。
> 如果用户真要合并 SQLite，让用户先导出成 CSV/JSON —— 这是合理的能力边界。

### 3.3 自由标签的「区分度」怎么保证（用户重点）

用户原话：「自由标签需要尽量详细，并尽量做到通过标签跟其他记忆条目进行区分」。

**光在提示词里说「要详细」是没用的**——模型会照做，但做得好不好无法度量。所以要有**程序侧的可测校验**：

```js
/**
 * 区分度检查：新条目的标签组合是否与库中某条高度重合。
 * 返回 { tooSimilar: boolean, conflictWith: 编号|null, overlap: 0~1 }
 */
export function checkTagDistinctiveness(newTags, existingRecords, { threshold = 0.8 } = {}) {
  // Jaccard 相似度：|A∩B| / |A∪B|
  // 与任一条 > threshold 且 主要内容 也不同 → 提示「标签太像，换几个更能区分的词」
}
```

**这是「提示」不是「拒绝」**：标签像不代表错（同一主题的条目本来就该共享标签）。
但模型会看到提示，从而在下一批里调整。

**更强的做法（推荐）**：在模型的输入里**直接给出该批候选的高频标签**，让它知道「这些词大家都用了，你要区分就得用更具体的词」。

### 3.4 整理 loop：现在不存在，要新建

**现状**：`runTidy` 只是状态机（稳定性演进），没有「模型参与的整理」。

**要做的**：新增一个真正的整理 loop。

```
触发：用户主动调 `dtm_tidy`（新增工具）或 UI 按钮
      （不做自动触发——整理会改库，必须人知情）

流程：
  ① 程序选出「需要整理」的候选
     · 空标签条目
     · 标签全是噪声（纯数字/单字）
     · 疑似重复（主要内容高度相似）
     · 形态为空的
  ② 分批喂给模型：候选条目 + 现有标签网络 + 整理规则
  ③ 模型产出：{ 编号, 形态?, 自由标签?, 合并到?, 归档? }
  ④ 程序校验 → 生成「改动提案」→ **先展示，等确认**
  ⑤ 确认后：备份 → 写回 → 台账
```

**关键：④ 的「先展示等确认」不能省。**
整理是改已有数据，一旦模型判错就是数据损坏。而合并是追加新数据，风险低得多。
所以：**合并可以直接做（有备份），整理必须两步。**

### 3.5 工具与提示词的注入方式

用户的诉求：「相关工具也要按照真实 loop 里的注入方式正常注入整理 loop」。

**现状问题**：`dtm_merge` / `dtm_review` 等工具是**全局注册**的（`ctx.tools.register`），
任何会话都能用。但它们**只在特定场景才该用**，平时挂在工具列表里白占 context。

**设计**：

| 场景 | 注入什么 |
|---|---|
| **日常会话**（默认） | 10 个工具全在，但 `dtm_merge` 的 description 明确写「只在用户要求导入外来记忆时用」 |
| **整理 loop** | ① 完整工具集 ② **额外的整理专用提示词段** ③ 标签网络全量 ④ 写入规则的完整版（不是压缩版） |
| **合并 loop** | ① 只需 `dtm_write` / `dtm_supersede` / `dtm_merge` ② **合并专用提示词** ③ 来源格式说明 |

**注入复用现有机制**：
- 提示词段 → `ctx.systemPrompt.section`（与现有 `renderInjection` 同一套）
- 一次性提醒 → `installWriteReminder` 同款（`agent/pre-step` + `inject-gate` 节流）
- 工具白名单 → 用 `ctx.tools.register` 的 `available` 回调按场景过滤

**不做的事**：不新造一套注入通道。现有 `section` / `context` / `reminder` 三种已经够用。

### 3.6 身份与项目：直接复制，不重新推断

用户明确：「不论是项目，还是身份都直接复制原有内容」。

**这条很重要，且与现有实现冲突**：

- 现有 `mergeInto` 确实原样保留（这点是对的）
- 但现有《记忆合并规则》建议「外来库归属未知时统一标 `引入`」——**与用户要求冲突**

**按用户要求改**：

```js
// 合并时，项目/智能体 从来源原样复制
const incoming = {
  项目: sourceRecord['项目'],      // 不猜、不改、不映射
  智能体: sourceRecord['智能体'],  // 同上
  形态: modelOutput.形态,          // 模型按写入规则判
  自由标签: modelOutput.自由标签,  // 模型按写入规则生成
  稳定性: '观察',                  // 首次落库规矩
  时距: 1,                        // 写入初值
  状态: '生效',
};
```

**例外**：来源里 `项目`/`智能体` 为空时怎么办？
→ 用 `引入`（如实记录「归属未知」），并在报告里点名。
这是「复制不到才兜底」，不是「主动改成 引入」。

## 四、分步实施

| 步 | 改动 | 可独立验证 | 优先级 |
|---|---|---|---|
| **1** | 抽 `normalizeSourceRecords()`：把任意来源解析成「候选条目」 | 三种格式各造样本，解析出正确条数 | 高 |
| **2** | 加「模型产出」的结构化契约（JSON Schema）+ 校验 | 模型输出不合规时能被拦下 | 高 |
| **3** | `dtm_merge` 改造：解析 → 分批 → 模型 → 校验 → 落库 | 合一个 `.md` 文件，标签是模型新生成的 | 高 |
| **4** | 加 `checkTagDistinctiveness()` 区分度检查 | 造两条标签 100% 重合的条目，能报出来 | 中 |
| **5** | 整理 loop：`dtm_tidy` 工具 + 两阶段确认 | 能列出「需要整理」的条目，确认后改库 | 中 |
| **6** | 整理/合并专用提示词段 + 场景化工具注入 | 两个场景的注入内容不同且完整 | 中 |

**顺序理由**：1、2 是所有后续的地基；3 是用户当前最痛的点；4 是用户特别强调的质量要求；5、6 可以后做。

## 五、需要用户拍板的两个点

> 这两个会显著改变实现路径，我给了推荐但需要确认。

### 5.1 模型调用从哪里来？

**问题**：插件目前**没有任何调用模型的通道**。它只有工具（模型来调插件），没有反向（插件调模型）。

三条路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **甲：模型主动调**（推荐） | 插件提供 `dtm_merge_prepare` / `dtm_merge_commit` 两个工具，**模型自己**解析→判断→提交 | 零新依赖，完全走现有工具通道 | 需要模型配合两步；用户得在对话里完成 |
| **乙：插件反向调模型** | 插件拿宿主 LLM 服务 | 全自动 | 需要 DSH 提供反向通道；**依赖是否稳定未知** |
| **丙：子智能体** | 起一个 subagent 专门做整理 | 上下文干净 | 复杂度高，且 subagent 也要模型调 |

**推荐甲**：它符合「一切走工具」的现有架构，且**天然有确认环节**（prepare 看结果，commit 才落库）。

### 5.2 整理要不要自动触发？

**推荐：不要。**
整理改已有数据，模型判错就是数据损坏。必须人知情、有确认。

## 六、不在本次范围

| 项 | 理由 |
|---|---|
| SQLite / 数据库直读 | 违反零依赖硬约束，让用户先导出 |
| 自动定时整理 | 改库操作不宜无人值守 |
| 跨库语义去重（「这两条讲的是同一件事」） | 需要模型判，但先做单库内的 |
| 标签网络瘦身 | 独立问题，已在别的清单里 |

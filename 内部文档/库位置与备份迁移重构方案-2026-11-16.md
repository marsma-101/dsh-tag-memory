# 库位置 / 备份位置 / 迁移：问题归因与重构方案

**日期**：2026-11-16
**范围**：`resolveLayout` 优先级链、`layoutOf` 路径派生、`migrateDataDir` 搬家、`backup.mjs` 备份与恢复
**结论**：这三块不是「参数没暴露」的问题，是**职责边界画错了**——把「位置」当成了一个可变字符串，而不是一个带生命周期的实体。

---

## 一、先看现状：一条链、三个洞

### 1.1 现状结构

```
resolveDataDir 五级优先级（决定 dataDir）
  ① config.dataDir（cordis.patch.yml，锁定）
  ② env DSH_TAG_MEMORY_DATA_DIR（锁定）
  ③ settings.json 指针（$DSH_HOME/tag-memory-settings.json，可写）
  ④ $DSH_HOME/tag-memory（默认）
  ⑤ 插件包内（最后手段，重装即丢）

layoutOf(dataDir) 从 dataDir 派生一切：
  store/memory.csv  records/*.jsonl  backup/  settings.json  store/.memory.lock
  ↑ 注意：这里的 settings.json 是数据目录内的，与 ③ 的指针文件是两个不同的东西
```

### 1.2 三个洞

| 洞 | 严重度 | 实测证据 |
|---|---|---|
| **A. 迁移目标落在源目录内部 → 无限递归复制** | **数据损坏** | 实测复刻代码顺序，嵌套 41 层后因 Windows 路径超限才中止 |
| **B. 迁移只复制、从不删源** | 数据分叉 | `moved=true` 名不副实，源目录原样留着 |
| **C. 备份目录硬编码在数据目录下，不可配** | 功能缺失 | `backupDir = <dataDir>/backup`，想放别的盘做不到 |

---

## 二、洞 A：递归复制（最严重，必须先修）

### 2.1 代码顺序决定它必然发生

```js
// index.js L2499-2507
await fsp.mkdir(dest, { recursive: true });          // ① 先建目标
const entries = await fsp.readdir(from, { withFileTypes: true });  // ② 再读源
for (const ent of entries) {
  await fsp.cp(srcPath, dstPath, { recursive: true, force: true }); // ③ 逐个复制
}
```

若 `dest` 在 `from` 内部：

1. ① 创建 `from/sub`
2. ② `readdir(from)` **会读到 `sub` 自己**
3. ③ `cp(from/sub → from/sub/sub)` → 递归

### 2.2 实测结果

复刻上述顺序，`dest = from/sub`：

```
mkdir 后 readdir(from) 读到：
  - backup [目录]
  - records [目录]
  - store [目录]
  - sub [目录]        ← 目标自己出现在列表里
```

复制时一路嵌套：

```
sub\sub\sub\sub\...\sub\backup\memory-20260101-000000.csv
Could not find a part of the path '...\sub\sub\...\sub\backup\memory-...csv'
```

**嵌套 41 层后因 Windows MAX_PATH 中止。** 在 Linux 上不会撞路径上限，会一直复制到磁盘写满或 inode 耗尽。

### 2.3 现有防护为什么不够

```js
// L2463，唯一的相关检查
if (path.resolve(dest) === path.resolve(layout.dataDir)) {
  return reject('TARGET_SAME', '目标目录就是当前目录，不需要搬。');
}
```

**只挡「相等」，不挡「包含」。** 而且用的是字符串比较，不是 `path.relative` / `path.parse` 的语义判断，连 `..` 都挡不住。

## 三、洞 B：迁移不删源，库会分叉

### 3.1 现状

```js
let moved = false;
await withFileLock(layout.lockFile, async () => {
  for (const ent of entries) {
    await fsp.cp(srcPath, dstPath, { recursive: true, force: true });  // 只复制
  }
  moved = true;   // ← 语义误导：这是"复制完成"，不是"搬迁完成"
});
```

**源目录从不删除。** 返回 `{ ok: true, moved: true }`。

### 3.2 后果

| 场景 | 结果 |
|---|---|
| 迁移成功，用户以为搬走了 | 两个目录各有一份，**之后往哪个写取决于配置** |
| 用户后来又改回旧目录 | 读到的是**迁移那一刻的旧快照**，中间的记忆全丢 |
| 磁盘占用 | 翻倍，且备份目录也跟着复制一份 |

### 3.3 为什么现在没出大事

因为迁移后会写 `settings.json` 指向新目录，下次启动读 ③ 走新库。但**旧库还在，且没有任何标记说明它已废弃**。一旦 `settings.json` 丢失/损坏/被手工改回，就会静默读到过期数据。

## 四、洞 C：备份位置与保留策略

### 4.1 备份目录不可配

`layoutOf()` 里 `backupDir = path.join(dataDir, 'backup')`，硬编码。

用户想：
- 备份放 D 盘（数据盘满了，备份盘还有空间）
- 备份放网盘同步目录
- 备份放 NAS 挂载点

**全都做不到。**

### 4.2 保留策略不可配，且只清一半

```js
backupLibrary({ ..., keep = 30 })   // 硬编码默认
pruneBackups() {
  if (!/^memory-.*\.csv$/.test(name)) continue;   // 只清 memory-*.csv
}
```

**`export-*.csv` 永不清理。** 实际数据里：

```
backup\export-20261110-105821.csv
backup\export-20261110-174724.csv
backup\export-20261110-211154.csv
```

这三个是 6 天前的，`pruneBackups` 跑过很多次，一个都没清。

### 4.3 备份与数据同盘，等于没有备份

这是最根本的问题：**备份目录在数据目录下，数据盘坏了备份一起没。**

而 `backupAuto` 这个开关（`config.backupAuto === true`）现在只控制「自动备份开不开」，不控制「备份到哪」。

## 五、根因：三层职责混在一起

### L1 设计层：把「位置」当成字符串，而不是实体

现在 `dataDir` 是一个字符串，五级优先级每级都可能给出不同的值，而**没有任何地方记录「这个库曾经在哪、搬过几次、现在以哪个为准」**。

后果：
- 无法判断旧目录是否已废弃（洞 B）
- 无法做「搬回来」（反向迁移）
- 无法审计「这个库的历史位置」

**正确的心智模型**：库是一个**有身份、有历史**的实体，位置只是它的一个属性。

### L2 实现层：迁移是「复制」而不是「搬迁事务」

现在的迁移：

```
复制 → 校验 → 写指针
```

缺了三件事：
1. **前置条件校验**（目标是否在源内部、是否同盘、是否可写）
2. **源目录的处置**（保留？标记？删除？）
3. **回滚路径**（指针写失败怎么办）

### L3 编码层：边界检查用字符串相等

`path.resolve(dest) === path.resolve(layout.dataDir)` 只能挡完全相等。
应该用「是否互为父子」判断，且必须做**符号链接解析**（`realpath`），否则 `dest` 是个指向 `from` 的软链接时同样会炸。

## 六、重构方案

### 6.1 方案选型

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **甲：最小修补** | 加父子检查 + 迁移后删源 | 改动小，1 天 | 不解决备份不可配、无历史 | ❌ 治标 |
| **乙：位置实体化** | 引入 `dataDir` 元数据（历史位置、当前生效、废弃标记），迁移变成带事务的搬迁 | 根治三个洞，留扩展空间 | 改动中等，需数据格式演进 | ✅ **推荐** |
| **丙：多库并存** | 支持同时挂载多个库 | 最灵活 | 与「单一记忆身份」的设计前提冲突，召回要合并排序 | ❌ 超出当前需求 |

**选乙。** 理由是它同时解决三个洞，且**为将来的「备份异地」「库历史审计」留了口子**——这两件事迟早要做，现在不做接口，以后要重写。

### 6.2 新结构：位置描述符

引入一个**独立于数据目录**的位置描述符文件：

```
$DSH_HOME/tag-memory-location.json
{
  "version": 1,
  "current": "/abs/path/to/data",        // 当前生效
  "backupDir": "/abs/path/to/backup",    // 可独立指定，null=默认 <current>/backup
  "history": [
    { "dir": "/old/path", "retiredAt": "2026-11-16T...", "reason": "migrated",
      "records": 367, "bytes": 354302 }   // 搬走时的快照，便于回溯
  ]
}
```

**关键设计点**：

- `current` 与 `backupDir` **解耦**。备份可以放别的盘，解决洞 C。
- `history` 记录每次迁移，**废弃的旧目录有据可查**，解决洞 B 的「不知道哪份是准的」。
- 这个文件放在 `$DSH_HOME` 下（不在数据目录内），所以迁移不会搬走它自己。
- 与现有 `tag-memory-settings.json` 的关系：**合并**。旧文件只存 `dataDir`，新文件是它的超集，读的时候做兼容迁移。

### 6.3 迁移改造成「事务」

```
① 前置校验（全部通过才继续）
   ├─ dest 必须是绝对路径
   ├─ realpath(dest) 不能等于 realpath(from)
   ├─ realpath(dest) 不能是 realpath(from) 的父或子     ← 修洞 A
   ├─ dest 所在盘必须可写（试写一个 .probe 文件）
   ├─ dest 不能已有非空 memory.csv
   └─ 磁盘剩余空间 > 源库大小 × 2

② 复制到临时目录 dest/.migrating-<ts>/
   （不直接写 dest，避免中途失败留下半成品）

③ 校验（字节数 + 记录数 + 逐行解析）

④ 原子切换
   ├─ rename(dest/.migrating-<ts> → dest/store 等)
   ├─ 写 location.json（current 指向 dest，history 追加旧位置）
   └─ 任一步失败 → 回滚 location.json，保留临时目录供排查

⑤ 源目录处置（由参数决定，默认 retire）
   ├─ retire：保留但写进 history 标记 retiredAt，并放一个
   │          `MIGRATED-TO.txt` 说明"本目录已废弃，新位置在 xxx"
   └─ delete：校验通过后删除（需显式传参，默认不做）
```

**为什么默认「保留但标记」而不是删除**：
迁移是高风险操作，用户可能想回退。留一份带标记的旧库，比删了再后悔强。
但**必须留下痕迹**——一个空的旧目录会让人以为数据丢了，一个带 `MIGRATED-TO.txt` 的目录会让人知道发生了什么。

### 6.4 备份位置独立

```js
layoutOf(dataDir, { backupDir }) {
  return {
    dataDir,
    storeDir: path.join(dataDir, 'store'),
    libraryCsv: path.join(dataDir, 'store', 'memory.csv'),
    recordsDir: path.join(dataDir, 'records'),
    backupDir: backupDir ?? path.join(dataDir, 'backup'),   // ← 可覆盖
    lockFile: path.join(dataDir, 'store', '.memory.lock'),
  };
}
```

`backupDir` 来源优先级：
```
① config.backupDir（cordis.patch.yml）
② location.json 的 backupDir
③ 默认 <dataDir>/backup
```

**注意**：`settingsFile`（数据目录内的 `settings.json`）要从 `layoutOf` 里移除。现在它是个**从未被写入的空壳**——真正的设置指针在 `$DSH_HOME/tag-memory-settings.json`。留着只会误导。

### 6.5 备份保留策略

```jsonc
// config 里新增
{
  "backupKeep": 30,              // 保留份数，0=不清理
  "backupKeepDays": 90,          // 或按天数
  "backupIncludeExports": true   // export-*.csv 是否一起清理
}
```

`pruneBackups` 改成按**模式 + 时间**双重规则：
- `memory-*.csv`：按 `backupKeep` 保留最近 N 份
- `export-*.csv`：按 `backupKeepDays` 保留最近 N 天
- **用户放进去的其他文件一律不动**（现有行为，保持）

## 七之二、实施中发现的**第四个洞**（原方案没预见到）

### 洞 D：`fsp.cp({recursive:true})` 不回调跳过规则 → 锁文件被搬到新目录

**这是端到端实测才发现的，纯逻辑单元测试完全测不出来。**

原方案的跳过规则只在**顶层**判断：

```js
for (const ent of entries) {
  if (ent.name === '.memory.lock' || ent.name.endsWith('.tmp')) continue;  // 只看顶层
  await fsp.cp(srcPath, dstPath, { recursive: true, force: true });        // 整棵树搬
}
```

但锁文件实际在 `store/.memory.lock`，**在 `store/` 目录内部**。
顶层遍历根本看不到它，而 `fsp.cp` 的 `recursive` 是整棵树搬过去，
不会回调任何过滤函数。

**后果**：新目录的 `store/` 里带着一个 `.memory.lock`，首次操作会
`LOCK_TIMEOUT`（最长等到 `staleMs`）。用户会以为"搬家把插件弄坏了"。

**实测证据**：

```
from 顶层条目：store
→ 顶层没有 .memory.lock（它在 store/ 里面）
→ 但 cp(store → staging/store, recursive) 会把 store/.memory.lock 一起带过去！
staging/store/.memory.lock 存在？ ❌ 被带过去了
```

**修法**：新增 `copyTreeFiltered`，**逐层递归并应用跳过规则**：

```js
export async function copyTreeFiltered({ src, dst, cpFn, readdirFn, mkdirFn }) {
  const skipped = [];
  await walk({ src, dst, prefix: '', cpFn, readdirFn, mkdirFn, skipped });
  return { skipped };
}
// walk 对每个子项判 shouldSkipOnMigrate，目录则递归
```

`skipped` 返回**带层级**的相对路径（`store/.memory.lock` 而非 `.memory.lock`），
因为一堆同名的锁文件分不清是哪个目录的。

**这条教训值得记住**：`fsp.cp` 的 `recursive` 是"整棵树"，任何"跳过某些文件"的需求
都不能靠"在顶层过滤 entries"实现——必须自己走树。

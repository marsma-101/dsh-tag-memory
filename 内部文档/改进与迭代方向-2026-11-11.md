## 1. 口径裁定（主子 2026-11-11，写进整理/审查说明，别再翻案）

### 1.1 「假查空」的严格定义

> **真正的假查空** = 条目本就在**可见集合**内（相同项目 / 相同智能体，或 `项目`/`智能体` 取值命中 `通用` / `引入` 白名单），语义上本该被调用，却没被返回。

- 硬筛（项目+智能体）的目的就是防记忆污染、防上下文污染。**不返回是对的。**

## 2. 写入侧失灵：明确的规矩没被记，是机制退化，不是模型偶然

> 起因：主子发现 §0 的源码/生产端规则没被记进记忆库，要求查「触发写记忆的说明和代码」有无问题。
> 结论：**说明本身没写错，但「说明 → 动作」之间没有任何程序级触发机制，而且这道机制在旧版本里原本存在、重构到 1.x 时丢了。** 属于回归，不是一次偶然疏忽。

### 2.1 说明侧：判据是对的，但只是「被动课文」

- 机器可读源 `lib/engine/templates/schema.json` 的 `writeRoutes.rules` 第一条就是：
  **「规矩（长期禁令 / 硬边界：「以后都…」「不要再…」「必须…」）→ 写 1 条，`规则`。这类最该记——不记下次照样犯。」**
- `preset/prompt.js` `renderWriteRoutes()` 把这段渲染进每轮注入的「什么情况该写」；`tests/gate2/prompt.l.test.mjs` L200-215 还专门断言「规矩 / 决策 / 踩坑 / 不写」四类判据一个不能少。
- `preset/tool-defs.js` 的 `dtm_write.when` 也写着「判定值得长期留下时（见「什么情况该写」）」。
- 所以**判据文案没问题、注入也确实到了模型面前**。问题在下面：它全靠模型每轮「自觉想起来」，没有任何机制在漏写时兜底。

### 2.2 代码侧：当前 1.x 完全没有轮级触发

全仓 grep 实证，当前 v1.3.0 源码里 **`ctx.on('agent/pre-step', …)` / `pre-step` / 漏记提醒 / 任何轮级监听器 = 0 处**。`preset/index.js` 的 `apply()` 只做三件事：注册 10 个工具、挂固定判据段（`systemPrompt.section`）、挂身份段（`systemPrompt.context`）。`index.js` 的 `apply()` 也只 `provide` 服务 + 身份投影 + 定时器 + 启动自检。

也就是说：**写不写，100% 取决于模型这一轮自己判。** 模型一旦把注意力放在「分析 / 出报告 / 写文档」上，`dtm_write` 就不会触发；而漏写之后**没有任何东西会提醒、不会记一次「疑似漏记」、也不进任何台账**——静默丢掉。

本轮就是活例：上一轮我把 §0 规则写进了 md，却没调 `dtm_write`；直到主子点破才补记。这恰好印证 `writeRoutes.rules` 自己那句「不记下次照样犯」。

### 2.3 关键证据：旧版本曾经有「漏记提醒」，重构时丢了

归档的旧版实现（`G:\AI_treaning\dsh插件\插件发布规则和辅助\_work_preset.js` L1055-1137，以及 `_container_now.js`）里有一套完整的 `agent/pre-step` 漏记提醒：

| 组成 | 旧版做法 | 现状 |
|---|---|---|
| 轮级钩子 | `ctx.on('agent/pre-step', …)`，step≥2 时检查 | **0 处** |
| 写没写过 | `ctx.on('tools/result', …)` 观察 `memory_write` / `memory_supersede`，按 agent+turn 用 WeakMap 记 `wrote` | **无** |
| 触发条件 | 本轮见过真实 user 消息、且没写过、且没提醒过 → 追加一条 user 角色提醒「这一轮还没写记忆。如果有该记的规矩/决定/坑，先调 memory_write…」 | **无** |
| 去重 / 插入 | `isDeepStrictEqual` 去重 + `toSpliced(lastClaimedIndex+1, 0, desired)` 插在已认领消息之后 | **无** |
| 注入里的自检 | 旧版还有一句「**答复前自问**：这一轮中了哪条必写？…中了就立刻 memory_write / memory_recall」（`_work_preset.js` L265） | 现注入**也已无**（全仓 grep「自问/答复前/必写」0 处） |

旧版还明确写了设计理由：**「只做一件事：这一轮调过 memory_write 没有。不判内容——判据给模型用，不要在程序里分类用户输入（正则/关键词必崩）。宁可少提醒，也不误判。」** 这条原则现在依然成立，值得原样沿用。

> 结论：不是「当初没想到」，是**架构从 0.3.x 重构到 1.x（9 列 / 10 工具 / section+context 拆分）时，把轮级提醒这道兜底一起删了，且没有用等价机制补回来**。判据文案留着，兜底没了 → 判据变成「靠自觉」，而库里 `M-20261011-049` 自己记着「靠自觉 = 没有机制」。

### 2.4 根因归纳

1. **触发链只有半截**：`说明（判据）→ 模型自觉 → dtm_write`。缺「本轮该不该写」的轮级检查点，也缺「漏写后可见」的反馈（台账 / 提醒）。
2. **回归未被测出来**：`prompt.l.test.mjs` 只断言「判据文本存在」，不断言「有轮级触发」；旧版那条 `pre-step` 用例随重构一起消失了。判据在、机制不在，测试全绿也照漏。
3. **文档与记忆库被混为一谈**：本轮我把规则写进 md 就以为「交代完了」，缺少 §1.4 那条口径来区分两种落点。
4. **与 §4.6 同构**：反馈回路断在写入侧（漏写无痕）、也断在读取侧（`feedback` 占位）。两头都没有「实际发生了什么」的记录，整理环节自然无从演进。

### 2.5 改进方向（落进 §4）

- **【P0，新增 §4.7】恢复轮级漏记提醒**：按旧版原则重做，但适配 1.x —— 工具名换 `dtm_write` / `dtm_supersede`，钩子用当前 DSH 的 `agent/pre-step` + `tools/result` 契约；**只判「这轮写没写过」，绝不判内容**；提醒走消息历史或工具返回值，不塞进 system prompt（KV cache 硬约束）；去重、每轮最多一次、可关闭。
- **配套**：注入补回一句「答复前自问」式自检（受 6000 字节预算约束，用词压到最短）；补一条**断言「轮级触发存在」**的测试，而不只是断言「判据文本存在」。
- **台账**：漏写 / 疑似漏记要不要记一条信号，与 §4.6 的 feedback 定稿一并设计（别再各造一套）。
- **说明**：§1.4 口径写进整理说明与审查清单。

## 3. 复测结论：同口径下**确实存在**真正的假查空

按主子要求重测。方法：直接调 `lib/engine/read.mjs` 的纯函数 `recall()` 读生产库 `memory.csv`（166 条），**绕过宿主 `dtm_recall`**——不写台账、不加时距、不产生副作用。范围严格锁在 `项目=dsh-tag-memory` + `智能体=萧潇`（即相同项目/身份 + 通用/引入白名单可见集合）。

**探针设计**：对每条「有标签的可见条目」，取它自己的前 k 个标签当查询词，看它是否出现在 `hits` 里。这是最强的自证——查询词 100% 来自条目本身，语义必然指向它。

| 探针（取前 k 个标签） | 出厂 `entryRatio=0.5` 返回率 | 假查空率 |
|---|---|---|
| k=1（模型最常见：只给 1 个词） | 1 / 65 | **98.5%** |
| k=2 | 8 / 65 | 87.7% |
| k=3 | 53 / 65 | 18.5% |
| k=5 / 全部 | 65 / 65 | 0% |

- 可见集合 74 条，其中 65 条有标签、9 条空标签（空标签另算，见 §4.2）；平均每条 **4.69** 个标签。
- **失败原因 100% 是 `ENTRY_RATIO`**，没有一条是 `QUERY_FLOOR` / `BELOW_PASS_LINE` / 硬筛。即：条目确实在可见集合里、分数高达 **90~93 分**（形态命中 50 + 标签命中 40 + 时距），却仍被否决。
- 对照：同一批探针把 `entryRatio` 降到 `0.3` → k=2 假查空率 87.7%→7.7%、k=3→0%；降到 `0.1` → k=1 即 0%。**说明这是阈值问题，不是隔离问题。**

### 根因（算术层面，已定位到具体代码）

`lib/engine/read.mjs:388` 的条目侧否决：

```
e_ratio = 命中标签数 ÷ 该条目的标签总数，要求 严格 > entryRatio(0.5)
```

写入规范（`标签字典.md` §自由标签 / `schema.json` `writeRoutes`）鼓励从「作用 / 注意事项 / 内容关键词」三方向拆标签，实库平均 4.69 个。于是：

| 条目标签数 | 要过 `>0.5` 至少需 query 命中几个 |
|---|---|
| 3 | 2 |
| 4 | 3 |
| 5 | 3 |
| 6 | 4 |
| 7 | 4 |

而模型一次查询通常只给 1~3 个词 → **标签打得越规范、分母越大，越召不回来**。这是写入规范与读取闸门两头没配平，属于设计层缺陷，不是数据脏。

> 备注：`entryRatio=0.5` 与 `q_ratio>=0.15` 的 `>`/`>=` 差异是逐位冻结的裁决（`内部文档/简化评估结论.md` §3.9），**不要顺手改判定符**；要动只动阈值数值，且改完补对应测试用例。

## 4. 改进与迭代方向

按主子归纳的三条主线 + 体检暴露项组织。每项都标**落点（源码文件）**与**验收**，方便直接派活。

### 4.1 【P0】召回阈值标定：让「同口径该召回的能召回」

对应主子结论 1 的后半「如果有，找出原因」——已找到，见 §3。

| 方向 | 说明 | 落点 |
|---|---|---|
| 重新标定 `veto.entryRatio` | 出厂 0.5 与「平均 4~5 标签」的实库不匹配。候选 0.3（温和）/ 0.1（彻底）；**不要一步到 0.1**，先用 0.3 做前后对比 | `lib/engine/templates/scoring.json` |
| 或改成「与标签数无关的口径」 | 例如改为按 `hit` 绝对数、或 `e_ratio` 分母改用 `min(条目标签数, query标签数)`、或引入 `hit>=1 且 q_ratio 达标` 的兜底分支 | `lib/engine/read.mjs`（`scoreRecord` / 闸门②） |
| 补回归用例 | 现 `tests/engine/read.*.test.mjs` 只冻结了「=0.5 不过」，没有「多标签条目 + 少标签 query」的用例，所以这个偏差一直没被测出来 | `tests/engine/` 新增用例；同步 `tests/gate3/` |

**验收（同一套指标，改前/改后对比）**：用 §3 的探针脚本跑 `k=1/2/3`，报 `passed / hits / QUERY_OFF_DIRECTION / 假查空率`；要求同口径假查空率显著下降，且**跨项目/跨身份隔离结果不变**（硬筛不受影响），全量测试 0 失败。

**调节位置提醒**：`scoring.json` 是出厂默认。用户侧调节走插件 `Config` 的 `scoring` overrides（`lib/engine/dict.mjs` `loadScoring` 深合并），不要改数据包内容去迁就单台机器。

### 4.2 【P1】自由标签：单独建「自由提示词说明表」，读写前先给规则

主子结论 3 明确指定的方案，**方向采纳**。现状问题：

- 实库 566 个唯一标签，**469 个（83%）只出现一次**；`tag-equivalence.json` 只收了 17 组技术同义词（发版/上线/deploy…），与实库高频词（原话、推断、坑、dsh…）几乎不重叠。
- 标签里混进纯数字（`3190`/`14080`/`0`/`2`）、来源标记（`原话`14 / `推断`16）——这些不会被当查询词，却白占 `e_ratio` 分母，放大 §4.1。
- 可见集合里 **9 条条目自由标签为空**，按 `read.mjs:22-25` 裁决，除「浏览形态」外任何带标签查询都召不回（写入侧虽有 `TAGS_EMPTY` 拦截，但合并进来的旧条目绕过了它）。

**方案**：单独放一份《自由标签提示词说明表》（建议 `lib/engine/templates/free-tag-rules.json` 或 `内部文档/自由标签说明表.md`，机器可读源 + 人读副本各一），内容只放「少量说明」，规范两件事：

1. **写入侧**：标签从哪三个方向取、什么该打（正文实词、短词、一个标签一个概念）、什么不该打（纯数字、来源标记、转述句、同义变体、超过 6~8 个就该收）、`|` 禁用、上限 20。
2. **读取侧**：一次给几个词、优先给哪类词、怎么配合形态、查空了怎么办（不反复换说法）。

**交付方式（关键）**：不加第 11 个工具（注入预算只剩 ~84 字节 / 46 行，`内部文档/简化评估结论.md` §五）。走现有通道：

- 在 `dtm_write` / `dtm_recall` 的**工具 description 或返回值前置提示**里，先给这张表的要点，再让模型填 `自由标签`；
- 或按 `preset/prompt.js` 现成的「判据放 schema、渲染器只排版」分工，把说明表挂进 `schema.json` 的 `writeRoutes` / 新增 `tagRules` 段，由 `renderWriteRoutes` 一类渲染器注入；
- 全文说明放表文件里，**每轮只注入极短一段**，避免撑破 6000 字节预算。

**验收**：注入总字节仍 ≤6000、工具数仍 10；新写入条目的标签数收敛、单例标签占比下降；按 §3 探针，同口径假查空率随标签规范化进一步下降。

### 4.3 【P1】合并记忆条目的规则不明确 —— 需要制定成文规则

主子结论 2。11-10 那次 merge 的 `tidy.jsonl` 实证：`added=154, changed=0, conflicts=0`。`index.js` `mergeLibrary`（L1791-1895）目前**只做 4 件事**：源存在校验、表头校验、按编号去重（同号保留「较新」）、整体写回 + 备份 + 记台账。**不校验、不归一任何字段取值**——旧库的 `项目` / `智能体` / `稳定性` / `时距` / 空标签全部原样落地。

现有 `内部文档/已有库检测与处置规则.md` 管的是「装完发现已有库怎么办」（格式/多库/问人），**没有覆盖「用户主动合并一份外来库时，字段口径怎么归一」**，这是空白。

**要定的规则（写进文档 + 落进 `mergeLibrary` 的 dryRun 预演）**：

| 维度 | 现状 | 待定规则方向 |
|---|---|---|

### 4.4 【P2】自动整理：设置界面有，但「提醒用户」这条链路要补

主子结论 3（末段）。**先如实核对源码**（已做）：

- 设置页**确实有**「自动整理」卡片：`client.js` L2331-2392，显示 `tidyAuto`（开/关）、`tidyFrequency`，并有「预览要改什么 / 立即整理」两个按钮（走 `runTidy`）。
- 宿主 `index.js` L1986-1989 的 `overview` 把 `tidyAuto: config?.tidyAuto===true`、`tidyFrequency` 透传给设置页。
- 定时器 `index.js` L2036-2051：`autoTidyIntervalHours > 0` 时按间隔判定，**只往 `ctx.logger.info` 写一行「建议整理」**，不自动改库（整理需模型参与，这是对的）。
- **但有两处要如实标注**：① 设置页文案自己写着「频率与开关的取值域仍在细化中（《功能说明》§10.2 标注为待定稿），此处先如实显示宿主当前值」——即 UI 目前是**只读展示**，没有开关控件让用户直接改 `tidyAuto` / `tidyFrequency`；② 定时器读的是 `config.autoTidyIntervalHours`，与设置页显示的 `tidyAuto` / `tidyFrequency` 是**两套键**，源码里未发现二者的换算/同步。这两点属于「待定稿」而非 bug，但改进时要一并理顺，别让用户在界面上设了却不生效。

**改进方向（主子给的两条 + 一条源码厘清）**：

1. **每周提醒**：未开启自动整理、且距上次 `tidy.jsonl` 有整理动作超过 7 天时，提醒用户「手动整理一次」或「去设置页开启自动整理」。落点：`lib/engine/schedule.mjs` 增一个纯判定（复用现有 `isTidyDue` 的写法，别新造一套）、`preset/prompt.js` 注入一句极短提示（受 6000 字节预算约束）、或走工具返回值通道。
2. **提醒逻辑要成套**：触发条件、去重（一周内不重复提醒）、用户忽略后的退避、提醒里带「上次整理时间 / 库里待整理条目数」——做成可配置、可关闭，别变成每轮刷屏。
3. **理顺配置键**：定稿 `tidyAuto` / `tidyFrequency` / `autoTidyIntervalHours` 三者的关系（一个来源、一个换算），设置页从只读展示升级为可设；补对应测试（`tests/gate3/timer.test.mjs` 已有整理提醒分支用例，扩展它）。

### 4.6 【P2】演进回路的数据源（本次体检暴露，立项备查）

`read.jsonl` 每行 `feedback` 恒为 `[]`；`read.mjs` L491-515 注释自认是「占位参数，落盘形态待定稿」。`tidy.mjs` `foldFeedback` 只能「命中即视为 ok」保守近似 → 状态机缺少真实信号源，稳定性自动演进实际上转不起来。

> 这与 §1.3「刚装未整理属正常」不矛盾：没整理是正常，**但回路要能转**是另一件事。列为改进项，不标成现网故障。

方向：定稿 feedback 的落盘形态（原地更新原行 / 另起 `action=feedback` 行），让「命中且被采纳 / 命中未采纳 / near 反复出现」有真实记录；再让 `runTidy` 用它演进。改这条要同时补 `tests/engine/tidy.k.test.mjs` 的用例。

### 4.7 【P0】恢复轮级「漏记提醒」，把写入触发链补全

> 本项由 §2 直接立项，是主子本轮点破的问题。**优先级高于 §4.1**：召回阈值影响「已经记住的东西取不取得出来」，而这一项影响「该记的东西根本没进库」——后者更根本。

**要做什么**：按旧版（`_work_preset.js` L1055-1137）已验证过的原则重做，适配 1.x：

| 落点 | 内容 |
|---|---|
| `preset/index.js` | 挂 `ctx.on('agent/pre-step', …)`：step≥2 时，若本轮见过真实 user 消息、且没写过、且没提醒过 → 追加一条极短提醒 |
| `preset/index.js` | 挂 `ctx.on('tools/result', …)`：观察 `dtm_write` / `dtm_supersede`，按 agent+turn 用 WeakMap 记 `wrote` |
| `preset/prompt.js` | 注入补回一句「答复前自问」式自检（压到最短，受 6000 字节预算约束） |
| `tests/` | **新增断言「轮级触发存在」的用例**；不能只断言「判据文本存在」（`prompt.l.test.mjs` 现状） |
| 说明 | §1.4 口径、§1.1~1.3 三条裁定写进整理说明与审查清单 |

**必须沿用的旧版原则（别重新设计）**：

1. **只判「这轮写没写过」，绝不判内容**。判据给模型用；程序里做正则 / 关键词分类必崩，换一种说法就漏。宁可少提醒，也不误判。
2. **提醒走消息历史或工具返回值，不塞进 system prompt**（KV cache 硬约束：`section` 内容一变，其后缓存全废）。
3. 去重（`isDeepStrictEqual`）、每轮最多一次、插在已认领消息之后（`toSpliced` 语义）、异常一律放行不卡住对话、可关闭。
4. 工具名换 1.x 的 `dtm_write` / `dtm_supersede`；钩子按**当前 DSH 版本**的 `agent/pre-step` + `tools/result` 契约核实后再写（旧版是 0.3.x 时期的 API，别照抄参数形状）。

**配套设计（与 §4.6 合并考虑，别各造一套信号）**：漏写 / 疑似漏记是否记一条台账信号。写入侧与读取侧都缺「实际发生了什么」的记录，feedback 定稿时一并定。

**验收**：

1. 造一轮「用户下达明确规矩但模型未调 `dtm_write`」的对话 → 提醒必须出现且只出现一次；
2. 造一轮「已调 `dtm_write`」→ 不出现提醒（不误报）；
3. 造一轮纯闲聊 / 一次性提问 → 不提醒（不刷屏）；
4. 注入总字节仍 ≤6000、工具数仍 10、缓存不因提醒而重建；
5. 全量测试 0 失败；旧版 `pre-step` 的行为逐条对齐（去重、插入位置、异常放行）。

# 架构简化评估结论

> 评估对象：`dsh-tag-memory` v1.2.8 源码（简化前 8763 行 / 简化后 8099 行）
> 评估方式：两个子智能体分别评审「后端（index.js + lib/engine）」与「前端（client.js + preset）」，
> 逐条核实后只采纳**不影响功能**的建议，其余明确驳回。

---

## 一、架构现状

```
dsh-tag-memory/
├── index.js             1662 行   宿主服务 dtmHost：40 个嵌套函数共享一个闭包
├── client.js            2705 行   前端单文件（React h()），CSS + 页面 + 弹窗
├── preset/               1392 行   10 个 dtm_* 工具的注册与排版
│   ├── index.js          153     插件入口：注册工具 + 两段注入
│   ├── tool-defs.js      276     工具定义（参数 schema）
│   ├── tools.js          363     execute* 接线
│   ├── define-tool.js    362     参数 DSL → JSON Schema 编译器
│   ├── format.js         236     工具返回值排版
│   └── prompt.js         202     注入渲染
└── lib/engine/          2140 行   零框架核心（不 import @deepseek-ai/* 或 cordis）
    ├── core.mjs          548     CSV 读写、锁、编号、路径
    ├── read.mjs          441     召回：硬筛 → 打分 → 否决
    ├── tidy.mjs          330     整理：稳定性状态机、归并
    ├── write.mjs         240     写入校验、造记录
    ├── dict.mjs          198     schema/字典加载
```

**分层是正确的**：`lib/engine` 零框架依赖（可独立测试）、`preset` 只做接线与排版、
`index.js` 提供宿主服务、`client.js` 是纯 UI。没有循环依赖。

## 二、已采纳并修复（全部实测通过）

### 2.1 真实功能缺陷

| # | 问题 | 影响 | 修复 |
|---|------|------|------|
| 1 | **备份/恢复/合并弹窗从未被渲染** | 260 行弹窗实现 + 4 个宿主方法 + 完整 locale 全部就绪，但设置页既没有按钮也没有 mode 状态。UI 文案却写着「用「备份/恢复/合并」按钮操作」——**对用户承诺了一个不存在的按钮** | 接上 3 个按钮 + mode 状态 + 弹窗渲染 |
| 2 | `formatWriteResult` 的 `identity` 形参从未被传入 | 「归属：智能体=」**永远不输出**；而宿主 `writeEntry` 已经返回了 `who` 字段（白算） | 改为直接读 `result.who` |
| 3 | **工具取值域与 schema.json 脱钩** | preset 传 `config?.shapes`，但宿主**刻意不导出 Config**（有踩坑记录）→ config 恒为 `{}` → domain 恒为 undefined → `buildToolDefs` 只能走硬编码兜底。注释却声称「从 schema.json 传入」。用户改 schema 加一种形态，注入显示 7 个、工具 enum 还是 6 个，模型选了新值会被拒 | 新增 `domainFor()` 复用 `schemaFor()` 的 mtime 缓存，两边同源 |

| 5 | `.dtm-cell-actions` 重复定义两次 | 后一处覆盖前一处并丢掉 `width:1%`，操作列会被撑宽 | 合并为一处 |

## 三、驳回的建议（附理由）

### 3.1 「拆解 `createHostService` 的 40 个嵌套函数」— 驳回

这些函数**共享同一个闭包**（`resolveLayout` 的结果、锁队列、配置缓存）。
提到顶层就要么每次重算 `resolveLayout`（20+ 次调用），要么显式传一长串上下文。
当前形态是**有意的**，不是疏漏。

### 3.2 「拆解 `retagEntry`（177 行）」— 驳回

它是 6 段**线性校验流水线**：单参兼容 → 字段白名单 → 身份判定 → 改库前备份 →
逐字段校验 → 写台账。每段依赖前一段的结果，拆成独立函数需要传递 5~6 个中间变量，
反而更难读。行数来自校验项多，不是冗余。

### 3.3 「表格化 `buildRemoteSpec`（156 行 / 14 方法）」— 驳回

子智能体自己也标注「能减但值得犹豫」。当前每个方法显式写出参数名与类型，
是**契约的可读形式**——评审 14 个 remote 方法的签名时，表格化会让差异藏在数据里。

### 3.4 「抽取 `EntriesPage.load` / `SettingsPage.load` 的共同异步骨架」— 驳回

两处**数据形状和 setter 完全不同**（一个设 items/total/overview/facets，
另一个设 settings/facets）。能共享的只有 `alive` 标志管理，约 10 行，
却要引入一层 hook 抽象。收益/风险比不划算。

### 3.5 「抽取 JSX 重复（`dtm-field` + label + control 出现 6~7 次）」— 驳回

最多省 10 行，但会动到表单渲染路径。**UI 回归风险 > 收益**。

### 3.6 「删除 `define-tool.js` 的 `oneOf` / `json` 分支」— 驳回

当前 10 个工具确实没用到，但这是**参数 DSL 的能力**，已被文档化为支持的特性。
删掉会让未来加工具时受限。这是设计取舍，不是死代码。

### 3.7 「去掉 5 个 engine 的多余 `export`」— 驳回

`backupStamp` / `readLibraryCsvSync` / `loadJsonFresh` / `normalizeTags` ×2
确实无外部引用，但 engine 作为**零框架独立库**保留导出是合理的弹性，
去掉只省 5 个关键字。

### 3.8 「`read.mjs` 与 `write.mjs` 的 `normalizeTags` 重复，合并」— 驳回

**两者语义不同**：`read.mjs` 的会套用同义归一（`canonicalOf`），
`write.mjs` 的只做 trim + 去重（写入时不该归一，否则用户填的原词会被改写）。
同名但职责不同，合并会破坏语义。

## 五、注入预算（唯一受限资源）

```
[L4 实测] bytes=5916/6000  lines=84/130  tools=10  shapes=6
```

仅剩 **84 字节 / 46 行**余量。这是**有意的紧约束**，不是浪费：

- `### 入口`（1170 B）：工具表 + 写入判据
- `### 被拒了怎么办`（552 B）：错误 → 纠正的闭环，让模型知道被拒是「补参数」不是「库用不了」
- `### 读`（405 B）：召回参数与命中解释

每一段都有明确目的，为省字节而削减会直接降低模型的工具使用正确率。
**不建议为了「看起来更小」而压缩这里。**

## 六、最终结论

**这个库不是「臃肿该大改」的状态。**

- 分层清晰、无循环依赖、无死代码
- 8 个「看起来可以简化」的点，核实后 6 个是**有意的设计**，2 个收益 < 风险
- 真正的收益不在「减少行数」，而在**修复 5 个真实缺陷**（尤其弹窗未接、取值域脱钩）

行数从 8763 → 8099（−664），其中：
- −83 行是死代码清理
- +92 行是**接上弹窗**（功能补全，不是膨胀）

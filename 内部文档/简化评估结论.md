# 架构简化评估结论

> 评估对象：`dsh-tag-memory` v1.2.8 源码
> 评估方式：两个子智能体分别评审「后端（index.js + lib/engine）」与「前端（client.js + preset）」，
> 逐条核实后只采纳**不影响功能**的建议，其余明确驳回。
> 规模：9995 行 / **代码 6526 行** / 注释 2575 行（26%）。

---

## 零、最重要的发现：一个从未启动过的功能分支

后端评审抓到一个**用户可触达的功能缺陷**，价值远超所有行数优化：

`tidyTimer` 在 4 处被使用（赋值 / unref / clearInterval ×2），但**从来没有 `let` 声明**。
ESM 严格模式下那是 `ReferenceError`。

后果链条：

```
用户配置 autoTidyIntervalHours > 0
  → startTimer() 在第二个 setInterval 处抛 ReferenceError
  → 被 registerTimer 的 try/catch 吞掉
  → 只留一行容易忽略的 warn
  → 整理提醒从来没响过
  → 连已经建好的备份定时器也一并失去管理（异常位置决定行为，很脆）
```

**为什么 327 条测试全绿却没抓到**：`timer.test.mjs` 的三条用例
**全部只传 `autoBackupIntervalHours`**，`autoTidyIntervalHours` 分支从未被执行过。
一个配置分支如果没有用例走过它，就等于没实现。

**修复**：1 行声明 + 1 条用例。新用例断言「两个 timer 都建出来 + 都已 unref +
无启动失败告警 + dispose 幂等」。实测对照：

- 移除声明后跑新用例 → 分支抛错、进程挂住（timer 未被清理）
- 恢复声明后 → 2 个 timer 正常创建、均 unref、无告警

## 三、驳回的建议（附理由）

### 3.1 「拆解 `createHostService` 的 40 个嵌套函数」— 驳回

这些函数**共享同一个闭包**（`resolveLayout` 的结果、锁队列、配置缓存）。
提到顶层就要么每次重算 `resolveLayout`（20+ 次调用），要么显式传一长串上下文。
当前形态是**有意的**，不是疏漏。

### 3.2 「拆解 `retagEntry`（177 行）」— 驳回

它是 6 段**线性校验流水线**：单参兼容 → 字段白名单 → 身份判定 → 改库前备份 →
逐字段校验 → 写台账。每段依赖前一段的结果，拆成独立函数需要传递 5~6 个中间变量，
反而更难读。行数来自校验项多，不是冗余。

### 3.3 「表格化 `buildRemoteSpec`（156 行 / 14 方法）」— 驳回

子智能体自己也标注「能减但值得犹豫」。当前每个方法显式写出参数名与类型，
是**契约的可读形式**——评审 14 个 remote 方法的签名时，表格化会让差异藏在数据里。

### 3.4 「抽取 `EntriesPage.load` / `SettingsPage.load` 的共同异步骨架」— 驳回

两处**数据形状和 setter 完全不同**（一个设 items/total/overview/facets，
另一个设 settings/facets）。能共享的只有 `alive` 标志管理，约 10 行，
却要引入一层 hook 抽象。收益/风险比不划算。

### 3.5 「抽取 JSX 重复（`dtm-field` + label + control 出现 6~7 次）」— 驳回

最多省 10 行，但会动到表单渲染路径。**UI 回归风险 > 收益**。

### 3.6 「删除 `define-tool.js` 的 `oneOf` / `json` 分支」— 驳回

当前 10 个工具确实没用到，但这是**参数 DSL 的能力**，已被文档化为支持的特性。
删掉会让未来加工具时受限。这是设计取舍，不是死代码。

### 3.7 「去掉 5 个 engine 的多余 `export`」— 驳回

`backupStamp` / `readLibraryCsvSync` / `loadJsonFresh` / `normalizeTags` ×2
确实无外部引用，但 engine 作为**零框架独立库**保留导出是合理的弹性，
去掉只省 5 个关键字。

### 3.8 「`read.mjs` 与 `write.mjs` 的 `normalizeTags` 重复，合并」— 驳回

**两者语义不同**：`read.mjs` 的会套用同义归一（`canonicalOf`），
`write.mjs` 的只做 trim + 去重（写入时不该归一，否则用户填的原词会被改写）。
同名但职责不同，合并会破坏语义。**建议改名区分**（`canonicalizeTags` / `dedupeTags`）
而不是合并——但改名会动到调用点，暂不做。

### 3.9 后端评审额外标出的红线（看着像不一致，其实是有意为之）

这几处极易被后来的重构者"顺手统一"，逐条记下：

| 位置 | 看起来像 | 实际是 |
|------|---------|--------|
| `retagEntry` 的双形状派发（首参有 `编号`/`patch` 且无 `.session` 即 payload） | 过度防御 | `REMOTE_SIGNATURES.retagEntry = ['request']` 是**单参**端点，工具侧是双参。改成统一双参会让远程端点把 request 塞进 agent 位，恒报 `ID_REQUIRED`。这是 2026-11-08 修的「界面点保存看起来成功、其实什么都没改」 |
| `identityOfSync` 里 WeakMap 优先于投影 | 顺序可以理顺 | 这是 F1b 修复。`bindIdentity` 不能 append 自造事件（官方禁止新 event type），只能写 WeakMap；若投影优先，同一会话内换绑会被旧投影值静默覆盖 |
| `read.mjs` 闸门里 `>`（e_ratio 0.5）与 `>=`（q_ratio 0.15）不一致 | 手滑 | `e_ratio = 0.5` 必须**不过**、`q_ratio = 0.15` 必须**过**，是逐位冻结的裁决，有对应用例 |
| 备份位置：`retagEntry` 在锁外，`archiveEntry` 在锁内 | 风格不统一 | archive 放锁内是 2026-11-06 的修复（原位置导致被拒的归档也白留备份）；retag 必须在锁外，因为字段校验在锁内、失败时仍需保留「改库前」快照 |
| 注释密度约 30%（`schedule.mjs` 51%、`migrate.mjs` 38%） | 废话多 | 是公开插件的裁决记录（「两个不同的 10 别混」、`0/0` 为什么定 0、「为什么只 warn 一次」）。删注释是负收益 |
| `serviceObj` + `HostServiceProto` + `new Function` 包装 | 构建期可消掉的机械代码 | gateway 的 `remoteMethods()` 只读原型符号描述符、`methodParameterNames()` 只从原型链找实现且用 `Function.toString()` 解析参数名 |

## 六、最终结论

**这个库不是「臃肿该大改」的状态。**

- 分层清晰、无循环依赖、**已无死代码**（40 + 44 个函数全部有引用）
- 17 个「看起来可以简化」的点，核实后 **11 个是有意的设计**（其中 5 条是
  踩过坑的修复，动它会重新引入 bug），6 个收益 < 风险
- 真正的收益不在「减少行数」，而在**修复 6 个真实缺陷**
  （尤其弹窗未接、取值域脱钩、`tidyTimer` 未声明）

**代码 6526 行、注释 2575 行（26%）**。本轮净变化：
- −83 行死代码清理
- +92 行**接上弹窗**（功能补全，不是膨胀）
- −28 行后端去重（`idNewerThan` / `readLibraryCsvSync` / `stamp` / `toLocalIso`）
- +1 行 `tidyTimer` 声明（救活整个整理提醒分支）
- +70 行测试（覆盖那个从未被执行过的配置分支）

**净增约 50 行，但修好了 6 个缺陷、删掉 2 处误导性死代码。**
这才是正确的方向——行数不是目标。

### 真正的收益不在行数上

两位评审者的结论一致，而且都写在了报告末尾：

> 这不是一个「靠删代码能变好」的仓库。真正的收益在三处，**都不在行数上**：
> ① **正确性**（`tidyTimer` 的 `ReferenceError`：0 行修复，救活一整个功能分支）
> ② **单一数据源**（四份时间格式化、两对「共用文案」——这些是将来会漂的）
> ③ **死代码的误导性**（注释承诺了不存在的调用方/消费者）
>
> **误导性注释比多余代码更贵。**

### 可安全简化的量：已接近上限

后端评审的量化结论：**约 68 行 / 4817 行 ≈ 1.4%**（占 `index.js` 约 3.2%），
若连中等风险项一起做，上限约 **95 行 ≈ 2.0%**。本次已做掉其中的低风险部分。

**这个数字本身就是结论**：1308 行有效代码承载了 27 个宿主方法 + 5 级目录优先级 +
3 道冻结闸门 + 无开关备份，密度已经很高。继续"瘦身"只会开始损伤可读性。

### 关于「从 1679 行的闭包里抽方法」

诚实结论：40 个内部函数里只有 **6~7 个真正闭包无关**
（`recordNewerThan`、`pickEditable`、`packageFallbackWarning`、`lockedHintOf`、
`currentDshHome` 等）。把它们提到模块顶层能缩小闭包、让它们可单测，
但**省 0 行**。剩下 33 个分别吃 `config` / `cfgCache` / `identityFallback` /
`lastBackupAt` / `timer` / `tidyTimer` / `ctx` / `PACKAGE_DIR` 中的一个或多个，
硬抽就要传 8 个参数或建上下文对象——**那是架构改写，明确不做**。

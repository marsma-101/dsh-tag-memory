**审计对象**：`dsh-tag-memory@1.4.4`（源码仓 = 生产端逐字节一致，`index.js` SHA256 `D62FFCAE…2642` 两端相同）
**审计数据**：生产库 `C:\Users\Administrator\.dsh\tag-memory\store\memory.csv`（358 条）+ 三本台账 `records/{write,read,tidy}.jsonl`
**审计时间**：2026-11-16
**审计方式**：全部结论来自**插件自身引擎函数**跑真实库副本（`readLibraryCsv` / `recall` / `applyTick` / `planTidy` / `foldFeedback` / `makeHostCtx` 宿主链路），不靠读代码猜、不靠事后兜底结论。

## 〇、一句话结论

库里的**写入侧是通的，读取侧是通的，但「让记忆随时间变好或退场」这条链路基本没在跑**：

- 时距（tick）确实在累加，但它**封顶 10 → 打分最高只能拿 6.64 分**，而配置声称满分 10；测试用一个真实运行中**不可能出现**的 `时距=32` 断言满分，把这条数学矛盾盖住了。
- 稳定性状态机**唯一的数据源 `feedback` 从 2026-11-10 至今恒为 `[]`**，实际靠「命中即 ok」的隐含默认在跑；而 `ok` 次数恰好等于 `时距-1`——两个「独立」的升格条件其实是同一个计数器。
- 稳定性**不参与召回的任何环节**（打分、过滤、排序都不读它），升到「稳定」在召回层面零收益。
- 全库**没有任何时间/时效字段**，也没有任何「闲置→归档」判定。7 天写 195 条、退场 0 条，库从 164 涨到 358（+118%）。这就是你说的「一次性记忆没有退场机制」。
- 顺带查出一个**测试通过但生产路径坏**的真缺陷：`read.jsonl` 里 `near` 存的是 `"M-xxx 分=50 e_ratio=0"` 字符串，`foldFeedback` 把整串当编号，69 条 near 反馈全落在垃圾 key 上。

### 检查点 A：时距机制——数值口径自相矛盾

**实测（`_audit-probe5` / `_audit-probe10` / `_audit-probe8`）**

```
scoring.json:  tickCap = 10   weights.tickMaxScore = 10   multiplier = 2
时距 10（字段封顶）→ 时距分 = min(log2(10)×2, 10) = 6.64
要拿满 10 分需要 时距 = 2^(10/2) = 32
→ 理论总分上限 = 50 + 40 + 6.64 = 96.64，而不是文档/测试声称的 100
```

而 `tests/engine/read.e.test.mjs` 的 E5：

```js
test('E5 满分构造：形态命中 + q_ratio=1 + 时距 32 → 恰为 100，不超 100', ...)
```

`时距=32` 在真实运行中**永远不可达**——`applyTick` 的 `cap` 就是 `scoring.tickCap = 10`。这条测试直接构造了一个不可能出现的输入来断言满分，属于「用构造出来的结果绕过真实链路」。

**其他实测**

| 现象 | 数字 |
|---|---|
| 时距分布 | 0=147、1=201、2=7、3=3（358 条） |
| 时距 ≥ 升格门槛（3） | **只有 3 条**（M-20261110-001/002、M-20261111-002） |
| 时距分 = 0 的生效条目 | 343 / 352（97.4%） |
| 靠时距才过 40 分及格线 | **0 / 117**（当前视角） |
| 时距改变返回顺序 | 抽样 99 个查询，**76 次（76.8%）** |
| 一次召回给几条 +1 | `topK=5` → 最多 5 条，而模型通常只用 1 条 |
| 浏览模式（标签留空） | **也会 +1**，实测返回 5 条全 +1 |
| 每次 +1 的代价 | **全量重写 330,878 字节**（tmp+rename），6.36 ms；按一天 50 次召回 ≈ 15.8 MB/天 |
| `createTickQueue`（注释说的「后台队列」） | **全仓只有定义，从未接线**；实际走同步全量重写 |
| 时距能否减少/衰减/重置 | **不能**，全仓无任何递减路径 |

**结论**

1. 时距分设计上限与字段封顶**数学上互斥**，导致「满分 100」是假的。当前真实可达上限 96.64。
2. 时距对**是否及格**几乎无影响（只能把 33.36 分以上拉到及格，实测 0 条受益），但对**排序**影响很大（76.8%）。所以它实际是个「排序扰动项」，不是「使用强度信号」。
3. 只增不减 + 无时间窗 + 浏览也加 + topK 放大 = **正反馈**：被翻到过的条目更容易再被翻到，而「被翻到」不代表「被用到」。
4. 每次召回全量重写库，成本随库线性涨。

**解决计划（不靠兜底，改逻辑）**

- **A-1 口径统一**：二选一，写进 `scoring.json` 注释与 README，并用测试锁死：
  - 方案 α（推荐）：`tickCap = 32`，使 `tickMaxScore=10` 可达；或
  - 方案 β：`tickMaxScore = 6.64` 并把「满分」表述改成「形态50+标签40+时距6.64」。
  - **改完必须删掉 E5 的 `时距=32` 构造**，改为「用 `applyTick` 把一条从 1 加到封顶，再用封顶值断言分数」，让测试走真实链路。
- **A-2 浏览不计时距**：`recall` 在 `browseMode=true` 时返回 `tickTargets: []`（语义：翻看不等于使用）。这条要同步改 `buildReadLog` 的 `hits` 记录方式，否则台账与库对不上。
- **A-3 只给「被采纳」的加**：时距 +1 的判据从「出现在 hits 里」改成「模型在后续动作里引用了该编号」——但这条依赖 feedback 通道（见 B-1），**不能先做**，否则又是靠猜。
- **A-4 接线 `createTickQueue`**：既然 `tick.mjs` 已经写好纯队列，宿主应当用它做**批量合并落盘**（一次召回只入队，进程空闲/下一轮 flush 一次），而不是每次召回同步全量重写。这能同时解决写入放大与并发竞态。
- **验收方式**：新增测试「从写入 → `recall` → `applyTick` → 落盘 → 再 `recall`」的完整链路，断言封顶值与分数上限一致；**禁止**在测试里直接构造 `时距=32`。

### 检查点 B：稳定性状态机——数据源是空的

**实测（`_audit-probe4` / `_audit-probe14` / `_audit-probe13`）**

```
read.jsonl 23 条记录，feedback 字段取值集合 = {"[]"}   ← 恒为空
foldFeedback 的实际逻辑：命中且无显式 feedback → 记 ok（"命中即视为被采纳"）
probe4 实测：一条从未被验证过的记忆，召回 4 次 →
  时距 = 5（初值1 + 4）
  foldFeedback.ok = 4
  → ok == 时距 - 1
  → 状态机判定：稳定（"时距 5（门槛 3）+ 连续 ok 4 次（阈值 3），无 wrong"）
```

**「连续 ok ≥ 3」和「时距 ≥ 3」是两个条件，但它们是同一个计数器。** 设计文档写「升格要同时满足用够久 + 反复没错」，实际上只满足了一个。

**稳定性在召回链路上零作用**

```
lib/engine/read.mjs:  '稳定性' 出现 0 行实际代码（只在注释里）
scoreRecord() 的三个分量：形态分 + 标签分 + 时距分 —— 没有稳定性
checkIsolation()：只判 项目/智能体/状态，不判稳定性
实测：同一条记忆改成 易变 / 观察 / 稳定，分数完全相同（93.17 / 93.17 / 93.17）
```

稳定性的唯一消费者：`merge` 的同编号冲突判定（`recordNewerThan` 的次级排序）、UI 列表展示、`getOverview` 统计。**升到「稳定」不会让它更容易被召回。**

**7 天里状态机的实际产出**

```
planTidy(dry-run) 在真实台账上的输出：changes = 2 条
  M-20261014-002 易变→观察（自愈）
  M-20261014-005 易变→观察（自愈）
→ 自动升格 0 次
tidy.jsonl 里 2 次「观察→稳定」全部是模型手动 dtm_retag 写的，不是状态机产的
```

**顺带查出的真缺陷：`near` 的编号解析**

```
buildReadLog (read.mjs):
  near: (r.near ?? []).map((n) => `${n['编号']} 分=${n.score} e_ratio=${n.e_ratio}`)
  → 存成 "M-20261110-005 分=50 e_ratio=0" 这种**字符串**

foldFeedback (tidy.mjs):
  const id = typeof n === 'string' ? n : n && n['编号'];
  → 整串当成编号

实测：foldFeedback 产出 63 个 key，其中 46 个是这种垃圾 key；
      69 条 near 反馈的 unused 全部落在垃圾 key 上，永远匹配不到任何条目。
```

测试 `K4` 用的是 `{ 编号: 'M-9', 分: 35 }` 对象形状，**与生产序列化形状不一致**——测试绿，生产路径坏。

**解决计划**

- **B-1 定稿 feedback 落盘形态**（这是根源，`内部文档/整理程序说明.md §6` 早已立项但没做）。推荐：`read.jsonl` 每行仍是「一次召回」，但新增**可选**字段 `feedback: [{id, verdict}]`，由模型在**下一次**召回或写入时回填「上次那几条有没有用上」。程序只负责记账，判读交给模型——符合插件「判据给模型、程序只校验」的一贯原则。
- **B-2 删掉「命中即 ok」这个隐含默认**：在 feedback 通道可用前，`nextStability` 应当**不产生升格变更**（返回 `null` 并给 reason「无反馈信号」），而不是拿时距冒充 ok。否则状态机永远在自证。
- **B-3 修 `near` 序列化**：`buildReadLog` 里 `near` 存对象 `{编号, score, e_ratio}`（与 `recall()` 的返回形状一致），`foldFeedback` 自然能解析。**同时把 K4 的用例改成走 `buildReadLog(recall(...))` 的真实形状**，而不是手搓对象。
- **B-4 让稳定性有召回层面的意义**（否则整个状态机白做）：二选一——
  - 降格生效：`稳定性=易变` 的条目在 `checkIsolation` 里**不进召回**（或排到 near 之外），这是「错了就别再喂给模型」；
  - 升格生效：`稳定性=稳定` 在分数上给一个小加权（例如 +3，明确写在 `scoring.json` 并纳入总分上限）。
  - 我倾向**只做降格**：降格有明确语义（判过错了），升格加权会与时距正反馈叠加，越滚越偏。
- **验收方式**：新增「一条新写入的记忆，在没有任何 feedback 的情况下，跑 10 轮 tidy 都不会变成稳定」的测试；以及「near 走真实 `buildReadLog` 后能被 `foldFeedback` 正确按编号累计」的测试。

### 检查点 C：一次性记忆——完全没有退场机制

这是你这次最直接的痛点。实测确认：**不是「退场机制没触发」，是根本没有这个机制。**

**证据 1：库里没有任何时间维度**

```
schema.columns = 编号, 主要内容, 形态, 项目, 智能体, 自由标签, 稳定性, 时距, 状态
含日期语义的列：无
唯一时间信息藏在编号 M-YYYYMMDD-NNN 里 —— 只有「创建日」，没有「最后召回日」「最后确认日」
```

**证据 2：没有任何自动退场判定**

```
index.js / tidy.mjs 里搜「未召回|闲置|超过 N 天|idle|stale|autoArchive」：0 命中
tidy.mjs 的 planTidy 产出里：没有「归档」类 change、没有「去重」类 change、没有「合并条目」类 change
archiveEntry 只能靠模型在对话里主动想起调 dtm_archive
```

**证据 3：7 天的实际行为**

```
写 195 条（write.jsonl，全部 ok=true）
退场 0 条（tidy.jsonl 里 archive 动作 0 次、supersede 0 次）
库：164 → 358 条（+118%）
现存 3 条「被取代」+ 2 条「已归档」全部是 2026-11-11 迁移/合并时带进来的状态
```

**证据 4：写入侧承诺的「去重是整理环节的事」没有落点**

```
schema.json writeRoutes.principles 原文：
  "**不查重、直接写**：去重是整理环节的事。"
但 tidy.mjs 的 planTidy 里没有任何去重能力。
→ 这句承诺指向一个不存在的功能。
```

**证据 5：机器可判定的「一次性候选」有 115 条**

用库内已有事实（创建日 + 台账 + 时距 + 状态），不靠正则猜内容：

| 规则 | 命中 |
|---|---|
| R1 = 生效 + 创建>3天 + 从未被召回 + 时距≤1 | 245 条（68.4%） |
| R2 = R1 且 稳定性=稳定（历史遗产，**不该自动动**） | 130 条 |
| **R3 = R1 且 稳定性∈{观察,易变}（本版写入后从未被用过）** | **115 条** |
| R4 = R3 且 内容含具体日期 | 36 条 |
| R5 = R4 且 内容含「未提交/未推送/待验证/已完成」 | 3 条 |

对照：如果按「时距=0 且 稳定」判（很多工具会这么写）会圈出 **131 条**，全是 2026-10 迁移进来的历史结论——删了就是丢历史。**这就是「没有时间维度」的代价：只能拿稳定性当代理，而代理会误伤。**

**解决计划（按插件自身逻辑，不靠事后清理脚本）**

- **C-1 加「时效」维度，但不要加 TTL 列**。理由：TTL 是猜的（谁知道这条该活 30 天还是 300 天）。推荐用**已有事实推导**：
  - 在 `schema.json` 增加 `lifecycle` 段（不是新列），定义三态：`常驻 / 观察中 / 待退场`，**由程序按规则推导，不落库**；
  - 推导输入：创建日（编号解析）+ 最后召回日（read.jsonl）+ 时距 + 稳定性 + 形态；
  - 规则本体写在 `scoring.json` 的可调参数里（`idleDays`、`minTickToStay` 等），整理时按《流程_整理》调参。
- **C-2 `planTidy` 增加第 6 类产出：`proposals` 里的 `retire`（只提议，不自动改）**。这符合现有纪律「拆库/升通用都只提议不自动执行」，也符合你「不能用兜底绕过」的要求——**程序负责圈出候选并给出依据，模型/用户负责最终判定**。
- **C-3 写入时就把「一次性」标出来**，而不是等整理时再猜。在 `dtm_write` 加一个**可选**参数 `时效`（`常驻 / 本会话 / 待验证`，默认常驻），落库进 `自由标签` 的固定类别词（如 `临时`）或新增第 10 列。**我倾向新增第 10 列**，因为标签是召回信号，掺进生命周期语义会污染 e_ratio 分母。
  - 关键：这个参数**必须由模型在写的时候判**，因为只有它知道「这条是这轮的进度还是长期结论」。程序判不了——正则分类必崩（这是插件一贯立场，`schema.json` 的 `_writeRoutes` 已写明）。
- **C-4 退场动作要有可逆性**：`dtm_archive` 已经是标状态不删行，够了。缺的是**批量提议 + 一键确认**的入口（UI 设置页已有整理按钮，扩一个「待退场候选」列表即可）。
- **C-5 修 `archiveEntry` 的可达性**：在 `dtm_recall` 的返回里，当某条命中但 `稳定性=易变` 或候选退场时，附一句提示。这是「让模型想起来」的唯一低成本手段。
- **验收方式**：造一个库，写 3 条带 `时效=本会话` 的记忆，把时钟推进 4 天，跑 `planTidy` 断言产出 3 条 `retire` 提议且**没有自动改库**；再断言 `稳定性=稳定` 的老条目**不出现**在提议里。

### 检查点 D：写入侧守门——校验与文档不一致

**实测（`_audit-probe7` / `_audit-probe8`）**

```
validateWriteInput(["3190","版本","测试"]) → ok:true，纯数字标签被放行
validateWriteInput(["坑"])               → ok:true，单字标签被放行
validateWriteInput([])                   → ok:false TAGS_EMPTY（这条拦住了）
```

但 `标签字典.md:226` 与 `free-tag-rules.json` 都明确写：

> **不打纯数字**（`3190` `0` `2`）、转述句、与内容无关的泛词

库内实际：**含纯数字标签 20 条**、**含单字标签 16 条**、**空标签 16 条**（空标签全部来自迁移，写入路径今天会拒）。

**写读比 8.4:1**

| 日期 | 写 | 读 |
|---|---|---|
| 11-10 | 5 | 3 |
| 11-11 | 21 | 13 |
| 11-12 | 77 | 3 |
| 11-13 | 66 | 4 |
| 11-14 | 16 | 0 |
| 11-15 | 6 | 0 |
| 11-16 | 3 | 0 |
| **合计** | **195** | **23** |

召回 23 次里有命中的只有 6 次（26%），5 次被 `QUERY_OFF_DIRECTION` 挡下。**11-14 之后零召回**——最近三天写的 25 条记忆一条都没被查过。

**解决计划**

- **D-1 校验对齐文档**：`validateWriteInput` 增加「纯数字标签」与「单字标签」的拒绝（用 `vocab.mjs` 已有的 `isUsefulTag` 判据，那里已经实现了完整规则，**不要再写第二份**）。
  - 注意：`isUsefulTag` 的 `minLen=2` 会误伤英文短词（`ai`、`ui`、`os`）。规则应当是「单字中文拒、单字拉丁字母看长度≥2 才收」。
- **D-2 库内历史数据不自动清洗**：20+16 条噪声标签只做 `proposals` 提议，由模型整理时逐条判。**绝不能写个脚本批量删**——那正是「用兜底绕过」。
- **D-3 召回率要有反馈**：写读比 8.4:1 说明「写得多、用得少」。当某一形态的召回成功率长期低于阈值时，`planTidy` 应当提议「这一形态的标签打得太散/太密」，而不是继续闷头写。这需要 `read.jsonl` 的 `cond` 与 `passed` 已有数据（已有，可直接算）。

### 检查点 E：归属隔离与项目名漂移

**实测（`_audit-probe7` / `_audit-probe6`）**

```
当前视角（项目=dsh-tag-memory，身份=萧潇）可见 117 / 358 条 = 32.8%
项目名漂移：
  privhub-1 (67 条)  vs  PrivHub (10 条)   ← 同一项目两种写法
  AI_treaning (69) / dsh-tag-memory (41) / .dsh (22)  ← 疑似同一项目的三种写法
后果：在 privhub-1 目录里工作时，项目=PrivHub 的 10 条记忆**完全看不见**（硬筛不过）
智能体名漂移：萧潇 327 / ClaudeCode@dsh-SQL 15 / 通用 11 / 星彩 3 / 无暇 2
```

`项目` 由程序按工作目录 basename 自动填（`projectOfSync`）。问题是**工作目录改名/换盘符/换克隆位置，历史记忆就整片失联**——而且没有任何提示。

**解决计划**

- **E-1 项目别名表**：`schema.json` 增加 `projectAliases`（`{ "PrivHub": "privhub-1" }`），`checkIsolation` 与 `selectVisible` 在比较前先归一。
  - 这是**配置**，不是硬编码；用户可改。归一是确定性逻辑，不是兜底。
- **E-2 可见比例告警**：`getOverview` 已能算总条数，加一个「当前视角可见 / 全库」比例。低于 50% 时在设置页提示「你的库有 68% 对当前项目不可见，可能是项目名漂移」。
- **E-3 别名不能自动猜**：`PrivHub` → `privhub-1` 是模型判的，程序只提供「疑似同一项目」的候选（按标签重合度）。这条走 `proposals`，不自动改。

### 检查点 F：注入体积

**实测**

```
标签网络（当前视角 117 条可见）：5539 字节 ≈ 1846 tokens
section A：3776 字节；10 个工具定义 C：7021 字节；A+C = 10797 字节
按当前增长速度（7 天 +194 条）：30 天后 ≈ 1023 条 → 网络约 16000 tokens
```

`free-tag-rules.json` 的 `_boundary` 明确写「全量不截断（约 1400 tokens，用户裁定）」。这个裁定在 117 条时成立，在 1000 条时不成立。

**解决计划**

- **F-1 退场机制落地后，网络自然只渲染「常驻」条目**——这是 C 检查点的直接收益，不需要额外做截断。
- **F-2 加体积上限作为**硬约束而非**兜底**：`renderTagNetwork` 的 `maxLines` 参数已存在但传的是 0（不限）。改成按 token 预算动态算，**超出时按「常驻优先、观察中次之、待退场最后」排序截断**，并在工具描述里明说「已按预算截断 N 条」。
  - 这不算兜底：截断是**有确定语义的**（生命周期优先级），不是「读不到就算了」。

## 二、改进计划（按依赖顺序，不按严重度）

依赖关系很重要：**B 不修，A-3 就是空话；C 不修，F 必然爆**。

```
第一批（互相独立，可并行）
├─ A-1 口径统一 + E5 测试改走真实链路
├─ B-3 修 near 序列化 + K4 测试改真实形状
├─ D-1 校验对齐文档（复用 isUsefulTag）
└─ E-1 项目别名表

第二批（依赖第一批）
├─ B-1 feedback 落盘形态定稿        ← 需要你拍板落盘形态
├─ B-2 删掉「命中即 ok」隐含默认     ← 依赖 B-1
├─ B-4 稳定性接入召回（建议只做降格）
└─ A-2 浏览不计时距

第三批（依赖第二批）
├─ C-1 生命周期推导（不落库）
├─ C-2 planTidy 产出 retire 提议
├─ C-3 dtm_write 增加「时效」参数    ← 需要你拍板：新列 or 复用标签
└─ A-4 接线 createTickQueue

第四批（依赖第三批）
├─ F-2 网络按预算截断（有语义的截断）
├─ D-3 召回率反馈
└─ E-2 可见比例告警
```

**需要你先拍板的 3 件事**

1. **`时距` 与 `时距分` 的口径**：抬高 `tickCap` 到 32（让满分可达），还是把满分改成 96.64（承认设计上限）？我倾向后者——32 次召回才拿满 10 分，实际库里最高才 3，抬高 cap 只是让理论上限好看，不改变真实分布。
2. **`feedback` 落盘形态**：推荐「模型在后续调用里回填上次召回的采纳情况」。这需要 `dtm_recall` 的返回带一个「上次查询的回执编号」，让模型有东西可回填。要不要做这个协议？
3. **「一次性」标记放哪**：新增第 10 列（语义清晰、不污染召回），还是复用 `自由标签` 加一个 `临时` 类别词（零结构变更，但会进 e_ratio 分母）？我倾向新列。

## 四、一句话给你

你说的两件事都成立，而且是同一件事的两面：

- **「一次性记忆不该跨会话」**——库里没有时间维度、没有退场机制，7 天写 195 条退场 0 条，只能靠模型自觉。有 115 条机器可判定的候选在等你处置。
- **「时距功能没起作用」**——它确实在跑（每次命中 +1、封顶 10、影响 76.8% 的排序），但它的两个设计目标都没达成：**打分上限不可达**（6.64 ≠ 10），**升格门槛被同一个计数器自证**（ok ≡ 时距-1）。它不是没跑，是跑在一条自己给自己打分的闭环上。

最该先动的不是加功能，是**把 B（feedback 通道）和 C（生命周期）这两块地基补上**——否则 A 和 F 无论怎么调，都是在没有信号的情况下调参。

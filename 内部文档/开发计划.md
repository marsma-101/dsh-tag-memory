# 开发计划（dsh-tag-memory）

> 依据是本仓库内 7 份已锁定的说明文件。凡说明里写「开发期做」的项，统一归入「阶段 0 探明」与对应实现阶段，不在此处重复争论设计。
> 优先级：先把"读写记录闭环 + JSONL 持久化"跑通（最小可用），再补整理与稳定性，最后做工具链与客户端 UI。

## 阶段 0 — 探明阻塞点

> **问题 1/2/3 已由官方文档解答**（见 `待查证问题.md` 的结论段）。这里只剩需要动手核实的实现细节。

- [ ] **0.1 客户端↔宿主通道**：用 `cordis_inspect_query` 查实 Client-callable Host 入口（如 `ctx.remote.commands.execute()`）的确切注册方式与参数；同理查实 storage service 与 `ctx.sessionProjections` 的用法。**不再自建 `/tag-memory-api`**。
- [ ] **0.2 客户端模块形态**：按 `templates/decoration/client.js` 的 `window.__ModuleLoader__.load({ id, factory })` 形态验证多文件 `client.<name>.js` 的加载与相互引用。
- [ ] **0.3 插件安装与清单**：用 `install_bundle` 路径；定 `package.json`（`dsh.bundle.patch` / `dsh.client` / `exports` / `files` 白名单）、`locale/*.json`（`meta.title`/`meta.description`）、`icon.svg`。
- [ ] **0.4 JSONL 读写**：确认宿主侧有无现成 JSON 读写；在 `core.mjs` 把序列化/反序列化抽一层（便于日后换格式或回退 CSV）。
- 产出：一份「探明结论」补进 `待查证问题.md` 或本文件。任一阻塞需立刻回报告主。

## 阶段 1 — 骨架与数据层（宿主入口 + 存储）
- [ ] **1.1 插件骨架三入口**：`index.js`（宿主入口：存储 + 宿主方法 + 定时任务）、预设声明（工具注册 + 提示注入）、`client.js`（客户端入口 UI）。
- [ ] **1.2 数据目录**：`store/memory.jsonl`（9 字段：编号,主要内容,形态,项目,智能体,自由标签[],稳定性,时距,状态）+ `records/{write,read,tidy}.jsonl`。
- [ ] **1.3 序列化层**：JSONL 读/写/追加/原位替换；空库校验；`records/*.jsonl` 同约定。
- [ ] **1.4 隔离维度**：项目 / 智能体作为每条记忆的隔离键，写入时必须有（用户手动改也有约束）。
- [ ] **1.5 一个操作两个调用者**：把手动改条目等操作实现成宿主方法，UI 与工具共调同一方法。

## 阶段 2 — 写入链路（dtm_write / dtm_bind / dtm_recall）
- [ ] **2.1 dtm_bind**：绑定当前会话身份（项目/智能体）。未绑定 → **写入拒写、读取返回空**（绝对规则）。
- [ ] **2.2 dtm_write**：落 `store/memory.jsonl` + 写 `records/write.jsonl`（不查重、不做取代/归档，仅追加）。
- [ ] **2.3 dtm_recall**：按评分召回（形态50 + 标签交集0~40 + 时距0~10，及格线40）；命中否决 `entry e_ratio>0.5`、`query q_ratio≥QUERY_FLOOR`；写 `records/read.jsonl` 含 `feedback{id,verdict}`。
- [ ] **2.4 首次使用引导**：缺参数时按 §4.3 进设置引导，不再"程序提示已有同一件事"。

## 阶段 3 — 整理链路（对话内，模型参与）
- [ ] **3.1 触发**：对话内模型触发整理；整理身份来源 = 当前绑定 → 设置页"整理智能体" → 都没有则提问。
- [ ] **3.2 去重 / 升通用**：跨身份合并同类记忆；升通用强判定（≥4 不同智能体/项目 + 语义相似>80% 且重点一致）。
- [ ] **3.3 稳定性状态机**：据 `records/read.jsonl` 的 `feedback` 驱动（观察/稳定/易变）；**同轮频繁错召（召回但与需求不符）触发一次整理**去调整，不由读写环节改。`feedback` 的具体落盘形态是占位参数，待"整理与记录"专项设计定稿。
- [ ] **3.4 归纳 / 拆库拆表**：独立场合可操作化；触发（条目数超阈值 / 时距超阈值 / 自由标签重复度过高）→ 拆。
- [ ] **3.5 写 `records/tidy.jsonl`**：动作含 `merge / feedback / user_edit`，`user_edit` 必须带项目/智能体。

## 阶段 4 — 维护工具链（dtm_supersede / dtm_archive / dtm_review / dtm_retag / dtm_export / dtm_records / dtm_merge）
- [ ] **4.1 单条维护**：覆盖(supersede)/归档(archive)/回顾(review)/改标签(retag)/导出(export)/查记录(records)。
- [ ] **4.2 dtm_merge**：手动合并条目（对应 §2.1 merge 动作），结果回写 `memory.jsonl` 并记 tidy。
- [ ] **4.3 用户手动改**：提供改项目/智能体的入口（强约束：必须有）。

- [ ] **5.2 记忆浏览/编辑面板**：渲染记忆、feedback 标记、手动改项目/智能体（调宿主同一方法）。

## 风险与回退
- **JSONL 是测试性选型**：阶段 0.4 / 1.3 若暴露体积或迁移痛点，立即回报告主，可加序列化抽象层或回退 CSV（架构已为切换留了抽层位）。
- **未绑定铁律** 贯穿所有阶段，任何链路不得为"传通用/跨身份"放行短路。
- **稳定性** 必须由整理环节执行（程序改值、模型判断）；写入与读取一律不碰。同轮频繁错召 → 触发一次整理处理。
- **不自建通道**：客户端↔宿主一律走官方 Remote/命令入口与 storage service；发现要走偏门时先回报，不自作主张。

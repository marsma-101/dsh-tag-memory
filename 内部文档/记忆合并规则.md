# 记忆合并规则（§4.3）

> 日期：2026-11-11
> 来源：`内部文档/改进与迭代方向-2026-11-11.md` §4.3
> 区分：现有《已有库检测与处置规则.md》管的是「装完发现已有库怎么办」（格式/多库/问人）；
> **本文件管的是「用户主动合并一份外来库时，字段口径怎么归一」**——这是原先的空白。
> 本文件在 `内部文档/` 下，不进发布包。

---

## 0. 实证基线（为什么必须立规则）

11-10 那次 merge 的 `tidy.jsonl`：`added=154, changed=0, conflicts=0`。
`index.js` 的 `mergeLibrary` 原先只做 4 件事：源存在校验、表头校验、
按编号去重（同号保留较新）、整体写回 + 备份 + 记台账。
**不校验、不归一任何字段取值**：旧库的 `项目`/`智能体`/`稳定性`/`时距`/
空标签全部原样落地，于是 7 个项目名、4 个身份名、9 条空标签、纯数字标签一起进了库。

---

## 1. 六维口径裁定

| 维度 | 规则 | 理由 |
|---|---|---|
| `项目` / `智能体` | **外来库归属未知时统一标 `引入`（不是 `通用`）**。是否批量映射到当前项目/身份由用户在合并弹窗里选，**程序不自动猜** | `通用` 是白名单，填错会污染所有项目/身份的召回；`引入` 如实记录「归属未知」，读取时同样可见但语义不同 |
| `稳定性` | **原样保留**。旧库已验证的 `稳定` 视为有效，不重置、不参与本版状态机首次升格 | 见《整理程序说明》§2（历史遗产，不是缺陷） |
| `时距` | **原样保留，从 0 起算，不伪造使用次数** | 时距是「本版被召回次数」的程序计数器，合并不是使用 |
| `自由标签` | **空标签条目要么补最小标签、要么标 `待整理`，且在 dryRun 里报出来，不静默入库** | 空标签 + 非空 query → `e_ratio=0` → 除浏览外永远召不回（废条）；写入侧有 `TAGS_EMPTY`，合并绕过了它 |
| 重复 / 同义条目 | **只按编号判重**（程序侧）。编号不同但内容重复的，留给整理环节按相似度归并，dryRun 里给「疑似重复 N 组」提示 | 程序不自己算语义相似度，那是模型/整理环节的活 |
| 冲突 | 同号按 **时距 > 稳定性 > 保留当前库**（幂等）。`conflicts` 计数要在预演/UI 里可见 | 规则本身合理，成文即可；已由 `recordNewerThan()` 实现 |

> **硬边界**：以上归一**只产出「体检报告」，不自动改库**。
> 合并是「用户主动导入」，改字段属于整理动作，必须有依据（见 `validateTidyPatch`）。
> 程序负责说清楚，用户负责决定（沿用《已有库检测与处置规则.md》的总原则）。

## 2. dryRun 字段口径体检（落点）

`mergeLibrary({ dryRun: true })` 的返回值新增 `fieldAudit` 小节，由
`lib/engine/diagnose.mjs` 的纯只读函数 `inspectMergeFields(records, schema)` 产出：

```
fieldAudit: {
  scanned: 154,                 // 体检了多少条（incoming.records）
  distinctProjects: 7,          // 不同项目名数量
  distinctAgents: 4,            // 不同身份名数量
  blanks: { 项目: 0, 智能体: 0, 自由标签: 9 },
  stability: { 观察: 15, 稳定: 136, 易变: 3 },
  tick: { zeros: 154, min: 0, max: 0 },   // 合并进来的从 0 起算
  noiseTags: { numeric: 12, sourceMark: 30 },  // 纯数字 / 来源标记
  emptyTagIds: ['M-...'],      // 空标签条目编号（最多列 10 条）
  suspiciousDuplicateGroups: 2, // 编号不同但 主要内容 完全相同的组数
  suggestions: [ ... ]          // 人读建议（不自动执行）
}
```

- `conflicts` / `changed` / `added` 原有字段保持不变，继续在预演里可见。
- 体检只在 **dryRun** 时算（正式合并也顺带返回一份，便于台账留痕），
  **绝不因体检结果拦下合并**——合并成功与「字段是否整洁」是两件事。
- 疑似重复只报组数，不列具体内容判断（程序不判语义）。

---

## 3. UI 落点

`client.js` 合并弹窗的预演结果里，把 `fieldAudit` 显示成一小节：
项目名/身份名种类数、空标签条数、噪声标签数、疑似重复组数、以及 `suggestions`。
正式合并成功后也显示一份（来自 `mergeLibrary` 的返回值），让用户知道带进来什么。

---

## 4. 与整理审查的关系（见《整理程序说明》§7）

合并带入的历史口径会在整理阶段被误判成「脏数据」。
审查时先区分「合并带入的历史口径」与「本版写入产生的问题」：
前者按《整理程序说明》§2/§3 的基线处置（老稳定是遗产、刚装未整理属正常），
**不要当脏数据清洗**，也不要因为 `时距=0` 就把 `稳定` 退回 `观察`。

---

## 5. 验收

- `mergeLibrary({dryRun:true})` 返回 `fieldAudit` 且字段齐全；
- 体检函数纯只读、不写文件、可脱离框架单测（`tests/gate3/merge-field-audit.test.mjs`）；
- 不自动改任何字段，`added/changed/conflicts` 语义不变；
- `conflicts` 在预演里可见；
- 空标签 / 噪声标签 / 疑似重复都在 `suggestions` 里被点名。

# 架构说明

> 重写 dsh-tag-memory 前必读。本文描述**架构事实与设计约束**。
> 功能需求见《功能说明》。四份流程文档是细节补充（v1.0.0）。

---

## 一、这是什么

DSH（DeepSeek Harness）的一个插件：给智能体一套**标签化的长期记忆**。

- **写入**：只追加，不改旧行（模型给自由标签，程序不生成）
- **读取**：按标签硬筛 + 形态/标签交集召回，宁可返空也不硬凑
- **整理**：对话内（也可定时批量）归并、改标签、归档/取代、维护标签等价表与打分参数、**稳定性状态机**、**feedback 反推**。整理是唯一能改动已有行的环节
  > 定时批量触发时没有对话可问，整理身份按《流程_整理》引言的三级兜底取（当前绑定 → 设置页"整理智能体" → 提问）。

---

## 二、插件结构与三个入口

**一个插件，一份引擎，三个入口。** 三者跑在不同环境，但共享 `lib/engine/` 同一份纯逻辑：

| 入口 | 实现 | 运行位置 | 职责 |
|---|---|---|---|
| **宿主入口** | `index.js`（Host plugin） | Node 进程 | 文件读写、数据存储、定时任务、给 UI 和工具提供同一套操作 |
| **预设入口** | 预设 YAML + 插件注册 | Node 进程（Agent 预设） | 工具注册（`ctx.tools.register`）、系统提示注入（`ctx.systemPrompt.section`） |
| **客户端入口** | `client.js`（Client module） | **浏览器** | 界面渲染（slot 里的 React 组件） |

三者的连接方式（**按官方机制，不是自建通道**）：

1. **预设 ↔ 引擎**：预设注册的工具**按操作性质分两类**走：
   - **纯读写类**（`dtm_write` / `dtm_recall` / `dtm_review` / `dtm_records`）→ **直调 `lib/engine/*`**
   - **改库类**（`dtm_supersede` / `dtm_archive` / `dtm_retag` / `dtm_export` / `dtm_merge`）
     → **走宿主方法**，因为这类要「备份 + 加锁 + 改行 + 记台账」四件事，
     且 **UI 有同款按钮必须共用实现**（见下条）
2. **客户端 ↔ 宿主**：客户端通过宿主暴露的 **Remote / 命令入口**调用宿主方法，**不自建 HTTP 前缀、不自做鉴权**（详见第五节）
3. **客户端 ↔ 预设**：没有直连。UI 的操作与工具调用落到**同一个宿主方法**上（见 `references/user-actions.md` 的"一个操作、两个调用者"）

> **为什么不是"预设全部直调引擎"**：若 `dtm_retag` 直调引擎、UI 改条目走宿主方法，
> 就会长出**两套改库逻辑**，行为必然分叉。所以凡是 UI 也要做的操作，统一收口到宿主方法。
> 这条优先于"预设直调引擎"的一般原则。

**客户端代码跑在浏览器里**，没有 `node:fs`、`node:path` 等模块。所有文件操作必须在宿主入口完成。

> **术语对齐**：官方叫 Host plugin / Client module / Agent preset。本文用"宿主入口 / 客户端入口 / 预设入口"指同一件事。

## 三、依赖策略：按阶段区分

| 阶段 | 策略 |
|---|---|
| **安装时** | 可以正常声明 `dependencies` / `devDependencies`，npm / pnpm 会装 |
| **构建时** | 可以引入构建工具（esbuild / rollup 等）作为 devDependency |
| **运行时** | 尽量精简，只留必需的；能复用 DSH 已有的就用它的 |

### 3.1 可以依赖什么

- `@deepseek-ai/dsh-*` 系列包：**优先复用**，DSH 里已经有了
- `react`：客户端从浏览器模块表取，不用自己装
- 通用的工具库（如 zod / dayjs）：**能用标准 API 手写就手写**，真的合适才引

### 3.2 `dsh.client.external`

客户端如果用了非基线模块，要在 `dsh.client.external` 里声明，这样不会被重复打包（见 cordis 组合语法）。

## 四、文件结构

### 4.1 宿主入口（Node 侧，可正常多文件 + import）

```
index.js                    ← 宿主入口（Host plugin）：存储、定时任务、生命周期、给 UI 与工具共用的宿主方法
cordis.patch.yml            ← bundle 补丁：插入本插件的 plugin 行
preset/                     ← 预设入口：Agent 预设声明（YAML 里列出要装进 agent 的子插件）
└─ tools.js                 ← 工具注册（ctx.tools.register + defineTool，dtm_*）+ 系统提示注入
lib/engine/                 ← 纯逻辑，不碰 Cordis，可脱离框架单测
├─ core.mjs                 ← schema、路径解析、CSV 读写（RFC4180）、文件锁、编号
├─ write.mjs                ← 写入校验与落盘（收模型 5 标签）
├─ read.mjs                 ← 召回打分（硬筛 / 命中否决 / 及格线 / 标签交集）
├─ tick.mjs                 ← 时距后台累加（队列，不阻塞）
├─ tidy.mjs                 ← 整理
├─ backup.mjs               ← 备份 / 恢复 / 合并
├─ schedule.mjs             ← 定时任务调度
├─ migrate.mjs              ← 数据目录搬家
├─ dict.mjs                 ← 字典加载（注入精简版标签字典）
└─ templates/               ← 程序侧配置（不注入模型）
   ├─ tag-equivalence.json   ← 标签等价表（发版≈上线≈deploy，双向归一）
   └─ scoring.json           ← 打分权重、及格线、命中否决阈值（默认值；可调项另在 Config 暴露）
```

**分工原则**：
- `lib/engine/*` 不知道 Cordis 存在——只接参数、返回结果，能脱离框架测试。**三个入口共享这一份**。
- `index.js` 负责 Cordis `ctx` 与引擎之间的转换，并提供 **UI 与工具共用的宿主方法**
- 预设入口负责工具定义与提示注入，实际执行调引擎（不重复实现业务逻辑）
- **大篇幅细节（阈值推导、匹配原理）只放 `lib/engine/templates/` 与流程文档，每轮注入的字典保持精简**

### 4.2 客户端入口（浏览器侧）

DSH 支持客户端多文件：**`client.js` 作入口，其余用 `client.<名字>.js` 命名**。

**推荐结构**（按功能拆分，每个文件职责单一）：

```
client.js                   ← 入口：模块装配、槽位注册、样式注入
client.api.js               ← 宿主调用封装（所有对宿主方法的调用集中在这，不是 HTTP）
client.pages.entries.js     ← 页面：记忆条目
client.pages.settings.js    ← 页面：设置
client.parts.js             ← 通用小组件（错误框、对话框、统计条）
client.styles.js            ← CSS 字符串
```

**拆分原则**：一个页面一个文件；**对宿主的所有调用集中 `client.api.js`**（内部走 Client-callable 入口，见第五节，不自建 HTTP）；通用件放 `client.parts.js`；每个文件开头写一行注释。

> 具体用多文件还是构建成单文件，看构建链的选择。两种都能跑，关键是页面级隔离。

## 五、客户端与宿主怎么通信

**不自建 HTTP 前缀，不自做鉴权。** 这是官方明确要求的（`references/user-actions.md`、`references/practices.md`）：

> 官方原文："The UI action calls it through a Client-callable Host entry point found with inspection,
> such as a session command that `ctx.remote.commands.execute()` runs."
> 以及："keep plugin-owned data in a storage service found through inspection."

### 5.1 正确的三层关系

```
UI 操作  ─┐
          ├─→  同一个宿主方法（Host service method）  ─→  lib/engine/*
工具调用  ─┘
```

- **一个操作只实现一次**：写在宿主的方法里，返回结果或明确的失败原因。
- **UI 通过 Client-callable 入口调它**（`ctx.remote.commands.execute()` 一类，具体入口用 `cordis_inspect_query` 查实后再定）。
- **工具调同一个方法**，参数和语义保持一致。
- **权威性操作（授权、确认、放宽策略）只给用户**，不开放给工具。

> 这正好满足《功能说明》要求：用户手动改 `项目`/`智能体` 与 `dtm_retag` **共用同一实现**，
> 不会出现两套逻辑打架。

### 5.2 数据怎么到客户端

- 插件自有数据放 **storage service**（用 inspection 查到的现成服务），不要自己造 HTTP 端点。
- 需要从会话派生的值 → 在宿主投影上声明 **`wire.view`**，值算好了再送到客户端；**客户端不自己折叠会话事件**。
- 插件 UI 是 **slot 里的 React 组件**，**不许**用 iframe 加载宿主返回的 HTML（iframe 拿不到主题、明暗切换、locale）。

### 5.3 端点命名

**不再有 `/tag-memory-api` 这套自建端点。** 需要对外暴露的操作，按上述"宿主方法 + Client-callable 入口"组织；
具体方法名与入口在前端设计阶段定稿，本文不预设不存在的端点。

> 之前那套"自定义前缀 + `connection.requestRejection` + fail closed 503"的方案**已废弃**——
> 那是绕开框架自建通道，官方文档里没有依据。见《待查证问题.md》问题 1 的结论。

## 六、数据目录与优先级

路径按这个优先级决定（**5 级**，2026-11-06 起）：

```
① config.dataDir（profile 补丁里写死的）      → source: 'config'   （锁定）
② 环境变量 DSH_TAG_MEMORY_DATA_DIR           → source: 'env'      （锁定）
③ 设置页选的（存在 <插件包>/config/data-dir.json） → source: 'settings'
④ $DSH_HOME/tag-memory                       → source: 'dsh-home'  ← 出厂默认
⑤ <插件包>/data                              → source: 'package'   ← 最后手段，会告警
```

**出厂默认从 ④ 挪到 ⑤ 是 2026-11-06 的修正。** 原先是 `<插件包>/data`，但：

- pnpm 重装 / 升级会连包目录一起删 → **用户数据丢失**（P0-3）
- 写死绝对路径在 bundle 补丁里，跨平台会静默指向不存在的路径

改后的 ④ 是用户级目录，跨平台自然对齐，不需要在包里写死任何路径：

| 环境 | `$DSH_HOME` | 默认数据目录 |
|---|---|---|
| Docker 容器 | `/opt/dsh` | `/opt/dsh/tag-memory` |
| Windows | `C:\Users\<你>\.dsh` | `C:\Users\<你>\.dsh\tag-memory` |

`$DSH_HOME` 解析规则与官方 `@deepseek-ai/dsh-home-paths` 一致：
环境变量优先，空/纯空白视为未设置，否则回落 `~/.dsh`。
**engine 不读 `process.env`**（纯度约束），由宿主解析好后作为 `dshHomeDir` 传入。

**⑤ 落包内时必须告警**：启动日志 warn + `getSettings().warning` 非 null。
不许静默 —— 静默的后果就是数据在升级时无声消失。

**①② 优先级高于设置页**——这种情况下搬家不生效。界面上要**直接说明改哪一行**。
（说明里的 id 必须等于 bundle 补丁 insert 的 id，见《安装说明》§二。）

数据目录结构：

```
<dataDir>/
├─ store/memory.csv      ← 记忆库本体（9 列 CSV；格式见本节末尾与第八节）
├─ records/              ← write/read/tidy 的 jsonl 台账（纯机器读，人不用改；见各流程文档）
├─ backup/               ← 备份
└─ settings.json         ← 设置
```

> **记忆库本体已定为 CSV**（见《待查证问题.md》问题 4），**台账 `records/*.jsonl` 仍用 JSONL**。
> 分工理由：
> - **库本体要给人看、给人改** → CSV（表格形态，插件 UI 里直接以表格呈现、可编辑）
> - **台账只给程序和模型排查用，从不需要人改** → JSONL（一行一条对象，天然适合追加与嵌套字段）
>
> `store/memory.csv` 9 列顺序固定：`编号,主要内容,形态,项目,智能体,自由标签,稳定性,时距,状态`。
> `自由标签` 列内用 **`|`** 分隔多个标签。
> `core.mjs` 应把序列化/反序列化单独抽一层（CSV 读写 + 标签拆分/合并），便于后期拆库拆表时换存储。

## 七、客户端多文件的机制（源码依据）

DSH 允许包内提供 `client.<name>.js` 形式的 chunk：

```js
// dsh-client-modules/lib/index.js
const CLIENT_CHUNK = /^client\.[A-Za-z0-9][A-Za-z0-9._-]*\.js$/

chunkResponse(requestUrl) {
  // 按请求 URL 找到包内对应文件，读出来当脚本返回
}
```

**注意**：这些 chunk 是**独立脚本**，不是 ES module。chunk 之间要靠 `window.__ModuleLoader__.load({ id, factory })` 注册，或用构建工具打包成单文件。
`exports["./client"]` 只能是一个字符串（入口文件），不能是数组。多入口靠在入口里动态注册，或靠构建。

## 八、记忆库 schema（v1.0.0：9 列，CSV）

**存为 `store/memory.csv`：一行一条记忆，9 列，列顺序固定。**

```csv
编号,主要内容,形态,项目,智能体,自由标签,稳定性,时距,状态
M-20261105-001,"部署时先跑 build 再跑 test, 否则旧产物会被打进包",技能,用户设置,通用,发版检查|需先build|部署,观察,3,生效
```

> **双标签体系**（v1.0.0 核心，详见《功能说明》§三）：
> **固定标签** = `形态` / `项目` / `智能体`（取值受限，硬筛 + 强加权）；
> **自由标签** = `自由标签`（模型自由给，召回主匹配信号）。

| 列 | 谁填 | 说明 |
|---|---|---|
| `编号` | 程序 | `M-YYYYMMDD-NNN`，日期 + 当天序号 |
| `主要内容` | 模型 | 要记的那件事，**不设字数上限**，一条一事。**可含逗号/换行/引号，按 RFC4180 用引号包裹** |
| `形态` | 模型 | 6 选 1：技能 / 流程 / 规则 / 偏好 / 事实 / 模板 |
| `项目` | 模型 | 属于哪个项目；`通用` = 所有项目可见；`引入` = 外部来的、归属未知 |
| `智能体` | 模型 | 属于哪个身份；`通用` / `引入` 同上 |
| `自由标签` | 模型 | 召回主信号，**≤ 20 个**，列内用 **`|`** 分隔 |
| `稳定性` | 程序 | `观察`(初值) / `稳定` / `易变`，由召回反馈驱动演进 |
| `时距` | 程序 | 存入 1，每召回 +1 |
| `状态` | 程序 | `生效` / `被取代` / `已归档` |

### 8.1 CSV 读写的硬规则

1. **RFC4180 转义**：字段含 `,` `"` 或换行时，整个字段用 `"` 包裹；字段内的 `"` 写成 `""`。
   **不许用简单 `split(',')` 解析**——正文里的逗号会直接把行拆错。
2. **`自由标签` 列内用 `|` 分隔**：`发版检查|需先build|部署` → `split('|')` 得到数组。
3. **`|` 是保留分隔符**：标签内容**不得包含 `|`**。写入时校验，含则**拒写**并报错告诉模型"哪个标签含非法字符"。
4. **表头必须存在**：第一行是列名，程序按列名定位（列序变了也能读）。
5. **数值列**：`时距` 存整数。

> **为什么要这些规则**（实测依据）：不加引号时，正文里一个 ASCII 逗号会让 9 列变成 10 列；
> 加了引号后，简单 `split(',')` 依然错——**必须实现标准解析器**。标签含 `|` 会串位（3 个标签读回 4 个）。
> 详见《待查证问题.md》问题 4 的实测数据。

### 8.2 标签比对为什么不受 CSV 影响

`自由标签` 在内存里**始终是字符串数组**：读时 `split('|')`，写时 `join('|')`。
命中否决、`e_ratio`、`q_ratio`、标签交集全部**在数组上运算**，与文件格式无关。

| 层 | 操作 | 复杂度 |
|---|---|---|
| 写 | `数组.join('|')` | 1 行 |
| 读 | `格内.split('|')` | 1 行 |
| 比对 | 数组求交集、算占比 | 与格式无关 |

> 关于"自由标签用 CSV 会很麻烦"的说法：**麻烦只在序列化那两行，比对完全不受影响。**

> **字段分工速记**：模型填 5 个（`主要内容`/`形态`/`项目`/`智能体`/`自由标签`），
> 程序填 4 个（`编号`/`稳定性`/`时距`/`状态`）。这 4 个各有自己的取值域——
> `稳定性` 三态、`状态` 三态、`时距` 为计数、`编号` 为唯一 ID；
> 不要把它们笼统说成"四个状态"，它们是**四个由程序负责的字段**。

**写入路径只追加**：不改旧行。改旧条用「取代」（新行 + 旧行标 `被取代`）。
整理路径可以改标签和状态列。

## 九、隔离规则

读取时**两道硬筛，与关系**：

```
条目的 项目 ∈ {通用, 引入, 当前项目}
AND
条目的 智能体 ∈ {通用, 引入, 当前智能体}
AND 状态 = 生效
```

- `通用` = 真的对所有项目 / 身份可见
- `引入` = 外部同步来的、归属未知（可见性同通用，但语义不同，整理时能找出来归位）
- 其他值 = 精确字符串匹配，不做模糊

**这条规则由程序强制执行。** 它不能靠提示词劝导——本会话看不见的条目，模型本就不该知道它存在。

## 十、会话身份

写记忆要标「属于哪个智能体」，所以模型每轮必须知道「本次会话我是谁」。

机制（**存取方式按官方机制，规则不变**）：
- **per-session 状态放 `ctx.sessionProjections`**：写一个投影单元，`apply(state, event)` 纯同步推导；
  绑定动作产生的事件进日志，投影据此算出"当前身份"。**不要自己订阅 `session/event` 重扫 `session.events`**。
- 每轮注入的系统提示里带一段「当前身份状态」（未绑定 / 已绑定 / 拿不到会话）
- 提供 `dtm_bind` 工具让模型绑定身份；用户问「都有什么身份」时，宿主提供「列出已有身份」的能力支撑
- **未绑定时写入拒、读取空**——不知道「我是谁」就不知道该读/写谁的记忆

> **为什么这样更好**：官方原则是"The session log is the only source of truth"（`practices.md:7`）——
> 模型看到的东西必须能从已提交的会话事件重建，插件内存只是派生缓存。
> 走投影后，fork / resume / replay 都能正确恢复身份状态；纯内存映射在 resume 时会丢。

会话身份的**语义**仍是有意不落长期库：用户要的是「报出名字就能读回」，不是「永久记住」。

## 十一、召回逻辑（替代旧 2-gram）

读取打分（百分制）：

```
形态命中      50 分
标签交集      0~40 分（按 query 命中占比线性，详见《流程_读取》）
时距微加权    0~10 分（min(log2(时距)×2, 10)）
```

**三道闸门顺序不能反**：硬筛 → 命中否决 → 及格线（40）。

**命中否决**（防错误召回，详见《流程_读取》）：
- 条目侧：条目 N 个标签，query 命中数 **> N×50%** 才进入候选（阈值可调）
- query 侧：query 命中率也设门槛，初值宽松，让宽泛需求多返回参考

旧的「描述 vs 主要内容 2-gram 匹配」已**弃用**，相关同义词表/停用词表移除，改由 `lib/engine/templates/tag-equivalence.json` 做标签等价归一（双向、不注入模型）。

## 十二、验证要求

**按官方 posture：能验什么就验什么，验不了的如实说。**
（依据 `references/verification.md`，这是硬规矩）

1. **引擎单测**：`lib/engine/*` 直接 import 测，不需要 Cordis。**这是主力**。
2. **工具注册冒烟**：用假 `ctx` 加载插件，检查 `dtm_*` 是否都注册了（`ctx.tools.register`）。
3. **清单与语法校验**：`package.json`、`cordis.patch.yml`、locale、icon 的合法性；JS 语法检查。
4. **视觉验证**：有已连接的页面时按真实页面看；**没有浏览器控制时，只验到上面三项，并明确报告"视觉未验证"**。

**官方明令不许做的事**（`verification.md:3`）：

- ❌ 不许从 shell 另起浏览器、改 `HOME`、翻个人浏览器配置、找 token
- ❌ 不许为了截图去找光栅化工具、Quick Look、把 SVG 导出成预览图
- ❌ 不许**模拟 React/DOM**、写自定义渲染器来"补上"没有浏览器的缺口
- ❌ **mock 页面的截图不算验证**

> ⚠️ 因此上一版"用假 React（`h` 返回普通对象）渲染每页检查结构"的做法**已废止**——
> 那正是官方禁止的"emulate React/DOM"。
> 但上一版的教训依然成立：**语法正确不等于结构正确**，所以更要在有真实页面时真验，而不是靠模拟糊弄过去。

## 十三、技术选型

| 场景 | 选择 |
|---|---|
| 需要一个通用工具函数 | 标准 API 能写就手写；真的很繁琐再引库 |
| 需要 schema 校验 | 优先用 DSH 已有的 `@deepseek-ai/schemastery` |
| 客户端要一个 UI 组件 | **自己写控件，复制宿主同名控件的实现**（官方禁止 import `dsh-client-ui-primitives` 等 Client 包） |
| 客户端样式 | **只用主题包中真实存在的 token，优先 `--dsw-alias-*`**（详见 13.2） |
| 客户端文件超过 800 行 | **优先拆成 `client.<模块>.js`**（官方 chunk 形态可用，见 13.3）；但**首版不强制**——见 13.3 |
| 要在插件里放图标 | `icon.svg`，`exports["./icon"]` 指过去 |
| 要写用户可见的文字 | 走 Client locale 服务，别硬编码（`meta.title` / `meta.description` 至少给中英） |
| 不确定某个 API 怎么用 | `cordis_inspect_query` 查，或读 `<packageDir>/README.md` |
| 要在页面上加东西 | 先 `Slots.listSubTree` 看有哪些槽位可选 |
| 插件要放静态资源 | 放包内，通过 `exports` 暴露 |
| 需要跑定时任务 | 宿主入口 `setInterval` + `.unref()`，别阻塞进程 |
| 需要跨会话共享状态 | 存磁盘（数据目录），别放内存 |
| 阈值/开关这类可调值 | 放插件 `Config`，让用户在 `cordis.patch.yml` 改（用户的补丁层能跨升级保留） |
| 插件安装/启用 | **只用 `plugin_manager` 的 `install_bundle`**；不许手写 profile 的 `package.json`/`cordis.patch.yml`、不许在 profile 目录跑 pnpm |

### 13.1 优先复用的 DSH 能力（已按官方文档核实）

- **工具注册**：`ctx.tools.register(defineTool({...}))`（`@deepseek-ai/dsh-tools`；工具命名统一 `dtm_` 前缀）
- **系统提示注入**：`ctx.systemPrompt.section()`
- **每个 agent 的上下文**：`agent.inject()`（在 `agent/created` 里拿 `agent.ctx` 注册，并自己保管 disposer）
- **UI 槽位**：`ctx.slots.inject(ownerKey, () => ctx.slots.register(...))`
- **配置 schema**：插件 `Config`（`@deepseek-ai/schemastery`），用户在 `cordis.patch.yml` 改
- **客户端与宿主通信**：Client-callable 的 Host 入口（如 `ctx.remote.commands.execute()`），**不是自建 HTTP**
- **插件自有数据**：storage service（用 inspection 查）
- **会话派生值送前端**：宿主投影上的 `wire.view`
- **per-session 状态**：`ctx.sessionProjections`（纯同步 `apply`，`stateOf()` 读），不要自己订阅 `session/event` 重扫

> ❌ **不要**：`connection.requestRejection` 自建鉴权、`@deepseek-ai/dsh-client-ui-primitives` 等 Client 包、iframe 载入宿主 HTML。

### 13.2 客户端样式 token 的裁定（2026-11-05）

**规则：只用主题包中真实存在的 token；能对上 `--dsw-alias-*` 的必须用 alias，对不上的允许用系统级 token。**

**为什么不是"一律只用 `--dsw-alias-*`"**（实测三条事实，qa 与 client-dev 各自独立复核）：

1. **`--dsw-alias-*` 共 107 个，其中 font / radius / transition / elevation 类为 0 个**——
   这些类别在设计系统里**没有 alias 对应物**。
2. 若强制改成 alias，只能写死 `8px` / `.1s` 这类具体值 → **反而变成硬编码，比现状更差**。
3. 官方参考页（`dsh-client-ui-plugin-manager`，`practices.md` 明说"management lists 照它抄"）
   自己也在用 `var(--ds-font-family-code)`；该 token 被 15 个官方包使用。

**唯一豁免：`--ds-font-family-code`**。它是一条两层回退链
`var(--dsh-font-family-code, var(--dsh-font-family-code-default))`，内联会**拍平用户的字体自定义能力**（功能退化，不是审美问题）。

**执行口径**：
- 纯常量（radius / transition / ease）→ 已内联（`4px/8px/12px/16px`、`.1s`、`cubic-bezier(.4,0,.2,1)`）
- 可覆盖变量链（font-family）→ 保留 `--ds-font-family-code`
- **绝对禁止**：字面色（`#rrggbb` / `rgb()` / `hsl()`），artwork 除外

> 这条是对官方 `practices.md:35`「`keep only --dsw-alias-*`」的**有据放宽**，不是随手放水。
> 依据：官方包自身实践 + 无 alias 等价物 + 内联有功能损失。qa 的 R5b 断言按此更新并留痕。

### 13.3 客户端文件拆分：800 行线的裁定（2026-11-05）

**原规则**："超过 800 行 → 拆成 `client.<模块>.js`，或引入构建"。
**裁定：这条是"该拆了"的信号，不是"必须拆"的硬线。首版允许单文件超线，理由见下。**

**官方 chunk 形态确实可用**（不是猜的，7 个官方先例）：
```js
// 主入口
const Loaded = React.lazy(() =>
  require.async('./client.pages.entries.js').then(m => ({ default: m.EntriesPage })))

// chunk 文件（多一个 chunk 字段，id 与主入口一致）
window.__ModuleLoader__.load({
  id: '<包名>', chunk: 'client.pages.entries.js',
  factory(require) { /* ... */ return { EntriesPage } },
})
```
先例：`dsh-client-ui-sidebar-terminal/lib/client.terminal.js`、
`dsh-client-ui-sidebar-documentpreview/lib/client.{excel,pdf,frontmatter-fields}.js` 等。

**但硬约束**（`dsh-client-modules/README.md`）：entry 与 chunk **不能同步 require 另一个 `client*.js`**。
所以拆分时只能"主入口同步加载共用件（样式/api/通用件），作为 props 传给懒加载页面"。

**为什么首版不强制拆**：
1. **拆完就没人验过它**——现在这版是跑过全量测试、零回归的；拆完所有导入路径变化，等于把"已验证"换成"待验证"
2. **拆分引入新失败模式**——`require.async` 是网络请求，可能失败，需补 `.catch` 否则白屏；这个失败模式现在不存在
3. **收益是可维护性，不是能跑起来**——功能不受影响

**执行口径**：
- **首版**：单文件，但**必须按 `// ===== 分区 N：xxx =====` 组织**，让日后拆分有清晰边界
- **拆分时机**：首版通过真实安装验证后（v1.1 起），或单文件超过 3000 行
- **拆分时必须**：补 chunk 加载失败的兜底 UI；重跑全量测试

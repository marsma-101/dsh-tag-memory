## 1. 「假查空」的严格定义（§1.1，别再翻案）

> **真正的假查空** = 条目本就在**可见集合**内（相同项目 / 相同智能体，
> 或 `项目`/`智能体` 取值命中 `通用` / `引入` 白名单），语义上本该被调用，却没被返回。
>
> **跨项目 / 跨智能体的查空 = 正常查空**，是硬筛隔离生效的结果，**不是缺陷**。

- 硬筛（项目 + 智能体）的目的是防记忆污染、防上下文污染。**不返回是对的。**
- 上一轮报告把「55% 条目对当前会话不可见」「查 `坑/排查` 查空」当成问题列出来，
  **判错了**：前者是隔离设计，后者那些条目挂在 `ClaudeCode@dsh-SQL` 名下，
  跨身份查空属于正常。
- 审查清单写法：先算可见集合，再在集合内判真假查空；**不得**把全库条目当分母。
- 同口径探针（`scripts/probe-recall.mjs`）就是按这个口径写的：
  只对 `项目=dsh-tag-memory + 智能体=萧潇 + 通用/引入 + 状态=生效` 的条目取自证标签。

### 1.1 与召回阈值的关系（§4.1 补充）

可见集合内的假查空，2026-11-11 实测 100% 由 `ENTRY_RATIO` 否决造成
（出厂 `entryRatio=0.5` 与实库平均 4~5 个标签不匹配，标签越规范分母越大越召不回）。
已标定为 **0.3**（温和，不一步到 0.1），判定符 `>` / `>=` 逐位冻结不改。
标定只影响「集合内能不能捞出来」，**不影响硬筛**——跨项目/跨身份仍查不到。

## 2. 老条目的「稳定」是历史遗产，不是问题（§1.2）

- 库里 136 条 `稳定`、`时距` 全为 0（旧版无「时距」概念、无 `stableMinTick=3` 规则）。
- 这些条目的稳定性是**上一版记忆程序验证过的结论**，合并时原样保留是正确处置。
- **不要**因为「违反 stableMinTick」就把它们退回 `观察`，
  也**不要**在审查里标成缺陷。

### 2.1 写进状态机的口径

> **合并进来的旧条目，其稳定性视为已验证，不参与本版状态机的首次升格判定。**

- `nextStability()` 的 `stableMinTick` 门槛只约束**本版写入后**由使用过程驱动的升格；
  旧库带进来的 `稳定` 是上一版程序的结论，属于输入事实，不是待验证对象。
- `foldFeedback()` 的「命中即视为 ok」是 v1 保守近似，不是真实反馈信号
  （见 §6 演进回路）。

## 4. 写进 .md 文档 ≠ 写进记忆库（§1.4，本轮新增裁定）

- 主子指出：「源码是唯一真源、生产端由主子手动同步」是**规则和要求**，
  属于该记进本项目记忆库的长期硬边界，却只写进了方向文档、没进库。
  判定成立，已补记为 `M-20261111-002`（`规则`）。
- **口径**：把规则写进方向文档 / 说明文档，**不等于**它已进记忆库。
  - 文档是**给人看**的材料；
  - 记忆库是**给模型跨会话召回**用的账本；
  - 两者不能互相替代。
- 凡是「规矩 / 决策 / 交代 / 纠正」类，**写文档之外仍要单独 `dtm_write` 一条**。
- 审查清单里加一条：检查本轮新增的规矩/决策是否既有文档落点、又有记忆库落点，
  不要再把「文档里有了」当成「记住了」。

## 5. 整理/审查清单（把上述口径变成可执行项）

| # | 检查项 | 判错了会怎样 |
|---|---|---|
| 1 | 先算可见集合（项目+智能体+通用/引入+生效），集合外的查空一律不算缺陷 | 把正常隔离当故障 |
| 2 | 集合内查空才判真假；用 `scripts/probe-recall.mjs` 的自证探针，不要凭印象 | 漏掉阈值型假查空 |
| 3 | 老 `稳定` 条目（时距 0）不重置、不标缺陷 | 把历史遗产当数据错误 |
| 4 | `tidy.jsonl` 少 / `feedback` 空 / 无被取代 = 刚装未整理，正常 | 把正常基线当故障 |
| 5 | 本轮所有「规矩/决策/交代/纠正」是否都 `dtm_write` 了 | 规则只躺在文档里，下次照犯 |
| 6 | 改阈值后复跑探针，并确认跨项目/跨身份隔离结果不变 | 修召回却破了隔离 |
| 7 | 改动只落源码仓，生产端由主子手动同步 | 源码仍有缺陷，别人装了还是坏的 |

## 6. 演进回路的数据源（§4.6，立项备查，非现网故障）

- `read.jsonl` 每行 `feedback` 恒为 `[]`；`read.mjs` 的 `buildReadLog()` 注释自认
  是「占位参数，落盘形态待定稿」。`tidy.mjs` 的 `foldFeedback()` 只能
  「命中即视为 ok」保守近似 → 状态机缺少真实信号源，稳定性自动演进转不起来。
- 方向：定稿 feedback 的落盘形态（原地更新原行 / 另起 `action=feedback` 行），
  让「命中且被采纳 / 命中未采纳 / near 反复出现」有真实记录；再让 `runTidy` 用它演进。
- 与 §4.7 的漏写信号**合并设计，别各造一套信号**。
- 改这条要同时补 `tests/engine/tidy.k.test.mjs` 的用例。

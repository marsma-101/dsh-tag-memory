## 〇、先纠正我上一轮的一个错误结论

上一轮我写「形态判错就召回不到」。**这是错的**，实测推翻：

```
目标 M-20261111-004（真实形态=技能），查询标签 [npm,发布,registry,缓存]
  query形态=技能 → 命中，分=92（形态分50 + 标签分40）
  query形态=流程 → 命中，分=42（形态分 0 + 标签分40）
  query形态=规则/偏好/事实/模板 → 全都命中，分=42
```

形态**不是硬过滤**，只贡献 50 分权重；标签分 40 分仍能把它捞回来。真正的硬门只有一个：`e_ratio`。这个纠正很重要——它把问题从"形态设计"精确挪到了"否决闸门的数学结构"上。

## 一、先看结果：写和读的实际行为

| 总召回 | **26 次** |
| 每轮写入 | 0.237 次 |
| 每轮召回 | **0.030 次** |

**写入的可召回性其实是好的**：拿 201 条真实写入的条目，用它们自己前 3 个标签查自己，**193 条能召回（96%）**。所以"写的质量"不是主要矛盾。

**但写完就再也不读了**。这是结构性的，见 L1-3。

### 1.2 读侧：73% 查空，主因不是"库里没有"

真实会话里 26 次召回，**命中 7 次、查空 19 次（查空率 73%）**。

| 原因 | 条数 | 说明 |

| 查询词**全不在库**（用词漂移） | **1** | 例如查「通用」当标签 |
| **有擦边条目，但没过否决阈值** | **18** | 查询词在库里明明存在，条目就在那儿，就是不返回 |

这 18 条的典型（全部是真实发生过的）：

```
[session-f2c3] 形态=技能 标签=[npm,发布]           → 查空（库里 npm=10条、发布=9条）
[session-f2c3] 形态=流程 标签=[发布,npm,推送]       → 查空（三个词全在库）
[session-0cb9] 形态=技能 标签=[npm,发布]           → 查空
[session-d91a] 形态=技能 标签=[github,issue,凭据]   → 查空（三个词全在库）
[session-131e] 形态=事实 标签=[privhub-1,同步,临时目录] → 查空（三个词全在库）
[session-f2c3] 形态=技能 标签=[NO_PROXY,schannel,openssl,代理,证书] → 查空（五个词全在库）
```

**这不是"没记住"，是"记住了取不出来"。**

## 二、分层归因（从上到下）

按你的要求：先问 L1 设计，再问 L2 实现逻辑，最后才是 L3 代码。**每一层都给"为什么判定问题在这一层"的证据。**

---

### L1 上层设计层：这套逻辑的三个前提假设错了

L1 层的判定标准：不是"某段代码写错"，而是"设计时的某个前提，在真实使用中不成立"。

#### L1-1 【最根本】召回判据的分母选错了：把"写入的自由度"变成了"召回的死刑"

**设计时的假设**：`e_ratio = 命中标签数 / 条目标签数 > 0.3` 可以衡量"这条记忆和查询有多相关"。

**为什么不成立**：这个式子的分母是**条目标签数**——一个完全由写入侧自由决定的量。给定查询词数 k，`e_ratio` 的数学上限就是 `min(k,n)/n`。所以：

```
e_ratio > 0.3  ⟺  min(k,n)/n > 0.3  ⟺  n < 3.33k
```

**这是一条硬边界，不是概率**：

| 查询给 k 个词 | 条目标签数必须 ≤ | 否则 |
|---|---|---|
| 1 个 | 3 个 | **永远召不回**（无论内容多相关） |
| 2 个 | 6 个 | **永远召不回** |
| 3 个 | 10 个 | **永远召不回** |

而插件的两条规则分别是：

- **写入规则**（`free-tag-rules.json`）：`1~20 个；超过 6~8 个就该收`
- **召回规则**（同一文件 read 段）：`一次给 1~3 个词最常见`

**把两条规则代进上面的不等式**：写 7 个标签 + 查 2 个词 → `2/7 = 0.286 < 0.3` → **这条记忆从写入那一刻起就注定召不回**。

**实测验证**（不是推算，是跑出来的）：

```
M-20261111-006 标签 11 个：[npm,代理,TLS,证书,UNABLE_TO_VERIFY_LEAF_SIGNATURE,NO_PROXY,git,schannel,openssl,推送,fetch]
  查询给  1 个词（全中）→ ✗ 召不回
  查询给  2 个词（全中）→ ✗ 召不回
  查询给  3 个词（全中）→ ✗ 召不回
  查询给  4 个词（全中）→ ✓ 召回
```

同一条记忆，内容完全相关、查询词 100% 命中，给 1~3 个词就是取不出来。

**库里有多少条落在这条死区**：

| 查询词数 | 永远召不回 |
|---|---|
| 1 词 | **103 / 120 条（86%）** |
| 2 词 | **27 / 120 条（23%）** |
| 3 词 | 1 / 120 条（1%） |

**这一层的设计缺陷是什么**：把"相关度"定义成了"覆盖率"。覆盖率天然惩罚长文档——这是信息检索里几十年的老问题，标准解法是 **BM25 那样的长度归一化**（`tf / (k1·(1-b+b·dl/avdl) + tf)`，长度只做**饱和惩罚**，不做**硬性除数**）。而这里用的是硬除数 + 硬阈值，等价于"文档长度直接决定生死"。

> 参考：[BM25 的长度归一化](https://www.cs.cornell.edu/courses/cs674/2007fa/guides/lec8.part2.pdf)、[长度归一化在排序中的作用](https://research.nii.ac.jp/ntcir/workshop/OnlineProceedings14/pdf/evia/01-EVIA2019-EVIA-ClarkeC.pdf)

**判定问题在 L1 的依据**：改任何一条代码都修不掉它。调阈值只能移动死区边界（0.3→0.1 把 2 词的上限从 6 个标签抬到 20 个），改不了"分母是写入自由度"这个结构。**必须换判据形态**。

---

#### L1-2 写和读共用一套标签，但两边对"标签该打多少"的要求是相反的

**设计时的假设**：标签既是写入时的"内容索引"，也是召回时的"查询词"，一套东西两用。

**为什么不成立**：

- **写入侧**希望标签**多**：覆盖全面、将来好找、复用 wiki 已有词
- **召回侧**希望条目标签**少**：分母小才容易过阈值

这两个要求在同一个数学式里正面冲突。**写入时越"规范"（打满 6~8 个），召回时越难**——这正是设计文档里自己写下的那句话的后果：

> `标签越多越召不回，见 §4.1`

**但那条文档把"召不回"归因成"标签区分度丧失"，没归因到数学结构。** 实测表明：不是区分度问题，是分母问题。库里 6~7 个标签的条目占 126/201（63%），全部落在 2 词查询的死区边缘。

**这一层的设计缺陷是什么**：一个字段承担了两个相反方向的职责，而这两个职责的度量方式恰好互为倒数。标准解法是把"索引"和"查询"解耦——索引侧可以任意丰富（多标签、全文），查询侧用一个**与文档长度无关**的匹配分数。

**判定问题在 L1 的依据**：改 `free-tag-rules.json` 的措辞（少打标签）会让召回变好但写入变差；改召回判据（降低阈值）会让召回变好但噪音变多。**在同一个字段上二选一，必然牺牲一边。** 必须解耦。

---

#### L1-3 只有写侧有触发机制，读侧靠自觉 → 结构上必然"只进不出"

**设计时的假设**：写侧需要"漏记提醒"（每轮检查），读侧不需要——因为"想找自然会找"。

**为什么不成立**：

| | 写侧 | 读侧 |
|---|---|---|
| 每轮检查点 | **有**（`agent/pre-step` 里 `shouldRemind`） | **无** |
| 会话里出现次数 | 漏记提醒在 **32/89 个会话**里出现过 | **0 次** |
| 注入覆盖率 | 26%（7/27 轮，dsh-SQL 主会话） | **0%** |
| 每轮发生频率 | 0.237 次 | 0.030 次 |

**实测**：`tag-memory` 来源的注入消息在 dsh-SQL 主会话里出现 7 次，**7 次全部是"这一轮还没写记忆"的漏记提醒，没有一次是"该回忆了"的提醒**。

**结果**：856 轮里只有 26 次召回（3%），而写入 203 次（24%）。**库以 7.9:1 的速度膨胀，读侧完全没被驱动。**

**这一层的设计缺陷是什么**：把"写"当成了需要被提醒的动作，把"读"当成了自然发生的动作。但在实际使用里，**读比写更不容易自发发生**——写是"我做了什么"，有明确的当下触发；读是"我可能需要过去的东西"，需要主动意识到"我可能忘了"。后者恰恰是 LLM 最不擅长的自我监控。

> 这不是我一个人的观察。Generative Agents 那套记忆流的标准做法是把 **recency（时间衰减）+ importance（重要性）+ relevance（相关性）** 三者加权，而 **recency 的基准是「上次被检索的时间」而不是「创建时间」**——也就是说，"被想起来"本身要能被度量、被奖励。见 [Memory Stream 实现参考](https://github.com/DanceNitra/agora/blob/main/onboarding/game-dev/references/memory-stream-impl.md)、[遗忘机制的分层设计](https://github.com/richmondalake/memorizz/blob/16d65d6aedef065a20063c4bd6864a0de3d68f46/docs/guides/forgetting-mechanism.md)

**判定问题在 L1 的依据**：加一条提醒文案是 L3 的活；但"读侧要不要有检查点、检查什么"是 L1 的结构问题。当前设计里读侧连一个观测点都没有（`read.jsonl` 只记录"模型主动查了什么"，不记录"模型本来该查什么"），**所以连"漏读率"都无法度量**——这比漏读本身更根本。

---

#### L1-4 生命周期维度缺失（上一轮已详述，这里归位到 L1）

**设计时的假设**：记忆只有"内容 + 形态 + 归属 + 稳定性 + 时距"，没有"这条该活多久"。

**为什么不成立**：库是"只追加"的，而"一次性/进度类"记忆和"长期规矩"记忆混在同一个空间里，没有任何机制区分。7 天写 195 条、退场 0 条，库 +118%。

**这一层的设计缺陷是什么**：把"记忆"当成了同质的东西。实际上至少有三种时间尺度：
- **常驻**（规矩、踩坑正解、环境事实）—— 应该永远在
- **会话内**（本轮进度、临时便签）—— 会话结束就该退场
- **待验证**（"已修好待测"）—— 验证完成后要么升常驻、要么退场

当前设计只有一个"稳定性"字段，而它衡量的是"这条对不对"，不是"这条还成不成立"。

**判定问题在 L1 的依据**：加一列是 L3；但"要不要引入时间尺度这个维度"是 L1。而且这个维度**必须和 L1-3 一起设计**——因为"这条多久没被用过"正是读侧检查点最自然的判据。

### L2 实现逻辑层：函数职责边界与信号来源

L1 判定为"设计前提不成立"的，不在 L2 重复。L2 只看**设计意图是对的、但实现时的函数划分/职责边界出了问题**。

#### L2-1 打分与否决闸门的职责倒挂：及格线从不生效，长度否决承担全部拒绝

**设计意图**（`scoring.json`）：三段闸门——①硬筛（归属/状态）②命中否决（e_ratio/q_ratio）③及格线（总分 ≥ 40）。意图是"否决先粗筛，及格线再精筛"。

**实现实际**：

```
可见 120 条，用各自前 2 个标签自查询：
  被否决闸门拦：27 条
  被及格线拦：  0 条   ← 及格线一次都没生效
  通过：       84 条
```

**为什么**：`scoreRecord` 的三项是 `形态分(50) + 标签分(40) + 时距分(10)`。只要形态命中就直接 50 分，**已经超过 40 的及格线**。所以及格线在形态命中时永远过；在形态不中时，标签分只要 ≥ 40×0.15（q_ratio 下限）= 6 分就够——而 `q_ratio ≥ 0.15` 正是否决闸门的另一条判据，所以**过了否决闸门就必然过了及格线**。

**这不是"参数没调好"，是职责重叠导致的恒真**：

```
否决闸门判据：q_ratio >= 0.15
及格线可达性：形态命中→50分(必过)；形态不中→标签分 = q_ratio×40 >= 6 分，加时距分 → 必过 40
⇒ 及格线是死代码（对筛选毫无贡献）
```

**实测佐证**：27 条"自查询得分 ≥80 却被否决"的条目——**分数高到 90 分都过不了**，因为否决闸门在前面：

```
M-20261111-004 标签9个 分=92.0 e_ratio=0.222 ← 被否决
M-20261111-005 标签10个 分=90.0 e_ratio=0.200 ← 被否决
M-20261111-006 标签11个 分=90.0 e_ratio=0.182 ← 被否决
M-20261012-016 标签7个 分=90.0 e_ratio=0.286 ← 被否决
```

**这是典型的"高相关度被长度惩罚杀死"**：分数在说"很相关"，否决在说"不许返回"。

**这一层的逻辑问题**：**筛选职责放错了位置**。真正该做粗筛的是"有没有任何相关"（零命中才否决），真正该做精筛的是"够不够相关"（及格线）。当前实现把这个顺序反了：用最粗暴的长度比值做粗筛，用本该精筛的分数做展示。

**修复后的效果（实测，非推算）**：

| 方案 | 自查询召回率 k=1 / k=2 / k=3 | 真实 26 次查询有返回 | 平均返回条数 | 跨主题噪音 |
|---|---|---|---|---|
| A 现状（e_ratio>0.3） | **7% / 76% / 97%** | 17/26 | 1.3 条 | 0% |
| B 只挡零命中 | 89% / 100% / 100% | 22/26 | 2.4 条 | **18%** |
| D 只挡零命中 + 及格线 75 | **89% / 100% / 100%** | 14/26 | **0.7 条** | **0%** |

**方案 D 是这一层该走的方向**：召回率从 7%/76% 提升到 89%/100%，同时**真实查询的返回量反而更少（0.7 vs 1.3）**、跨主题噪音 0%。也就是说，**及格线完全能承担长度否决原本想做的工作，而且做得更好**——因为它是连续信号、可解释（形态/标签/时距三项明细）、可通过改善标签质量提升，而不是一道数学死锁。

**判定问题在 L2 的依据**：L1 说的是"分母选错了"，L2 说的是"就算分母选对了，三段闸门的职责也是重叠的"。这是两个独立的缺陷：即使把 e_ratio 改成"与长度无关的口径"，只要及格线仍然恒真，筛选就仍然只靠否决闸门一道。

#### L2-2 信号来源缺失：状态机在拿自己的输入当输出验证

**设计意图**（`tidy.mjs` 注释）：`foldFeedback` 从 `read.jsonl` 读 feedback，驱动稳定性三态演进。

**实现实际**：`feedback` 字段**恒为 `[]`**（23 条 read 记录全部为空），于是 `foldFeedback` 退回"命中即视为 ok"。

**为什么这是 L2 而不是 L3**：

```
时距 = 1 + 命中次数          （由 applyTick 维护）
ok   = 命中次数              （由 foldFeedback 的隐含默认产生）
⇒ ok ≡ 时距 - 1
```

而状态机的两个"独立"升格条件是：`时距 ≥ 3` **且** `连续 ok ≥ 3`。代进去就是同一个条件写了两遍。

**实测**：一条从未被任何人验证过对错的记忆，召回 4 次 → 时距 5、ok 4 → 状态机判定"稳定"，理由写着"时距 5（门槛 3）+ 连续 ok 4 次（阈值 3）"。

**这一层的逻辑问题**：**"被检索"和"被采纳"是两件事，但实现把它们合成了一件**。而这两个信号在语义上完全独立——一条记忆可以被检索 10 次、10 次都没用上（说明它是个高频干扰项，该降级），也可以被检索 1 次、那次解决了大问题（说明它很重要）。

**根本原因**：`read.jsonl` 只记录了"召回了什么"，**没有记录"召回之后发生了什么"**。而"之后发生了什么"才是反馈。这不是某个函数写错，是**数据流在设计上少了一段**。

**与 L1-3 的关系**：这是同一个洞的另一面。L1-3 说"读侧没有检查点"，L2-2 说"读侧没有结果回写"。两者合起来：**读侧是一个开环**——发出去了，没人知道结果。

---

#### L2-3 写侧遵守了"判据给模型"，读侧退回了"关键词枚举"

**这是最能说明"同一套原则没有贯彻到底"的一处。**

插件在 `schema.json` 的 `_writeRoutes` 里明确写着：

> 判据给模型用——**不要在程序里分类用户输入（正则/关键词必崩，换一种说法就漏）**

写侧确实做到了：`writeRoutes.rules` 是一组**判据**（"规矩→规则""决策→事实"），不是关键词表。

**但读侧（`preset/prompt.js:111`）写的是**：

```
- 提到「之前/上次/定过」、要做可能做过的事、说你漏了什么 → `dtm_recall`。
```

**这是一串封闭的短语枚举**，正是写侧明确禁止的那种做法。

**实测代价**（89 会话、811 条真实用户消息）：

| 信号类型 | 用户实际说法 | 命中数 |
|---|---|---|
| 延续类 | 继续 / 接着 / 下一步 / 然后呢 | **63 条（7.8%）** |
| 回指类 | 那个 / 刚才 / 前面说 / 你说过 | **111 条（13.7%）** |
| 状态类 | 进展 / 到哪了 / 完成了没 | 4 条 |
| 复现类 | 又出现 / 还是不行 / 老问题 | 1 条 |
| 偏好类 | 按我的习惯 / 老规矩 / 照旧 | 0 条 |
| **插件触发词** | 之前 / 上次 / 定过 / 说过 | **66 条（8.1%）** |

```
任何"需要回忆"的信号：165 条
插件触发词覆盖：66 条
漏掉：141 条（85%）
```

**典型漏掉的**（真实用户原话）：

```
"继续"                                    ← 最典型的"接着上次"，插件完全不认
"刚才你查的时候…"                          ← 回指，插件不认
"老问题 / 又出现了"                         ← 复现类，最需要历史记忆，插件不认
"按我的习惯来"                              ← 偏好类，最需要跨会话记忆，插件不认
```

**这一层的逻辑问题**：**同一套原则在两条路径上执行标准不一致**。写侧用判据（可泛化），读侧用枚举（不可泛化）。而读侧恰恰是更需要泛化的地方——因为"我需要回忆"这个意图，比"我该记住"的表达方式更发散、更隐蔽。

**判定问题在 L2 的依据**：L1 说的是"读侧没有检查点"（结构缺失）；L2 说的是"读侧有检查点，但检查的是封闭短语表"（实现方式错）。即使加上检查点，只要检查的是枚举，覆盖率仍然只有 15%。

---

#### L2-4 形态与类别标签是两套正交分类，但名字撞车

**设计意图**：`形态`（技能/流程/规则/偏好/事实/模板）是"这是哪种东西"；`自由标签` 的第一个词是"类别值"（规矩/决策/交代/踩坑/纠正/流程/原话/推断）。

**实现实际**：这两套分类**语义高度重叠，但取值不重合**：

```
形态 6 值：  技能 / 流程 / 规则 / 偏好 / 事实 / 模板
类别标签：  规矩 / 决策 / 交代 / 踩坑 / 纠正 / 流程 / 原话 / 推断
```

**「流程」两边都有**。库内实测：形态=流程 23 条，标签含"流程"19 条，**两者都有 11 条**——同一个词在两条正交轴上各标一次，信息完全重复。

**真实会话里已经出过事**：`_sess-probe4` 提取的 203 次写入里，形态参数出现过 **`决策=1`、`交代=1`**——这两个值是**类别标签**，不是形态。它们会被 `SHAPE_INVALID` 拒写（这条校验是对的），但说明**模型自己都分不清这两套分类**。

**这一层的逻辑问题**：分类维度重叠却各立一套词汇表。模型每次写入要做两次语义相近但取值不同的判断，任一处判错都会影响后续（形态错→丢 50 分；类别词错→标签噪音）。

---

### L3 代码与调用层

L1/L2 都干净的才归这里。以下四条是纯实现缺陷，**单独修不影响逻辑结构**。

#### L3-1 `near` 序列化形状不一致（上一轮已发现）

```
buildReadLog  : near: (r.near ?? []).map(n => `${n['编号']} 分=${n.score} e_ratio=${n.e_ratio}`)  ← 存成字符串
foldFeedback  : const id = typeof n === 'string' ? n : n && n['编号']                         ← 整串当编号
```

实测：`foldFeedback` 产出 63 个 key，**46 个是这种垃圾 key**；69 条 near 反馈的 `unused` 全落在垃圾 key 上。

测试 K4 用的是 `{ 编号:'M-9', 分:35 }` 对象形状，与生产序列化不一致，所以绿。

**为什么归 L3**：`recall()` 返回的 `near` 本来就是对象数组，`buildReadLog` 在写盘时把它转成字符串是为了"人可读"，`foldFeedback` 在读盘时应该反向解析但没做。**这是两个函数之间的数据格式契约没对齐**，与 L1/L2 的设计无关。修法：`buildReadLog` 存对象（与 `recall` 返回一致），`foldFeedback` 自然能解析。

#### L3-2 时距 cap 与打分上限数学互斥（上一轮已发现）

```
tickCap = 10（字段封顶）   tickMaxScore = 10（打分权重上限）   multiplier = 2
封顶时 时距分 = min(log2(10)×2, 10) = 6.64  ← 永远拿不到 10
要拿 10 分需 时距 = 2^(10/2) = 32     ← 而 applyTick 的 cap 就是 10
⇒ 理论总分上限 96.64，文档/测试声称 100
```

测试 E5 用 `时距=32` 断言满分——**这个输入在真实链路永远不可达**。

**为什么归 L3**：两个配置项各自独立看都合理（计数器封顶 10 次、权重上限 10 分），**放在一起才矛盾**。这是配置取值问题，不是设计问题。

#### L3-3 浏览模式也给时距 +1

```
recall(browseMode=true) → tickTargets = 5 个编号 → 5 条时距 +1
```

"翻看"和"使用"被当成了同一件事。而时距参与排序（实测改变 76.8% 查询的返回顺序），所以**翻看一次就会让这 5 条以后更容易被翻到**——正反馈。

**为什么归 L3**：`recall()` 里 `tickTargets = hits.map(...)` 这一行没有区分 `browseMode`。设计上"被返回就算用过"这个假设在 L2 层面也站不住，但**至少浏览模式是明确知道自己在浏览的**，这一处是纯粹的遗漏。

#### L3-4 写入校验没有复用已有的 `isUsefulTag`

`vocab.mjs` 里已经有完整的标签质量判据（`isUsefulTag`：排纯数字、版本号、十六进制、单字、无字母符号串…），但 `validateWriteInput` **没有调用它**。

实测：`['3190','版本','测试']` → `ok:true`，纯数字标签被放行。库内实际有 **20 条含纯数字标签、16 条含单字标签**。

而 `标签字典.md:226` 明确写"不打纯数字"。**文档有规则、代码有实现、两者没接上。**

**为什么归 L3**：判据已经存在且经过实测打磨（注释里写了六轮迭代），只是没被调用。这是接线问题。

## 三、改进方案（按层，从 L1 往下）

**原则**：先改 L1（结构），L1 定了 L2 才有意义，L2 定了 L3 才不会白改。**不按严重度排，按依赖排。**

### 3.1 L1 层的改动（三条，互相咬合，建议一起设计）

#### L1-A：把召回判据从"覆盖率"改成"命中强度 + 及格线"

**动的不是某个阈值，是判据形态。**

```
现状：e_ratio = |命中| / |条目标签数| > 0.3     ← 长度做硬除数
改为：① 否决闸门只挡"零命中"：|命中| == 0 才否决
      ② 筛选职责交给及格线，及格线改成三项明细可解释的连续分
```

**为什么这样改能根治**：

- 长度不再做硬除数 → 不存在"标签打多了就永远召不回"的死区（L1-1 解决）
- 写入侧可以自由打标签 → 索引与查询解耦（L1-2 解决）
- 及格线可解释（形态/标签/时距三项）→ 用户能看懂为什么这条没返回
- 标签质量差会体现为分数低，而不是"永远出不来"→ 可通过 `isUsefulTag` 改善（与 L3-4 呼应）

**实测支撑（方案 D）**：自查询召回率 7%/76%/97% → **89%/100%/100%**；真实查询平均返回 1.3 → **0.7 条**（更精准）；跨主题噪音 **0%**。

**必须同时做的**：`probe-recall.mjs` 的自查询探针**不能作为唯一验收标准**（它的查询词天生与条目标签 100% 重合，测不出真实场景）。必须补一个"真实查询回放"探针——用会话日志里实际发生过的查询重放。这次审计已经验证可行（26 条真实查询）。

#### L1-B：给读侧加检查点，且用判据不用枚举

```
新增：与"漏记提醒"对称的"该回忆提醒"
判据（给模型看，不是程序正则）：
  · 用户在延续之前的工作（继续/接着/下一步/然后呢）
  · 用户回指过去（那个/刚才/前面说/你说过）
  · 用户报告旧问题复现（又出现/还是不行/老问题）
  · 用户引用习惯或旧约定（按我的习惯/老规矩/照旧）
  · 本次要做的动作在库里可能有先例
```

**关键设计约束**（照抄写侧的成功经验）：

1. **判据给模型，程序只判"这轮调没调过 dtm_recall"**——绝不写正则分类用户输入（那正是 L2-3 的错误）
2. 走 `agent/pre-step` 消息历史，不进 system prompt（KV cache）
3. 复用 `inject-gate.mjs` 的节流闸门（同轮不重投、会话配额、退避）
4. **必须能关闭**，且默认策略要保守（否则会变成刷屏）

**同时补上观测能力**：`read.jsonl` 增加一个"本轮有召回信号但未召回"的记录位。否则"漏读率"永远无法度量（这是 L1-3 说的"连观测点都没有"）。

#### L1-C：引入生命周期维度（与 L1-B 共用"闲置"判据）

**不加 TTL 列**（TTL 是猜的），用已有事实推导：

```
常驻    ：稳定性=稳定，或被召回 ≥ 3 次
观察中  ：本版写入后从未被召回（时距 ≤ 1）且创建 ≤ N 天
待退场  ：本版写入后从未被召回 且 创建 > N 天
```

**推导依据**（全部库内已有）：创建日（编号解析）+ 最后召回日（`read.jsonl`）+ 时距 + 稳定性 + 形态。

**落点**：`planTidy` 增加第 6 类产出 `proposals: [{kind:'retire', 编号, 依据}]`——**只提议不自动改**，符合现有纪律（拆库/升通用都是只提议）。

**实测候选**：规则 R3（生效 + 创建>3天 + 从未召回 + 时距≤1 + 稳定性∈{观察,易变}）= **115 条**。对照：按"时距=0 且稳定"判会误伤 131 条历史结论——**这就是必须用时距+创建日+台账三者联合判、而不能只看一个字段的理由**。

**与 L1-B 的关系**：`read.jsonl` 有了"漏读"记录后，"从未被召回"就能区分"没被需要"和"想找但没找到"——**这是生命周期判定的质量分水岭**。

### 3.2 L2 层的改动

| 编号 | 改什么 | 为什么这是 L2 而不是 L3 |
|---|---|---|
| **L2-1** | 三段闸门重新分工：否决只挡零命中，及格线承担精筛（与 L1-A 同一次改动） | 动的是**函数职责边界**（`recall` 里闸门②③的顺序与权重），不是某一行判断 |
| **L2-2** | 给 `read.jsonl` 补 feedback 回写通道：模型在下次调用时回填"上次那几条有没有用上" | 动的是**数据流结构**（少了一段回写），不是某个函数实现 |
| **L2-3** | 删掉 `prompt.js` 的召回触发词枚举，换成 L1-B 的判据 | 动的是**注入内容的性质**（枚举→判据），不是措辞 |
| **L2-4** | 形态与类别标签去重：`流程` 二选一，或把类别词从"首标签"挪到独立位置 | 动的是**两个分类维度的关系**，不是取值表 |

**L2-2 的落盘形态建议**（需要你拍板）：

```jsonl
{"ts":"...","cond":{...},"hits":["M-xxx"],"feedback":[
  {"id":"M-xxx","verdict":"used"},      // 用了，且解决了问题
  {"id":"M-yyy","verdict":"irrelevant"},// 看了，不相关
  {"id":"M-zzz","verdict":"stale"}      // 内容已过期
]}
```

**回填时机**：模型下一次调 `dtm_recall` 或 `dtm_write` 时，工具返回里带一句"上次召回的那几条，哪条真用上了？"。这是**唯一不靠猜的信号源**——只有模型自己知道刚才那条记忆有没有帮上忙。

**为什么不能继续用"命中即 ok"**：实测 `ok ≡ 时距-1`，状态机在自证。而且这个默认值会让**高频干扰项**（被反复召回但从不解决问题）反而升到"稳定"。

## 四、需要你拍板的三件事

### 拍板 1：召回判据换成什么形态

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）** 否决只挡零命中 + 及格线提到 75 | 实测召回率 7%/76%/97%→89%/100%/100%，返回量更少更准，噪音 0% | 需要重新标定 `passLine`；`scoring.json` 的 `entryRatio` 语义改变 |
| B 只挡零命中，及格线维持 40 | 召回率同样拉满，但返回量翻倍（1.3→2.4 条）、跨主题噪音 18% | 噪音需要靠模型自己过滤 |
| C 保留 e_ratio，只把阈值降到 0.1 | 改动最小（一个数字） | 2 词查询下标签 ≤20 个都能过，等于取消长度约束但保留了不透明的判据形态；**治标不治本** |

**我推荐 A**，理由：它同时满足"该召回的能召回"和"不该召回的召不回"，而且及格线是三项明细，出问题能定位到是哪一项低。

### 拍板 2：feedback 回写要不要做

这是 L2-2 的地基。不做的话：
- 稳定性状态机永远在自证（`ok ≡ 时距-1`）
- 生命周期判定分不清"没被需要"和"想找但没找到"
- 时距只能反映"被翻到"，不能反映"被用到"

做的话需要你接受一个交互成本：**模型每次调 `dtm_recall` 会被追问"上次那几条用上了吗"**。这会让召回多一轮往返。

**我推荐做**，但可以先用"只在下次写入时顺带回填"降低频率（不额外多一轮）。

### 拍板 3：读侧提醒的默认策略

| 选项 | 说明 |
|---|---|
| **A（推荐）** 默认开，但节流到"每会话最多 2 次、间隔 ≥1 轮"（复用现有 `inject-gate` 的默认策略） | 与写侧漏记提醒同一套闸门，行为可预期 |
| B 默认关，设置页可选开 | 保守，但大概率没人开，等于没做 |
| C 不新增提醒，只改 `prompt.js` 的触发词枚举 | 零成本，但实测覆盖率只能从 15% 提到约 35%（仍是枚举） |

---

## 五、一句话总结

上一轮我停在 L3，给的是"改这几行"。这一轮往上看，真正的根因是三条：

1. **L1-1 召回判据的分母是写入自由度** → 写入越规范、越召不回，这是数学死锁，调阈值无效。
2. **L1-3 读侧是开环** → 没有检查点、没有结果回写、连"漏读率"都无法度量。所以库以 7.9:1 膨胀，而读侧频率只有 3%。
3. **L2-3 同一套原则只贯彻了一半** → 写侧"判据给模型"做对了，读侧退回"关键词枚举"，覆盖率 15%。

你说的"不该写的写了、该写的没写、该召回的没触发、不该召回的却找回了"，实测答案是：

- 该写的**基本都写了**（0 轮漏写）
- 不该写的**有 4%**，但库内累计 115 条待退场
- **该召回的 85% 没触发**（这是最大的洞）
- 不该召回的**没明显过召回**，反而是**该返回的返回不出来**（73% 查空）

所以这不是"写入质量"问题，是**读侧的两级失效**：想不起来去查（L1-3/L2-3）+ 查了也查不到（L1-1/L2-1）。

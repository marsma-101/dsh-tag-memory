# 一、已确认的缺陷（有实测证据）

## P0-1：数据目录落到 package 兜底，配置不生效

**实测证据**（在容器内执行）：

```
不传 config 调 apply({}) 时：
  dataDir: /opt/dsh/plugins/dsh-tag-memory/data
  来源: package
  锁定: false
```

而 patch 里写的是 `dataDir: /opt/dsh/tag-memory`。

**已排除的推断**：一开始怀疑是「没导出 Config 导致 config 不传」。
查 cordis 源码 `resolveConfig`（`cordis/lib/index.js:244`）：

```js
function resolveConfig(runtime, config) {
  if (!runtime.Config) return config;        // 没 Config 就直接原样返回
  const result = runtime.Config["~standard"].validate(config);
  ...
}
```

→ **没有 Config 时 config 照样传入。所以这不是 Config 缺失导致的。**
真正原因待查：可能是 patch 没被加载、或 config 传给了错误的插件实例。

## P0-2：目录命名带版本号（违反主子明确要求）

主子原话：
> 这个是 v1，而且是内部记录版本，不显示在插件上，插件名不变，文件夹也需要用插件名。

**当前不符的地方**：

| 位置 | 当前值 | 应为 |
|---|---|---|
| 容器插件目录 | `/opt/dsh/plugins/dsh-tag-memory` | ✅ 已改好 |
| 容器数据目录 | `/opt/dsh/tag-memory` | ✅ 已改好 |
| 宿主机数据目录 | `C:\Users\Administrator\.dsh\tag-memory` | ✅ 已改好 |
| **package.json version** | `0.1.0` | 待确认（内部版本号应保留但不出现在路径） |

**遗留问题**：改名后容器 UI 显示「共 0 条」，但 `/opt/dsh/tag-memory/store/memory.csv` 有 180 行。
→ 数据在，但插件没读到。与 P0-1 是同一个根因。

## P0-3：数据写在会被升级删除的位置

因为 P0-1，历史数据一直写在 `/opt/dsh/plugins/dsh-tag-memory/data/`（插件包内）。
`pnpm` 重装/升级会删掉整个包目录 → **数据丢失风险**。

设置页其实如实显示了「生效来源：插件包内目录（出厂默认）」并给出搬家提示，
但没人把这行提示当回事。

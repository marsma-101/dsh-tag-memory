### 问题 1 的结论：不要自建 HTTP 路由与鉴权

- 官方路径：**客户端通过 Client-callable 的 Host 入口调用宿主方法**（如 `ctx.remote.commands.execute()`）；插件自有数据放 **storage service**。
- `user-actions.md` 明确“一个操作、两个调用者”：UI 与工具调**同一个宿主方法**。
- 结论：`/tag-memory-api` + `connection.requestRejection` + fail-closed 503 的**自建方案作废**。
- 仍需动手核实：`ctx.remote.commands` / storage / `ctx.sessionProjections` 的**具体注册写法**——用 `cordis_inspect_query` 查，不靠猜。

### 问题 2 的结论：客户端模块形态已定

官方模板 `templates/decoration/client.js` 给出确切形态：`window.__ModuleLoader__.load({ id, factory(require){...} })`，
React 从浏览器模块表 `require('react')` 取、**不用自己装**；非基线运行时依赖声明在 `dsh.client.external`。
官方：“For compiled sources, use the deployment's Client build tooling to emit this format” —— **可多文件 + 构建**至该形态。
仍需动手核实：多文件 `client.<name>.js` 是各自独立 `__ModuleLoader__.load`，还是入口内动态注册。

### 问题 3 的结论：安装与依赖

- **只用 `plugin_manager` 的 `install_bundle`**（target 传包目录绝对路径）。
  官方明令：**不许**手写 profile 的 `package.json`/`cordis.patch.yml`、**不许**在 profile 目录跑 pnpm、**不许**在 `$DSH_HOME` 下建包。
- 必需显示资源：`locale/*.json` 的 `meta.title`/`meta.description`（含用户语言）+ `icon.svg`（≤256KiB）+ `exports`/`files` 覆盖全部运行时文件。
- 可调值放插件 `Config`，用户在 `cordis.patch.yml` 改（补丁层跨升级保留）。

### 另外三条官方硬规矩

1. **不许 import 任何 Harness Client 包**（如 `@deepseek-ai/dsh-client-ui-primitives`）——要控件就复制宿主实现进自己插件。
2. **不许 iframe 载入宿主返回的 HTML**——UI 必须是 slot 里的 React 组件。
3. **验证不许造假**：不另起浏览器、不找光栅化工具、**不模拟 React/DOM**、mock 截图不算验证；无浏览器控制就如实报“视觉未验证”。

## 问题 4：记忆库本体文件格式（CSV vs JSONL）

### 现状认知

架构原定 `store/memory.csv`（9 列，顺序固定）。v2 引入了两个新约束：
- `自由标签` 是多个离散词（≤20），文档示例用逗号分隔（`发版检查,需先build`）；
- `主要内容` 不设字数上限，必然含逗号、换行、引号。

这两点和 CSV 的"逗号字段分隔符 + 需 RFC4180 引号转义"直接冲突：标签列内再用逗号会撞分隔符；长正文必须严格引号包裹转义，否则一行被拆多行。

备选是改用 **JSONL**：`store/memory.jsonl`，每行一个 9 字段对象，`自由标签` 直接是字符串数组，逗号/换行/引号天然无冲突；`records/*.jsonl` 已是 JSONL，少一套序列化逻辑。代价：文件体积略大、检索仍要全扫（CSV 本也要全扫）。

### 不明确的地方

- 在 DSH 宿主侧，**整文件读写 CSV 与 JSONL 的工程成本差多少**？是否有现成工具（如 DSH 自带 CSV/JSON 读写）？
- 若选 JSONL，是否沿用 `records/*.jsonl` 的同款序列化约定（一行一条、字段顺序无关）？
- 记忆量大到需要拆库拆表时（条目数超阈值 / 时距量级超阈值 / 自由标签重复度过高），两种格式各自的迁移成本？
- 是否需要在 `core.mjs` 里把"序列化/反序列化"单独抽一层，便于日后换格式？

### 倾向

**已拍板：采用 JSONL。** 理由见《架构说明》数据目录与第八节——CSV 与 v2 的"自由标签多词 + 主要内容无上限含逗号/换行"冲突，JSONL 干净解决且与 `records/*.jsonl` 同格式。
仍需查的只剩实现细节（DSH 有无现成 JSON 读写、序列化抽层位置、拆库拆表迁移），可在开发阶段顺带确认，不阻塞架构。

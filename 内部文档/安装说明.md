# 安装说明

> 适用于 dsh-tag-memory v1（内部版本 `0.1.0`，**版本号不体现在任何路径上**）。
> 最后更新：2026-11-06（P0-1 事故后重写）

---

## 一、装（唯一正确方式）

**用 `plugin_manager` 的 `install_bundle`。**

```
plugin_manager {
  action: "install_bundle",
  target: "dsh-tag-memory"
}
```

它会做三件事：装包 → 读包里的 `cordis.patch.yml`（bundle 补丁）→ 把它 insert 的两行挂进 profile。

### ❌ 不要这么做

| 反面做法 | 后果 |
|---|---|
| 手动 `cp` 包目录到 `node_modules` | profile 的 `package.json` / bundle 列表不会更新，DSH 根本不加载 |
| 手写 profile 的 `package.json` 或 `cordis.patch.yml` | 官方明令禁止；容易写成 DSH 解析不了的形状 |
| 在 profile 目录里跑 `pnpm` | 会破坏 lockfile 与 link 投影 |
| 在 `$DSH_HOME` 下建包 | 同上，官方明确禁止 |

---

## 二、⚠️ 最容易踩的坑：profile 补丁的 `id` 必须等于 bundle 补丁 `insert` 的 `id`

### 这是 2026-11-06 P0-1 事故的根因

**现象**：插件装上了、UI 能打开，但显示「共 0 条」；数据其实在 `插件包/data/` 里，配置里的 `dataDir` 完全没生效。

**原因**：补丁方言里，**顶层 `- id: xxx` 不是"新增条目"，而是"按 id 覆盖一个已存在的条目"**。

`dsh-app-boot` 的 `applyPatches()`：

```js
const { id, insert, name, ...overrides } = patch;
if (insert) { data.push(...clone); continue; }        // insert = 新增
if (!id) { warn("patch: id is required for non-insert patches"); continue; }
const target = entryMap.get(id);
if (!target) { warn("patch: entry %C not found", id); continue; }   // ← 找不到就整条丢弃
```

**只打一条 warn，不报错，不中断启动。** 于是：

```
bundle 补丁 insert 的 id:  dsh-tag-memory   dsh-tag-memory-tools
profile 补丁写的 id:       tag-memory       tag-memory-preset      ← 对不上
结果:                      patch: entry "tag-memory" not found
                           config 根本没传进 apply() → 落 package 兜底
```

### 正确的 profile 补丁

```yaml
- id: dsh-tag-memory              # 必须逐字等于 bundle insert 的 id
  name: dsh-tag-memory
  config:
    dataDir: /opt/dsh/tag-memory

- id: dsh-tag-memory-tools        # 预设入口，同上
  name: dsh-tag-memory/preset
  config:
    dataDir: /opt/dsh/tag-memory
```

bundle 补丁（插件自带，`cordis.patch.yml`）里定义的就是这两个 id：

```yaml
- insert:
    - id: dsh-tag-memory
      name: 'dsh-tag-memory'
    - id: dsh-tag-memory-tools
      name: 'dsh-tag-memory/preset'
```

**改 bundle 补丁的 id 就要同步改 profile 补丁。** 反过来也一样。

### 怎么自查

装完跑一次（见第五节）：

```bash
node 内部文档/工具/verify-install.mjs
```

它会报出「profile 有、bundle 没有」的 id —— 那些就是会被静默丢弃的条目。

## 三、⚠️ 另一条：`config` 是**整体替换**，不是深合并

补丁方言对 `config` 这个键做的是 `target[key] = value`，**整块覆盖**。

```
bundle insert 的 config:  { dataDir: '/a', other: 1 }
profile 覆盖的 config:    { dataDir: '/b' }
最终结果:                  { dataDir: '/b' }          ← other:1 被整个抹掉
```

所以：

- 在 profile 里写 `config` 时，**要么把需要的键都写全**，要么就别写
- 不要指望「只覆盖一个键、其余继承」

> 这也是为什么 **bundle 补丁里不写 `dataDir`**：绝对路径写死在包里，Linux 容器能用、Windows 宿主机就指向不存在的 `/opt/dsh/...`，而 `resolveDataDir` 对非空字符串是**直接采纳、不检查是否存在**的 —— 会静默写错地方，比不配更危险。

## 四、数据目录：默认在哪、怎么改

### 5 级优先级（`lib/engine/core.mjs` 的 `resolveDataDir`）

| 级 | 来源 | `dataDirSource` | 搬家是否生效 |
|---|---|---|---|
| ① | `config.dataDir`（profile 补丁） | `config` | ❌ 锁定 |
| ② | 环境变量 `DSH_TAG_MEMORY_DATA_DIR` | `env` | ❌ 锁定 |
| ③ | 设置页选的（`<包>/config/data-dir.json`） | `settings` | ✅ |
| ④ | **`$DSH_HOME/tag-memory`** | `dsh-home` | ✅ |
| ⑤ | `<插件包>/data`（**最后手段**） | `package` | ✅ 但危险 |

### 默认位置

| 环境 | `$DSH_HOME` | 默认数据目录 |
|---|---|---|
| Docker 容器 | `/opt/dsh` | `/opt/dsh/tag-memory` |
| Windows 宿主机 | `C:\Users\<你>\.dsh` | `C:\Users\<你>\.dsh\tag-memory` |

**不配也能用** —— ④ 级兜底会自然落到 `$DSH_HOME/tag-memory`，且不写死在包里。
这正是「两边不用手动对齐」的原因。

### ⑤ 级为什么危险

`<插件包>/data` 会被 `pnpm` 重装/升级**整个删除**，用户数据随之丢失。

落在这里时会有两处告警：

- 启动日志：`[dsh-tag-memory] ⚠️ 数据目录落在插件包内…`
- 设置页返回值：`getSettings().warning` 非 `null`

**看到这两条就说明配置没生效，去查第二节的 id 是否对得上。**

### 怎么改

**方式 1：profile 补丁（推荐，锁定）**

```yaml
- id: dsh-tag-memory
  config:
    dataDir: /your/path
```

改完要重启 DSH（配置只在启动时读）。

**方式 2：设置页搬家（不锁定时可用）**

设置页 → 数据目录 → 搬家。① ② 生效时按钮不给（给了也没用）。

**方式 3：环境变量（临时）**

```bash
DSH_TAG_MEMORY_DATA_DIR=/tmp/mem
```

## 五、装完必须做的校验

```bash
node 内部文档/工具/verify-install.mjs
```

输出示例（**有问题时**）：

```
=== verify-install：dsh-tag-memory 安装校验 ===
DSH_HOME:  C:\Users\Administrator\.dsh
profile:   C:\Users\Administrator\.dsh\profiles\web
插件包:    ...\node_modules\dsh-tag-memory

--- bundle 补丁 insert id ---
  · dsh-tag-memory
  · dsh-tag-memory-tools

--- profile 补丁覆盖 id（非 insert）---
  · tag-memory              ← 问题在这
  · tag-memory-preset

❌ 校验未通过：
  [PATCH_ID_MISMATCH] profile 补丁里有 2 个 id 在 bundle 补丁的 insert 里不存在
```

### 参数

| 参数 | 说明 |
|---|---|
| `--profile <dir>` | 指定 profile 目录（默认自动探测 `$DSH_HOME/profiles/{web,headless}`） |
| `--bundle <dir>` | 指定插件包目录（默认走 `profile/node_modules/dsh-tag-memory` 软链） |
| `--json` | 机器可读输出（CI 用） |

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 全部通过 |
| 1 | 发现问题（id 对不上 / 数据目录在包内 / 补丁解析失败） |
| 2 | 无法完成检查（找不到文件等） |

### 检查项

- ✅ bundle 补丁的 insert id 列表
- ✅ profile 补丁里所有 `- id: xxx`（非 insert 部分）
- ✅ **「profile 有、bundle 没有」且名字像本插件的 id** ← 本次事故的检查点
- ✅ `dataDir` 实际解析结果 + `source`
- ✅ 数据目录是否落在插件包内

- [ ] 启动日志零 `did not activate`、零 `patch: entry ... not found`

## 七、卸载与重装

```bash
# 卸载
plugin_manager { action: "remove_bundle", target: "dsh-tag-memory" }

# 重装
plugin_manager { action: "install_bundle", target: "dsh-tag-memory" }
```

**卸载/重装不会删数据目录**（数据在 `$DSH_HOME/tag-memory`，不在包内）。
但如果之前因为配置没生效、数据落在了 `<插件包>/data`，**卸载会把它一起删掉**。
卸载前先确认：

```bash
node 内部文档/工具/verify-install.mjs   # 看 dataDir 是否在包内
```

如果在包内，先把 `data/` 整个拷出来再卸载。

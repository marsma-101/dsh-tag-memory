# 开发流程（dsh-tag-memory）

> **不排时间，只定顺序和闸门。** 每一段做完、测过，才进下一段。
> 角色见《团队_子智能体说明.md》。总负责人 = Lead。

---

## 总览：六段流程

```
① 探明（Lead 独做，全员等）
      ↓ 产出「探明结论」
② 骨架 + 引擎（Lead 搭骨架 → E 做引擎）
      ↓ Q 测：引擎单测
③ 宿主 + 预设（H 做宿主方法 → P 接工具）
      ↓ Q 测：工具注册 + 落盘
④ 客户端（C 做 UI）
      ↓ Q 测：清单/语法 + 视觉（如实报告）
⑤ 集成联调（Lead 接线 → 全员修）
      ↓ Q 测：端到端
⑥ 安装交付 + 归档（Lead）
```

---

## ① 探明 — Lead 独做（其他人等结论）

**必须先做完这一段再动手写业务代码**，否则会在错误的 API 上盖房子。

| 要探明什么 | 怎么探 |
|---|---|
| Client-callable 宿主入口的确切写法 | `cordis_inspect_query` 查 `Service` / `Event` |
| storage / `ctx.sessionProjections` 用法 | 同上 |
| slot 有哪些、本插件该用哪个 | `Slots.listSubTree` |
| 工具注册的完整写法 | 读 `@deepseek-ai/dsh-tools` README |
| 预设 YAML 怎么声明子插件 | 读 `@deepseek-ai/dsh-agent-preset` README |

**产出**：一份「探明结论」写进 `待查证问题.md` 或单独文件。
**闸门**：结论没出来，**E/H/P/C 都不开始写代码**。

> 这一段是**唯一允许 Lead 直接看源码/查 API 的阶段**，后面遇到 API 疑问也报 Lead 统一查，避免各自摸索出不同结论。

## ② 骨架 + 引擎

### 2.1 Lead 先搭骨架（半天量级）

- `package.json`（`dsh.bundle.patch` / `dsh.client` / `exports` / `files` 白名单）
- `cordis.patch.yml`
- 空目录与占位文件：`lib/engine/`、`preset/`、`client.js`
- **不写业务逻辑**，只把结构立起来

**闸门**：骨架能被 `install_bundle` 装上（哪怕只是个空插件）。

### 2.2 E 做引擎（主力）

按顺序，**每完成一个就叫 Q 测**：

| 顺序 | 模块 | 交付后立即测什么 |
|---|---|---|
| 1 | `core.mjs` CSV 读写 | RFC4180：逗号/引号/换行/`""` 转义往返；标签 `|` 拆分合并 |
| 2 | `core.mjs` 编号 | `M-YYYYMMDD-NNN` 取号、当天序号、不重复 |
| 3 | `write.mjs` 校验 | 9 列校验、6 形态、≤20 标签、**含 `|` 拒写并点名** |
| 4 | `read.mjs` 打分 | 形态50/标签0~40/时距0~10；及格线40 |
| 5 | `read.mjs` 闸门 | 硬筛→命中否决→及格线**顺序不能反**；浏览模式不受否决限制 |
| 6 | `read.mjs` 隔离 | 项目/智能体两道与关系；`通用`/`引入`放行 |
| 7 | `tick.mjs` 时距 | 被召回才 +1，其余不动；上限 10 封顶 |
| 8 | `dict.mjs` | 字典加载 |

**闸门（本段总）**：所有引擎测试通过；**引擎不 import 任何 Cordis 东西**。

---

## ③ 宿主 + 预设

### 3.1 H 做宿主

| 顺序 | 内容 | 测试点 |
|---|---|---|
| 1 | 数据目录解析（4 级优先级） | 各级生效顺序；被锁定时能报明改哪一行 |
| 2 | `store/memory.csv` 落盘、`records/*.jsonl` 追加 | 追加不改旧行 |
| 3 | 宿主方法：列表 / 改条目 / 导出 / 备份 / 恢复 / 合并 | 与工具共用同一实现 |
| 4 | 会话身份投影 | 未绑定返回空/拒写；resume 后能恢复 |
| 5 | 定时任务 | `.unref()`，不阻塞进程 |

### 3.2 P 接工具

- 预设 YAML 声明
- 10 个 `dtm_*` 注册，**每个都调 engine 或宿主方法，不重复实现**
- 每轮注入：精简字典 + 身份状态

**闸门（本段总）**：
- 假 `ctx` 加载能检出 10 个工具全部注册
- 注入文本通过「精简但入口齐全」检查
- 未绑定时注入提示会问用户

---

## ④ 客户端

### C 做 UI

| 顺序 | 内容 | 测试点 |
|---|---|---|
| 1 | 入口 + 槽位注册 + 样式基线 | 控制台无 slot crash |
| 2 | 记忆条目页（表格、筛选、分页） | 表格能渲染出数据 |
| 3 | **条目编辑**（只开放 6 个字段） | 改项目/智能体能存回；`主要内容` 不可编辑 |
| 4 | 设置页 | 库位置、备份、自动整理、字典预览 |
| 5 | 导出 / 备份 / 恢复 / 合并弹窗 | — |

**闸门**：
- 只用 `--dsw-alias-*` token，明暗都可读
- 未 import 任何 Client 包、无 iframe
- **视觉验证如实报告**——没浏览器控制就说"视觉未验证"，不许造假

---

## ⑤ 集成联调

Lead 接线，全员待命修：

- UI 改条目 ↔ `dtm_retag` 走**同一个宿主方法**，结果一致
- 写入 → 读取 → 整理全链路通
- 未绑定场景：写入拒、读取空、注入提示问用户
- **Q 做端到端测试**

**闸门**：端到端全通；跨项目/跨身份查不到对方的记忆。

---

## ⑥ 安装交付 + 归档

- Lead 用 `install_bundle` 装进 profile 并用起来
- 检查 `locale/*` 的 `meta.title`/`meta.description`、`icon.svg`
- **`files` 白名单确认不含 `内部文档/`**
- Q 出最终报告（按官方 posture：验了什么、没验什么）
- Lead 归档：版本记录标 **v1.0.0**，PrivHub 同步

---

## 测试闸门总表（Q 的职责）

| 段 | 必须通过 | 备注 |
|---|---|---|
| ② | 引擎单测全绿 | **主力**，能脱离 DSH 跑 |
| ③ | 工具注册 + 落盘 | 假 `ctx` 冒烟 |
| ④ | 清单/语法 + 视觉如实报告 | 不许模拟 DOM |
| ⑤ | 端到端 | 含隔离验证 |
| ⑥ | 安装可用 | `install_bundle` 后能力真的可用 |

**Q 的纪律**：
- 只报问题，**不修业务代码**
- 发现问题写进报告，交回对应 owner
- **不许放宽断言来通过**
- 报告必须含「没验到的部分」

---

## 协作节奏

1. **接口先行**：E 先出引擎签名 → H/P 才能接；H 先出宿主方法签名 → C 才能接
2. **交付即叫测**：每完成一块立刻叫 Q，**不自测通过就宣布完成**
3. **不跨域改文件**：需要改别人范围先报 Lead
4. **争议上交**：设计分歧、要改说明文件，一律报 Lead
5. **旁见不动手**：看到可疑处写进报告，不顺手改

# 开发流程（dsh-tag-memory）

> **不排时间，只定顺序和闸门。** 每一段做完、测过，才进下一段。
> 角色见《团队_子智能体说明.md》。总负责人 = Lead。

---

## 总览：六段流程

```
① 探明（Lead 独做，全员等）
      ↓ 产出「探明结论」
② 骨架 + 引擎（Lead 搭骨架 → E 做引擎）
      ↓ Q 测：引擎单测
③ 宿主 + 预设（H 做宿主方法 → P 接工具）
      ↓ Q 测：工具注册 + 落盘
④ 客户端（C 做 UI）
      ↓ Q 测：清单/语法 + 视觉（如实报告）
⑤ 集成联调（Lead 接线 → 全员修）
      ↓ Q 测：端到端
⑥ 安装交付 + 归档（Lead）
```

## ① 探明 — Lead 独做（其他人等结论）

**必须先做完这一段再动手写业务代码**，否则会在错误的 API 上盖房子。

| 要探明什么 | 怎么探 |
|---|---|
| Client-callable 宿主入口的确切写法 | `cordis_inspect_query` 查 `Service` / `Event` |
| storage / `ctx.sessionProjections` 用法 | 同上 |
| slot 有哪些、本插件该用哪个 | `Slots.listSubTree` |
| 工具注册的完整写法 | 读 `@deepseek-ai/dsh-tools` README |
| 预设 YAML 怎么声明子插件 | 读 `@deepseek-ai/dsh-agent-preset` README |

**产出**：一份「探明结论」写进 `待查证问题.md` 或单独文件。
**闸门**：结论没出来，**E/H/P/C 都不开始写代码**。

> 这一段是**唯一允许 Lead 直接看源码/查 API 的阶段**，后面遇到 API 疑问也报 Lead 统一查，避免各自摸索出不同结论。

## ② 骨架 + 引擎

### 2.1 Lead 先搭骨架（半天量级）

- `package.json`（`dsh.bundle.patch` / `dsh.client` / `exports` / `files` 白名单）
- `cordis.patch.yml`
- 空目录与占位文件：`lib/engine/`、`preset/`、`client.js`
- **不写业务逻辑**，只把结构立起来

**闸门**：骨架能被 `install_bundle` 装上（哪怕只是个空插件）。

### 2.2 E 做引擎（主力）

按顺序，**每完成一个就叫 Q 测**：

| 顺序 | 模块 | 交付后立即测什么 |
|---|---|---|
| 1 | `core.mjs` CSV 读写 | RFC4180：逗号/引号/换行/`""` 转义往返；标签 `|` 拆分合并 |
| 2 | `core.mjs` 编号 | `M-YYYYMMDD-NNN` 取号、当天序号、不重复 |
| 3 | `write.mjs` 校验 | 9 列校验、6 形态、≤20 标签、**含 `|` 拒写并点名** |
| 4 | `read.mjs` 打分 | 形态50/标签0~40/时距0~10；及格线40 |
| 5 | `read.mjs` 闸门 | 硬筛→命中否决→及格线**顺序不能反**；浏览模式不受否决限制 |
| 6 | `read.mjs` 隔离 | 项目/智能体两道与关系；`通用`/`引入`放行 |
| 7 | `tick.mjs` 时距 | 被召回才 +1，其余不动；上限 10 封顶 |
| 8 | `dict.mjs` | 字典加载 |

**闸门（本段总）**：所有引擎测试通过；**引擎不 import 任何 Cordis 东西**。

## 实战教训（v1.0.0 开发期沉淀，全員遵守）

### 教训 1：判据必须先自证有效，再用来量东西

**案例**：验证 `setInterval` 是否真调了 `.unref()`，用 `process._getActiveHandles()` 过滤 `hasRef()` 结果为空 → 判通过。
**对照实验推翻**：Node v24 上该 API **连明确 `ref()` 的 timer 都不返回**，所以"列表为空"**恒真**，无论代码有没有 `unref`。

**教训**：
- **恒绿判据比没有判据更危险**——它给出虚假的确定性
- 有效判据的特征：**断言具体的期望值**（有反例就会挂）
- 危险判据的特征：**用"没发现问题"证明"没问题"**（列表为空 / 无报错 / 无异常）
- 做法：**先做对照组证明尺子准，再量被测对象**；把"判据有效性自检"作为测试的第一条断言

> **硬性纪律（2026-11-05 定）**：**任何声称"验证通过"的判据，必须先构造反例确认它能判失败。**
> 做不到这一点，该判据的结论**不得用于交付**。
>
> 具体操作：写判据时**同时写一个"应该失败"的对照组**，跑一遍确认它真的失败——尺子先量一个已知长度，才可信。
> 已落地的样板：`tests/gate3/timer.test.mjs` 的第一条用例就是判据自检
> （先证明 `hasRef()` 能区分 ref/unref，再用它量被测对象）。将来 Node 改行为，这条会失败提醒，不会悄悄变绿。

### 教训 2：跨模块最容易漂移的不是逻辑，是字段名

**案例**：宿主 descriptor 写 `request`，客户端 spec 写 `payload` → 装上后 `gateway/arguments-invalid: missing "request"`，**整个编辑功能不可用**。
**双方自测都发现不了**：客户端假宿主照自己 spec 造（自洽）；宿主自测直接调服务方法（绕过 wire 层字段名匹配）。

**教训**：
- **必须有一道跨模块契约测试**：逐方法比对"客户端参数名 ↔ 宿主参数名"，双向断言 + 打印计数
- 同类检查还要覆盖：endpoint 名三方一致、descriptor 必填字段齐备
- **服务端与客户端各自的自测通过，不等于能对接**

### 教训 3：脚本化改源码后必须立刻 `--check`

**案例**：用 `node -e` + 正则批量把 15 处 `return {...}` 改成 `return reject(...)`，改出两处语法错误（少括号、`}` 被误换成 `)`），交付给 qa 后直接报"加载不了"。

**教训**：
- **禁止在交付前对源码做批量正则替换**
- 任何脚本化改源码 → **立刻 `node --check`**，通过才算改完
- 批量改写后要**人工抽查 diff**，不只依赖测试

### 教训 4：检查脚本必须打印计数，"没报错"不等于 PASS

**案例**：用 `Compare-Object` 比对方法名，正则写错导致一边是空数组，PowerShell 因 null 参数报错但被吞 → 输出看起来像 PASS，实际只提取到 4 个。
**另**：`$Host` 撞 PowerShell 保留变量，赋值静默失败。

**教训**：
- 检查脚本**必须打印提取到的计数**（`spec=10 api=10 lazy=10`），不能只看"没报错"
- 断言里先检查"提取到非空"，再比对内容
- 关键数据比对**用 node 跑，不用 PowerShell 做**
- PowerShell 里避免 `$Host` / `$Matches` 等保留名

### 教训 5：视觉验证不可替代，也不可伪造

**全程状态**：`http://127.0.0.1:3080` 返回 **401**，无浏览器控制。
**全程处置**：4 条视觉用例一律 **SKIP**，报告每次都写"视觉未验证"，**不用任何间接证据冒充**。

**教训**：
- 语法正确、manifest 合法、slot 注册成功、spec 验证通过 —— **都不能证明"用户看到了界面"**
- 不做：另起浏览器、找 token、改 HOME、翻浏览器配置、模拟 React/DOM、mock 截图、找光栅化工具
- **装了不等于用户看到了** —— `install_bundle` 成功也只证明"装上了"

### 教训 6：假环境验业务逻辑，验不了框架契约

**案例**：全部 177 条测试通过（引擎 101、工具+落盘 54、清单/契约 22），
装进真容器后**暴露 3 个缺陷**，其中 2 个是致命的：

1. `preset/index.js` 导出 `export const Config = {}`（空对象）→ **整个插件行激活失败**。
   `cordis` 的 `resolveConfig` 是 `if (!runtime.Config) return config; runtime.Config['~standard'].validate(config)`——
   空对象过了第一道判断但没有 `~standard`，直接抛 TypeError。
2. `bindIdentity` 只返回结果不存储 → `identityOf` 恒为 null → **所有写入被拒**。
   投影依赖 `tool/call` / `command/run` 事件；宿主方法被直接调用时投影恒空。
3. `writeEntry` / `recall` 不自动填当前绑定值 → engine 判 `PROJECT_EMPTY`；`recall` 漏兜底 `项目` 导致硬筛用空串匹配、`filtered` 归零。

**为什么测试全绿也发现不了**：假 `ctx` 绕过了框架的 `resolveConfig`、模块解析、Remote 挂载。
**这些被"绕过"的东西，恰恰是真实环境里最先崩的地方。**

**教训**：
- **假 `ctx` / 本地复刻能验业务逻辑，验不了框架契约**
- 框架契约清单（每项都必须在真环境验）：`Config` schema 校验、模块解析（依赖从哪来）、
  插件激活与生命周期、Remote namespace 挂载、slot 注册
- 报告里必须区分「**本地测试通过**」和「**真装验证通过**」，不能混用
- **安装一次的成本，远低于在错误假设上继续开发**

> 这条与教训 1（判据必须先自证有效）同源：都是「**用间接证据代替直接证据**」。

#### ⚠️ 必须区分两类缺陷（不说清这个，教训 6 会被误用成借口）

初次复盘时我把 4 个缺陷都归为"环境限制"。**这个归因是错的，会放过真正的问题。**

| 缺陷 | 真实类别 | 本地为什么没测出 |
|---|---|---|
| `Config = {}` 触发 resolveConfig TypeError | **框架契约** | 本地没有 `resolveConfig` 这一步，**真的测不出** |
| `bindIdentity` 不存储 | **实现缺口 + 用例缺口** | 假 ctx 的 `stateOf` 直接返回设好的值，**从未模拟"投影还没吃到事件"的时序** |
| `recall` 漏兜 `项目` | **实现缺口 + 用例缺口** | 自测**显式传了** 项目，从没测"省略"路径 |
| `read.jsonl` 的 `cond` 记原始 query | **实现缺口 + 用例缺口** | 同"省略路径"没覆盖 |

**结论**：
- 只有 **`Config = {}`** 是真正的"本地测不出"（框架契约）
- **其余三个本地完全能测出来**，只要用例覆盖「模型会省略参数」和「事件可能还没进投影」——
  那是**测试设计缺陷**，不是环境局限

**因此自查清单必须分两条**：

1. **框架契约类**（`Config` schema、模块解析、插件激活与生命周期、Remote 挂载、slot 注册）
   → 本地测试**一律不算验过**，必须标注「需真装验证」
2. **调用形态类**（参数省略、时序竞态、异常路径、默认值兜底）
   → **本地必须覆盖**；没覆盖就是测试设计缺陷，**不许归因于环境**

> **把用例缺口说成环境限制，是最容易自我原谅的偷懒。**
### 教训 7：**把"读不到"伪装成"没有"** —— 本次 5 个缺陷的共同模式

真容器安装暴露的 5 个缺陷，表面各不相同，**根因是同一个模式**：

| # | 缺陷 | 伪装成了什么 |
|---|---|---|
| ① | `export const Config = {}` | 把"配置契约不满足"伪装成"没有配置" |
| ② | `bindIdentity` 只返回不存储 | 把"绑定没生效"伪装成"绑定成功（ok:true）" |
| ③ | `recall` 漏兜 `项目` | 把"筛不到"伪装成"库里没有（filtered=0）" |
| ④ | `read.jsonl` 的 `cond` 记原始 query | 把"用了绑定值查"伪装成"没传条件" |
| ⑤ | `listEntries`/`getOverview` 丢弃 `errors` | 把"读不出（格式不兼容）"伪装成"空库（total:0）" |

**共同点：错误路径返回了"看起来正常的空值"，调用方无法区分「真的没有」和「读不到」。**

**危害**：用户/模型会做出相反的决定。
- ⑤ 最典型：库格式不兼容时显示"0 条"，用户会以为**记忆丢了**或**插件坏了**，
  而真相是需要处理格式——**这两种情况该做的事完全相反**。

**检查清单（写代码时逐条自问）**：

1. 这个返回值里，`0` / `空数组` / `null` / `ok:true` 是否可能来自**失败路径**？
2. 调用方拿到它，能不能区分「真的没有」和「出错但没报」？
3. 上游返回的 `errors` 我是不是**直接丢弃**了？
4. 有没有把"未生效"当成"成功"返回（如 `ok:true` 但实际没写）？
5. **错误信息够不够让调用方决定下一步**（说清"是什么问题、该怎么处理"）？

**正确做法**：
- 失败就 `ok:false` + 明确错误码 + **可直接展示的中文整句**
- 保留非致命错误（单行损坏）在 `errors` 里，数据照常返回，让 UI 能提示
- **绝不把致命错误降级成空值**

> 这条是教训 6 的具体化：**能区分「没有」和「读不到」，是接口的基本责任。**
### 教训 8：**必须用无头浏览器实测，不能靠推测**

**背景**：Remote 通道调试耗了 4 轮，每轮都是"读源码猜 API → 部署 → 用户报错 → 再猜"。
直到用 CDP 驱动无头 Edge 才一次性拿到全部真实错误，3 个缺陷一次定位。

**为什么必须上无头浏览器**：
- **报错信息只在运行时出现**，而且会**逐步引导**（`has no prototype method` → `must use unique identifier parameters` → `expected 0 argument(s)`）
- 静态检查、假 ctx、单元测试**全部看不到**这些
- 用户的截图有用，但**我看不到控制台原始报错**

**做法（本项目已验证可行，零依赖）**：
1. 本机已有 Edge：`C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe`
2. `--headless=new --remote-debugging-port=9333 --user-data-dir=<临时目录>`
3. 自实现最小 WebSocket 客户端（约 80 行，不用装 puppeteer）
4. 用 CDP 命令：
   - `Runtime.enable` + `Runtime.consoleAPICalled` / `Runtime.exceptionThrown` 抓控制台
   - `Network.enable` + `requestWillBeSent` / `responseReceived` 抓请求与状态码
   - `Runtime.evaluate` 读 DOM 文本、点按钮、检查元素
5. 验证完 **必须** `Stop-Process msedge` 并清理 `--user-data-dir`（否则 git add 会因文件锁失败）

**验证脚本要做的检查**：
- 页面有无错误框（正则匹配错误关键词）
- 表格表头与首行数据
- 分页器文案（能反映真实条目数）
- 只读字段是否真的没有可写控件
- 控制台异常

> **不要再用「读源码推断 API」代替「跑起来看」**。前者适合理解机制，后者才是验收。

# 整理/合并：用新会话启动的方案

**日期**：2026-11-16
**决策**：用户提议「开一个新对话来启动整理/合并」，采纳。
**为什么这个方案最好**：它把「模型参与整理」这件事，从「插件要会调模型」变成「模型在干净会话里自己干活」。

---

## 一、为什么新会话方案优于其他三条路

之前列过三条路（模型主动调 prepare/commit、插件反向调模型、子智能体）。用户提的新会话方案**同时避开了三者的缺点**：

| 方案 | 需要的宿主能力 | 缺点 |
|---|---|---|
| 甲：prepare/commit 两工具 | 无 | 仍在本会话里做，上下文被日常对话污染；且要模型自己记着分两步 |
| 乙：插件反向调模型 | **需要 DSH 提供反向 LLM 通道**（现状未知） | 依赖未验证的能力 |
| 丙：子智能体 | 需要 spawn 能力 | 复杂度高 |
| **丁：新会话（采纳）** | **无** | 需要用户手动开一次 |

**关键洞察**：整理/合并是**低频、重量级、需要专注**的任务。它本来就该在一个干净的上下文里做，
而不是混在日常对话里。新会话不是妥协，是**符合任务性质的正确形态**。

### 1.1 技术上为什么可行（已核实）

| 要素 | 现状 | 结论 |
|---|---|---|
| 插件能否创建会话 | 不能（`inject` 只有 `tools`/`systemPrompt`，只用 `ctx.sessionProjections` 读） | **不需要**——用户手动开 |
| 提示词能否按会话区分 | 能。`ctx.systemPrompt.section({ text: () => ... })` 的 `text` 是**函数** | ✅ 可按会话动态返回 |
| 工具能否按会话过滤 | 能。`ctx.tools.register` 支持 `available` 回调 | ✅ |
| 插件能否知道「当前是哪个会话」 | 能。`identityOfSync(agent)` 已用 `projections.stateOf(session, KEY)` | ✅ 可打标记 |

**所以：插件只需要「识别出这是一个整理会话」，然后注入对应的提示词与工具集。**
不需要创建会话，不需要调模型。

## 二、设计：会话角色（Session Role）

### 2.1 核心概念：给会话打一个「角色」标记

引入一个轻量概念——**会话角色**（`role`）：

| 角色 | 何时进入 | 注入什么 |
|---|---|---|
| `daily`（默认） | 普通对话 | 现有压缩版提示词 + 10 个工具 |
| `tidy` | 用户从 UI/工具发起整理 | **整理专用提示词** + 整理相关工具 |
| `merge` | 用户从 UI/工具发起合并 | **合并专用提示词** + 合并相关工具 |

### 2.2 角色怎么确定（三种方式，推荐第一种）

**方式 A：会话启动参数（推荐）**

用户点「整理记忆库」按钮 → DSH 新开一个会话 → 会话的第一条消息是插件生成的
「整理任务说明」，里面带一个结构化标记：

```
【dsh-tag-memory 整理任务】
role: tidy
batchId: tidy-20261116-183000
候选: 12 条（编号见下）
来源: 空标签 / 噪声标签 / 疑似重复
---
M-20261011-003
M-20261012-007
...
```

插件通过 `ctx.sessionProjections` 读这条消息（或读会话的 `metadata`）判断角色。

**方式 B：会话名/slug 约定**（备选）

新会话的 slug 里带 `tidy-` 前缀。简单但不牢靠（用户能改）。

**方式 C：显式工具调用**（兜底）

用户在新会话里调 `dtm_tidy`（无参数）→ 插件据此把该会话标记为 `tidy` 角色。

**推荐 A + C 组合**：A 用于自动识别，C 用于用户手动进入。

### 2.3 提示词按角色注入

现在的 `renderInjection()` 是单一的。改成：

```js
text: () => {
  const role = roleOf(ctx);              // 从 session 读角色
  if (role === 'tidy')  return renderTidyInjection({ ... });
  if (role === 'merge') return renderMergeInjection({ ... });
  return renderInjection({ ... });       // 现有的日常版
}
```

**三个版本的差异**：

| 内容 | daily | tidy | merge |
|---|---|---|---|
| 工具入口表 | 10 个全列 | 只列整理用到的 | 只列合并用到的 |
| 写入判据 | 压缩版 | **完整版**（含 principles） | **完整版** |
| 自由标签规则 | 「见被拒提示」 | **完整展开**（含区分度要求） | **完整展开** |
| 标签网络 | 存在性一句话 | **全量**（整理要看全库标签） | **全量** |
| 本批任务 | 无 | **候选条目清单** | **来源文件 + 格式说明** |
| 输出契约 | 无 | **结构化产出格式** | **结构化产出格式** |

**token 预算**：tidy/merge 会话是重量级的，注入 3000~5000 tokens 可以接受（日常版才需要抠到 1400）。

### 2.4 工具按角色过滤

```js
ctx.tools.register(def, {
  available: (agent) => {
    const role = roleOf(agent);
    if (role === 'tidy')  return TIDY_TOOLS.has(def.name);
    if (role === 'merge') return MERGE_TOOLS.has(def.name);
    return true;   // daily 全部可见
  }
});
```

| 角色 | 工具 |
|---|---|
| `tidy` | `dtm_review` `dtm_retag` `dtm_supersede` `dtm_archive` `dtm_write` `dtm_records` |
| `merge` | `dtm_merge_prepare` `dtm_merge_commit` `dtm_write` `dtm_records` |

**注意**：`dtm_recall` / `dtm_bind` 在 tidy/merge 里**不需要**（整理不看召回，身份由任务指定）。

## 三、合并：两阶段工具（配合新会话）

即使用新会话，合并仍要分两步——因为模型判完要让程序校验：

### 3.1 `dtm_merge_prepare`（阶段一）

```
输入：path（任意格式的记忆文件）
输出：{
  format: 'csv' | 'markdown' | 'json' | 'text',
  parsed: 154,                 // 解析出多少条候选
  batchId: 'merge-20261116-...',
  candidates: [                // 交给模型逐条判断
    { seq: 1, raw: '原始内容…', meta: { 项目, 智能体, 来源 } },
    ...
  ],
  note: '按纯文本切块，可能不准'   // 非精确格式时如实告知
}
```

**程序只做解析，不做判断。** 模型拿到 `candidates` 后，按合并专用提示词逐条产出：

```json
[
  { "seq": 1, "主要内容": "…", "形态": "技能", "自由标签": ["…"] },
  ...
]
```

### 3.2 `dtm_merge_commit`（阶段二）

```
输入：batchId + 模型产出的结构化数组
程序：① 逐条 validateWriteInput（复用写入规则）
     ② isUsefulTag 检查标签质量
     ③ checkTagDistinctiveness 检查区分度
     ④ 项目/智能体 从 meta 原样复制（用户要求）
     ⑤ 编号去重 + 备份 + 原子写入 + 台账
输出：{ added, changed, conflicts, rejected: [...], backupPath }
```

**`rejected` 是关键**：模型判错的条目**不静默丢弃**，而是带着原因返回，让模型（或用户）决定补还是弃。

### 3.3 为什么不用「模型一次全判完」

- 154 条 × 每条几十字 = 上万 token，一次判完超出可靠区间
- 分批（默认 20 条）可以**部分成功**：某一批模型判错了，其他批照常入库
- 每批独立校验，坏批跳过并报告

## 四、整理：同样是新会话 + 两阶段

### 4.1 `dtm_tidy_prepare`

```
程序选候选（纯规则，不判语义）：
  · 空标签条目
  · 标签全是噪声（纯数字 / 单字 / 来源标记）
  · 形态为空
  · 疑似重复（主要内容 Jaccard 相似度 > 0.9，只报组不判合并）

输出：{ batchId, candidates: [...], stats: {...} }
```

### 4.2 模型在新会话里判断

模型看到候选 + 全量标签网络 + 完整写入规则，产出：

```json
[
  { "编号": "M-...", "动作": "retag", "形态": "技能", "自由标签": ["…"] },
  { "编号": "M-...", "动作": "merge", "into": "M-...", "理由": "…" },
  { "编号": "M-...", "动作": "archive", "理由": "…" },
  { "编号": "M-...", "动作": "skip", "理由": "无需改动" }
]
```

### 4.3 `dtm_tidy_commit`

程序校验 → 生成改动提案 → **返回给模型/UI 展示** → 用户确认 → 落库。

**整理必须比合并多一道确认**：
- 合并是**追加**新数据，出错有备份可回滚，风险低
- 整理是**改动**已有数据，模型判错就是破坏，风险高

## 五、提示词设计（这是用户最关心的）

### 5.1 合并专用提示词（核心段落）

```markdown
## 记忆合并任务

你在把一个**外来记忆文件**并入当前记忆库。这不是简单搬运——每条都要按
**写入规则重新表达**。

### 你必须做的三件事

1. **读懂内容**：不管来源是什么格式（CSV / Markdown / JSON / 纯文本），
   先理解这条记忆到底在讲什么。一条只记一件事；如果原文混了几件事，
   **拆成多条**。

2. **判形态**（6 选 1）：
   单件事怎么做→`技能`；多件事次序→`流程`；必须/禁止→`规则`；
   喜欢/倾向→`偏好`；客观陈述→`事实`；可复用格式/清单→`模板`。
   判据是「**将来怎么找它**」，不是「它长什么样」。

3. **打自由标签**（1~20 个离散实词，不含 `|`）：
   - 从三个方向拆：**内容关键词 / 作用 / 注意事项**
   - **尽量详细，并尽量与其他条目区分开**——这是本任务的重点要求。
     库里已有的通用词（如「dsh」「通用」「推断」）人人都在用，
     你要让这条**能被单独找到**，就得给它**独有**的词。
   - 下面会给你**现有标签网络**（全库标签及共现），
     看一眼就知道哪些词已经被用滥了。

### 你不能改的字段

- `项目` / `智能体`：**原样复制来源里的值**，不要重新推断、不要映射。
  来源里为空 → 用 `引入`（如实记录归属未知）。
- `稳定性`：一律 `观察`（首次落库规矩，不自称稳定）。
- `时距`：一律 `1`（写入初值）。
- `状态`：一律 `生效`。

### 输出格式

严格输出 JSON 数组，每条对应一个候选序号：
```json
[{ "seq": 1, "主要内容": "...", "形态": "技能", "自由标签": ["...","..."] }]
```
不要输出任何解释文字。
```

### 5.2 整理专用提示词（核心段落）

```markdown
## 记忆整理任务

你在整理现有记忆库。候选条目**已经由程序挑出来**（空标签/噪声标签/疑似重复），
你的任务是逐条判断该怎么处理。

### 可用的动作

| 动作 | 什么时候用 | 必填 |
|---|---|---|
| `retag` | 标签不合格，但内容有价值 | 形态、自由标签 |
| `merge` | 这条与另一条讲的是同一件事 | into（目标编号）、理由 |
| `archive` | 内容已失效/过时 | 理由 |
| `skip` | 无需改动 | 理由 |

### 判断要点

- **空标签的条目**：读内容，按写入规则补形态和标签。补不出合格标签的，
  说明这条本身可能不该存在 → `archive`。
- **疑似重复**：**必须真的读完两条**再判。只有内容确实讲同一件事才 `merge`；
  只是主题相近（比如都是讲 npm 发布）**不算重复**，保持独立。
- **标签噪声**：纯数字、单字、来源标记（如「原话」「推断」）不是有效标签，
  换成有检索价值的实词。

### 输出格式

严格输出 JSON 数组：
```json
[{ "编号": "M-...", "动作": "retag", "形态": "技能", "自由标签": ["..."], "理由": "..." }]
```
```

### 5.3 「区分度」怎么真正落地（用户重点要求）

用户要求「自由标签尽量详细、尽量跟其他条目区分」。**只在提示词里说不够**，要三管齐下：

| 层次 | 手段 |
|---|---|
| **提示词** | 明确要求 + 给出「通用词已被用滥」的事实（附标签频次） |
| **输入** | 把**现有标签网络 + 高频词列表**喂给模型，让它知道该避开什么 |
| **程序校验** | `checkTagDistinctiveness()` 算 Jaccard 相似度，超阈值**提示**（不拒绝） |

**标签频次表**是这里的关键增量。现有 `vocab.mjs` 已经能算频次，直接把
「出现 >10 次的词」列给模型，告诉它「这些是泛词，别指望靠它们被找到」。

## 六、实施顺序

| 步 | 内容 | 依赖 | 优先级 |
|---|---|---|---|
| **1** | 会话角色机制：识别 `tidy`/`merge` 会话 | 无 | 高 |
| **2** | 三版提示词：`renderTidyInjection` / `renderMergeInjection` | 1 | 高 |
| **3** | 工具按角色过滤（`available` 回调） | 1 | 高 |
| **4** | 格式解析：`normalizeSourceRecords()`（CSV/MD/JSON/文本） | 无 | 高 |
| **5** | `dtm_merge_prepare` / `dtm_merge_commit` | 4 | 高 |
| **6** | `checkTagDistinctiveness()` + 标签频次注入 | 无 | 中 |
| **7** | `dtm_tidy_prepare` / `dtm_tidy_commit` | 1,2 | 中 |
| **8** | UI：「开始整理」「导入记忆文件」两个按钮 | 1 | 中 |

**1、2、3 是骨架**，先做能立刻看到效果（新会话的注入内容明显不同）。
**4、5 是用户最痛的点**（现在只能合并自家 CSV）。

## 七、验收

| # | 项 | 判据 |
|---|---|---|
| V1 | 日常会话不受影响 | 注入内容与现在**逐字节相同**（回归） |
| V2 | tidy 会话注入不同 | 包含候选清单 + 完整写入规则 + 全量标签网络 |
| V3 | merge 会话注入不同 | 包含格式说明 + 输出契约 |
| V4 | 工具过滤生效 | tidy 会话里看不到 `dtm_recall` |
| V5 | 合并 Markdown | 一个 `.md` 文件能解析出正确条数，标签由模型新生成 |
| V6 | 合并 CSV | 自家格式仍能合（回归） |
| V7 | 项目/智能体原样复制 | 来源是什么，落地就是什么（不映射） |
| V8 | 空归属兜底 | 来源为空 → `引入`，且报告里点名 |
| V9 | 模型产出不合规被拦 | 形态非法/标签为空 → 进 `rejected`，不静默入库 |
| V10 | 区分度提示 | 造两条标签 100% 重合，能报出来 |

**负对照**：
- 去掉角色判断 → V2/V3 变红（注入退回日常版）
- 去掉 `validateWriteInput` → V9 变红

## 八、需要确认的一点

**新会话由谁开？**

| 选项 | 做法 | 我的判断 |
|---|---|---|
| **A：UI 按钮**（推荐） | 插件在设置页加「开始整理」「导入记忆文件」按钮，点了新开会话并带上任务说明 | 用户主动、可见、符合「改库要人知情」 |
| B：工具让模型开 | 模型调 `dtm_tidy_prepare` 后，提示用户「请新开一个会话」 | 多一步，但不需要 UI 改动 |

**推荐 A**，B 作为过渡。

## 九、不在本次范围

| 项 | 理由 |
|---|---|
| 插件自动创建会话 | 需要宿主能力，且违背「改库要人知情」 |
| SQLite 直读 | 零依赖硬约束 |
| 定时自动整理 | 同上，改库不宜无人值守 |
| 跨库语义去重 | 先做单库内 |

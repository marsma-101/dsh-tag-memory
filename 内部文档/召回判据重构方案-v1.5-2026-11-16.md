# 召回判据重构方案（v1.5）

**问题**：见《审计报告2》L1-1/L2-1。`e_ratio = |命中| / |条目标签数| > 0.3` 把「写入侧自由决定的标签数」变成了召回的硬性除数，导致 `n < 3.33k` 之外的条目**数学上永远召不回**。

**本文件锁定的口径**：改什么、为什么、实测依据、验收标准。改代码前先对齐这里。

---

## 一、核心改动：否决条件从「条目侧比例」换成「查询侧覆盖率」

### 1.1 改动内容

```
旧：
  闸门②否决  =  (|命中| / |条目标签| > entryRatio=0.3)  AND  (|命中| / |查询标签| >= queryFloor=0.15)
                                                                                    ↑ 分母是写入自由度
新：
  闸门②否决  =  |命中| >= minHit (=1)  AND  (|命中| / |查询标签| >= queryFloor=0.5)
                ↑ 绝对数，与条目标签数无关        ↑ 分母是查询词数，模型可控
```

**关键点**：`entryRatio` 这个配置项**彻底删除**，不是改数值。理由：

- 只要它存在，分母就是条目标签数，死区就存在
- `queryFloor >= 0.5` 已隐含「零命中必被拒」（`hit=0 → q_ratio=0 < 0.5`），`minHit` 是冗余但**显式**的表达
- 穷举验证：1~5 个查询词 × 0~5 个命中，`queryFloor=0.5` 单独与两者并联**完全等价**

### 1.2 为什么 queryFloor 从 0.15 提到 0.5

`queryFloor` 现在是**唯一的实质判据**，必须承担筛选职责。

- 0.15 的语义是「查询词命中 15% 就算方向对」——太松，取消 entryRatio 后会放大量噪音
- 0.5 的语义是「**查询词至少命中一半**」——符合直觉，模型也能据此自我修正（"我给的词太多了，收窄一点"）

**实测**：`queryFloor=0.5` 时零交集噪音 **0 条**（因为零交集必然 `q_ratio=0 < 0.5`）。

### 1.3 权重与及格线：让两个因子都不能单独及格

```
旧：形态 50 + 标签 40 + 时距 10 = 100，passLine 40
    → 形态命中就 50 分，单独过及格线 → 标签质量对筛选毫无作用

新：形态 30 + 标签 60 + 时距 10 = 100，passLine 45
    → 形态单独 30 < 45（不能单过）
    → 标签满分 60，但 q_ratio=0.5 时只有 30 分，加形态 30 = 60 > 45（需两者配合）
    → 标签质量真正参与筛选
```

**为什么是 30/60 而不是 25/65 或 40/50**：

| 档位 | 形态单独能否及格 | 真实查询命中 | 形态错时仍召回 |
|---|---|---|---|
| 50/40 + 40 | **能（50>40）** ← 职责倒挂 | 17 有效 | 92% |
| 40/50 + 55 | 不能 | 16 | **0%** ← 形态变硬门 |
| 35/55 + 50 | 不能 | 17 | 92% |
| **30/60 + 45** | **不能** | **17** | **95%** |
| 25/65 + 45 | 不能 | 17 | **99%** |

30/60 + 45 是「结构正确（形态不可单过）+ 召回不降 + 形态不硬化」三者的平衡点。
25/65 的形态错召回更好（99%），但形态权重过低会让"形态"这个维度近乎失效，不符合设计意图。

## 二、连带必须改的三处

### 2.1 浏览模式（`自由标签` 留空）

**问题**：新权重下形态分只有 30 < 45，浏览模式（跳过否决、只走及格线）会**全部返回空**。实测确认：6 个形态全部返回 0 条。

**改法**：浏览模式**跳过及格线**，只做硬筛 + 按形态过滤 + topK 截断。

理由：浏览的语义是"把这一形态的都给我看看"，不是"找最相关的"。及格线是用来筛相关性的，浏览没有相关性可筛。

```
if (browseMode) {
  // 不做否决、不做及格线：只按硬筛 + 形态 + topK
  候选 = screened.filter(形态匹配).sort(按时距降序, 编号降序).slice(0, topK)
}
```

**排序依据**：浏览没有查询词，无法算相关性分数。按时距降序（被用过多的先看）+ 编号降序（新的先看）——这是确定性排序，不引入新概念。

### 2.2 `near` 的语义要跟着变

**问题**：`near` 现在的核心字段是 `gap`（还差几个标签才能过 `e_ratio`），而 `e_ratio` 没了，`gap` 失去意义。

**改法**：`gap` 改为「还差几个查询词才能过 `queryFloor`」：

```
needHits = ceil(queryFloor * |queryTags|)     // 需要命中几个查询词
gap      = max(1, needHits - |命中|)          // 还差几个
```

同时 `near` 的 `reason` 取值从 `ENTRY_RATIO` / `QUERY_FLOOR` 改为：
- `QUERY_FLOOR`：命中数不够（唯一会出现的否决原因）
- `BELOW_PASS_LINE`：过了否决但分数不够
- `OTHER`

`ENTRY_RATIO` 这个 reason 值删除。

### 2.3 `QUERY_OFF_DIRECTION` 的判定条件

现在是 `maxQ < queryFloor`。`queryFloor` 提到 0.5 后，这个条件仍然成立且更有意义：
"全库没有任何条目能命中你一半的查询词" → 确实是你给的词方向不对。

保持不变，但阈值随配置走（已经是 `queryFloor` 变量，无需改代码）。

### 3.1 标签数分档召回率（旧判据死锁的直接证据）

固定用 2 个查询词查条目自己（正确答案已知），按条目标签数分档：

| 标签数 | 改后召回率 |
|---|---|
| 1–3 个 | 100% |
| 4–6 个 | 100% |
| 7–10 个 | 100% |
| 11+ 个 | 100% |

改前 7–10 档会明显掉（`e_ratio = 2/n`，n≥7 时 < 0.3 被否决）。**现在标签数不再是召回的决定因素**，死锁解除。

### 3.2 剩下 6 次查空的归因（重要：不是判据问题）

改后 26 次真实查询里仍有 6 次查空。逐条查了原因：

| 查询 | 归因 |
|---|---|
| 规则 [改源码,生产环境] | 该形态下**零命中** —— 库里真的没有这些词 |
| 事实 [前端,原型,导航] | 零命中 |
| 规则 [通用] | 零命中（「通用」是项目值不是标签） |
| 事实 [坑,排查] | 零命中 |
| 技能 [github,issue,凭据] | 零命中 |
| 规则 [规矩,兜底,测试] | **命中 1/3 = 0.333 < 0.5** —— 查询词太多太散 |

**5 次是真的没有，1 次是查询词太散。** 这不是判据太严，而是**模型的用词与库内标签不重合**（标签词汇漂移问题），属于下一批（见 §六）。判据已经不该再放宽——再放宽就会引入误召回。

### 实施中发现的额外问题（原计划没预见到）

**浏览模式跳过及格线会连带丢掉形态过滤。** 旧版靠「形态不命中 → 0 分 → 不过及格线」
实现「浏览技能就只出技能」。跳过及格线后这层过滤消失了，浏览「技能」会把「规则」「事实」全带出来。

实测当场踩到：改完 F8a/F8c 两条测试立刻变红，输出里多出了 `M-20261105-004`（形态=规则）。

**修正方式**：在浏览分支里**显式按形态过滤**，不是加兜底。这是把「原本隐含在分数里的约束」
改成「显式约束」——语义更清楚，也不再依赖权重数值。已加注释说明，防止后人又改回去。

## 五、验收标准（硬要求）

### 5.1 实施结果（已全部通过）

| # | 验收项 | 判据 | 实测 |

| V1 | 自查询召回率 | k=1 ≥ 85%，k=2/k=3 = 100% | **88% / 100% / 100%** ✅ |

| V6 | 归属隔离不变 | 跨项目/跨身份完全不可见 | **泄漏 0 条** ✅ |

### 5.2 负对照（证明测试真的会红，不是摆设）

| 破坏方式 | 预期 | 实测 |
|---|---|---|
| 把 `entryRatio: 0.3` 加回 scoring.json | H1 变红 | ✅ `not ok 1 - H1 ... entryRatio 已不存在` |
| 权重调回 50/40 + passLine 40 | I2 变红 + `loadScoring` 抛错 | ✅ 抛错原文：`打分参数非法：任一单项都不得单独越过及格线，但 形态分(50) >= 及格线(40)...` |

第二条尤其重要：**配置坏掉时是当场抛错，不是静默接受**。旧版没有这个校验，所以「形态分 50 > 及格线 40」这个职责倒挂一直没被发现。

### 5.3 测试必须走真实链路（不许构造）

- **禁止**在测试里手搓 `{ 编号, 分 }` 形状的 near（这是 L3-1 的教训）
- **禁止**用「条目自己的标签查自己」当唯一验收（这是 `probe-recall` 报 97% 而真实 27% 的原因）
- 新探针必须**回放会话日志里真实发生过的查询**

**已落实**：`scripts/probe-recall.mjs` 重写，现在四段：
1. **真实查询回放**（主口径）—— 从 `$DSH_HOME/sessions/*.zstd` 解出历史上真实的 `dtm_recall` 调用逐条重放
2. 自查询基准（回归基线，明确标注「不是真实召回率」）
3. 隔离检查
4. **标签数分档检查**（专测旧判据的死锁有没有复发）

`E5` 满分测试也改了：旧版直接构造 `时距: 32`（当时 `tickCap=10`，这个值不可达），
现在改为**用 `applyTick` 从初值 1 一路加到配置声明的封顶值**再算分。
如果 `tickCap` 与 `tickMaxScore` 再次错配，这条会立刻变红，而不是被构造输入盖住。

## 六、不在本次范围（下一批）

| 项 | 理由 |
|---|---|
| **标签词汇漂移**（新发现，优先级已升到最高） | §3.2 实测：剩下 6 次查空里 5 次是「查询词在库里零命中」。这不是召回判据的问题，是**模型临时想的词与库内标签对不上**。需要靠写入时的词汇约束 + 等价表扩充来解决，属于写侧改动。 |
| 读侧「该回忆提醒」（L1-B/L2-3） | 独立改动，需要新的事件钩子，与判据无关 |
| feedback 回写通道（L2-2） | 独立改动，需要 `read.jsonl` 格式变更 |
| 生命周期三态（L1-C） | 依赖 feedback 通道，先做会分不清「没被需要」和「想找没找到」 |
| near 序列化修复（L3-1） | 独立，可与本批并行，但不在同一提交 |
| `isUsefulTag` 未被写入校验调用（L3-4） | 独立，写侧改动 |

**本批只做「让已经记住的东西能取出来」。** 当前最痛的一环已经解决：
真实查询有返回 17→20/26，取回的相关条目 18→30 条，零噪音。

## 八、回滚方式

改的是配置和判据，**数据零改动**（没有迁移、没有重写库）。

```bash
git checkout HEAD -- lib/engine/read.mjs lib/engine/dict.mjs lib/engine/templates/scoring.json
```

回滚后旧行为立即恢复（含旧的死锁）。库文件、三个 ledger 都不受影响。

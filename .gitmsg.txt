补齐整理链路：tidy.mjs + schedule.mjs + migrate.mjs + 宿主 runTidy

新增三个引擎模块（纯逻辑，零 Cordis 依赖）：

1. lib/engine/tidy.mjs
   foldFeedback     从 read.jsonl 调用序列反推 ok/wrong/unused
                    （显式 feedback 优先；near 反复出现未被采纳记 wrong）
   nextStability    状态机：观察→稳定(ok≥阈值且无wrong) / 任意→易变(wrong>0)
                    / 易变→观察(安静自愈)；已到目标态不重复改
   planPromote      升通用：≥4 个不同身份/项目 + 模型判定的同一簇
                    每次只升一个维度（不做连升两级）
   planInduction    归纳：≥3 个独立场合（按 ts 日期分组近似）
   validateTidyPatch 越界校验：编号/主要内容/时距 不可改
   planTidy         汇总 changes（有依据可执行）+ proposals（只提议）

2. lib/engine/schedule.mjs
   isBackupDue / isTidyDue / formatInterval
   注意与 tick.mjs 分工：tick 的 createTickQueue 是纯队列（无 timer），
   schedule 是纯判定 —— 都不持有 timer，host 用 setInterval 驱动

3. lib/engine/migrate.mjs
   canMigrate      ①② 优先级(config/env)锁定时明确拒绝 + 告诉用户改哪一行
   verifyMigration 字节数 + 记录数双校验

宿主新增 runTidy({dryRun, promoteCandidates, who})
  编排：备份 → 锁内读库+台账 → planTidy → 锁内写回 → 记 tidy 台账
  dryRun 只算不写（UI 预览用）

修复一个实测才发现的 bug：
  readJsonl 返回 { items, errors } 而非数组，我直接当数组用
  -> 台账永远读成空，整理永远不会改任何东西
  这个 bug 静态检查和单测都发现不了，必须真跑

容器实测通过：
  写 1 条 + 造 3 次 ok feedback
  dryRun  -> 识别"稳定性 观察→稳定，依据连续 ok 3 次"
  real    -> applied=1，库中稳定性列变"稳定"
  tidy.jsonl 记 1 行 action=stability，含 before/after/basis

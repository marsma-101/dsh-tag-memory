# 多智能体规则

> 规则：**所有智能体共用一个库**，靠标签控制「给谁看什么」。
> 不靠文件隔离，靠**调用规则 + 标签**隔离。

## 〇、谁能写（2026-10-11 定）

**装过本插件的智能体就懂四个维度，直接按完整格式写。** 不需要"只填两列等管理员补"。

| 场景 | 做法 |
|---|---|
| **本机、装了本插件的智能体** | **直接读写库里的 `memory.csv`**（库在 `<DSH_HOME>/tag-memory`） |
| **别的机器** | 用户要求时打包 `store/` → 交给本机合并（见 `portability.md` 第六节） |

**并发铁律**：

> **只追加，不重写。** 追加一小段安全；**读全量 → 拼接 → 整体写回会覆盖别人的写入**。

**id 竞态**：取当天最大序号 +1。两人同时取到同号时，**后写的发现重号自己往后挪一位**，不必加锁。

## 一、一条铁律：所有智能体写同一个文件

```
<DSH_HOME>/tag-memory/store/memory.csv   ← 全库唯一，所有角色都往这里写
<DSH_HOME>/tag-memory/store/index.md     ← 手边层／索引，共用
```

**不做一人一文件**。理由：共用一个库，任何一个智能体都能知道全部——这正是标签方案的初衷（一个助理了解所有项目）。

## 二、`角色` 标签怎么写（关键规矩）

**规则：谁写入的条目就写谁。**

**`角色` 是「工作环境标识」**——**用途：多设备汇总时，区分每条记录出自哪个工作环境。**

| 情况 | 角色标签 | 例 |
|---|---|---|
| 本机本智能体写的 | 自己的名字 | `萧潇` |
| 多设备时 | **名字 + 机器** | `萧潇@工作机`、`萧潇@笔记本` |
| 没有定义身份的智能体 | `临时智能体` | 新装的、还没起名的 |

**注意**：
- **`角色` 的含义是「谁写入的」，不是「关于谁」，也不是「谁交代的」**——别搞混。
- **用户直接交代的内容，`角色` 仍写智能体名**（因为确实是智能体写进去的）。
  要标「这是主子原话」→ **用 `依据=原话`**，别动 `角色`。
- **`类型=固定` 的条目可以不打 `角色`**——没人会按「哪个智能体写的」去查物理规律或文件位置。
- 新装机器、还没定角色的智能体，**先用 `临时智能体`**，别占用别人的名字。
- 将来某个临时智能体转正有了名字 → 把它的旧条目 `角色` **改成新名字**（这是允许的标签迁移），别留两个。

**⚠️ 旧写法已废**：原来写 `marsma101` 表示"用户的通用记忆"——**这个用法取消了**（跟"谁写入的"混了）。

**⚠️ 2026-10-12 纠正**：萧潇曾在 A-03 方案里提议**把 `角色` 改成「来源等级」（原话/推断/外部）**——
**这个提议错了**。`角色` 管工作环境，是有用的（多设备汇总要用）；
「来源等级」另设 `依据` 列，**两回事，不能合并**。详见 `tags.md` 第五节。

## 三、怎么靠标签控制「给谁看什么」

**读的时候按角色筛**：

```bash
# 只看某个智能体写的（库在 <DSH_HOME>/tag-memory）
grep '"萧潇"' <DSH_HOME>/tag-memory/store/memory.csv

# 看全部（当前只有一个存储者，这是默认）
# 不必筛——直接用 CSV 解析器读全部
```

**默认读法**（`workflow.md` 第二节漏斗的第一步）：

```
① 当前只有本智能体一个存储者 → 直接读全部，不必按角色筛
② 将来多智能体共用一个库时，才按 角色 筛：
     先取 角色=<自己>（多设备时含 名@机器）→ 本智能体的可见范围
     需要跨智能体参考时，再放开过滤
③ 默认不主动展示别人的私有记忆，除非用户要

**注意**：`角色` 筛的是**「谁写入的」**，不是「这话是谁说的」。
要按「主子原话 / 萧潇推断」筛 → 用 **`依据`** 列（见 `tags.md` 第五节）。
```

## 四、手边层也共用

`<DSH_HOME>/tag-memory/store/index.md` 是**共用的入口**，所有角色的指针混在一起。

- **入口只放指针和常驻规则**，不放具体条目（见 `entry-format.md`）。
- 将来条目多了，可在入口里**按角色分组**列指针：

```markdown
### 本智能体存的
- [PrivHub] 三栏布局 → 稳定性=稳定 项目=PrivHub → 在库 M-...

### 用户直接交代的
- [通用] 某条 → 稳定性=稳定 项目=通用 → 在库 M-...
```

## 五、并发写入怎么办

多个智能体**同时**写同一个文件会互相踩。规矩：

| 场景 | 做法 |
|---|---|
| 同一台机器、同一个宿主 | 一般串行，风险低；仍建议**追加写**（append），不改已有行 |
| 多台机器共用一个库（同步盘） | **同一时间只让一台机器写**，其余只读 |
| 确实要并行 | 各写各的临时文件，事后按 `id` 合并去重 |

**为什么追加写安全**：每行独立、互不依赖；改已有行才需要读-改-写，那才是冲突源。

## 六、id 撞号怎么办

`id` 是 `M-<日期>-<序号>`，两台机器同一天各写各的会撞号。处理：

- **能避开就避开**：多机场景让各机用不同的序号段（A 机 001-499，B 机 500-999）。
- **已经撞了**：把其中一条的序号段整体偏移，**同时改 index.md 里对应的索引行**。
- 合并时用 `id` 去重，别用 `title`——同名标题可能有好几条。

## 七、给智能体的自检清单

写记忆前问自己三句：

1. 我是谁？→ 决定 `角色:` 标签
2. 这是谁的事？→ 决定 `项目:` 标签
3. 这是什么性质？→ 决定 `深度`（情景/语义/程序）与 `稳定性`

三句答不上来，这条就先别写。

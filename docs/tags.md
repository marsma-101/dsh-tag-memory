# 标签字典

> **本文件是召回准确率的核心**。每个标签写清三件事：**什么含义 / 什么时候打 / 什么时候调用**。
> 标签可随时加改，但**加了就要登记进本文件**。
>
> **机器可读版见插件内的 `lib/engine/tags.schema.json`**（程序照它校验与筛选）。两份要**同步改**：本文件给人读、讲道理，schema 给程序读、管判定。

---

## 〇、⭐ 话题 → 标签：一次摘全的映射表

**这是本文件最重要的一张表。** 用法：**判断这轮在聊什么 → 查这张表 → 一次性定下筛哪些标签 → 一次摘完**。
**不要**先摘一批、读完发现不够、再摘一次——那是两次检索，标签字典就白写了。

| 这轮在聊什么 | 筛这些 | 说明 |
|---|---|---|
| **记忆系统本身**（记忆怎么存/升/降/冲突） | `项目=AI_treaning` | 记忆架构类全在这里 |
| **用户是谁 / 他怎么想** | `关键词` 含「用户/偏好/思维模式」 | 偏好、背景、思维模式（**没有「关于谁」这一维**，靠 `关键词` 兜底） |
| **某个具体项目**（如 PrivHub、公众号） | `项目=<项目名>` | 项目专属条目 |
| **要做技术/代码相关的事** | `工具=dsh`（或对应工具）+ `类型=固定` | 工具事实与位置 |
| **排查故障 / 找东西** | `深度=情景` + `关键词` 含「坑/报错/排查」 | 踩坑记录 |
| **要出方案 / 做判断** | `深度=语义` + `距离=常驻` | 规律与原则 |
| **要执行某个流程** | `深度=程序` | 做法类 |
| **拆解视频/文章/他人经验** | `关键词` 含「拆解/思维模式/下钻」 | 方法论 |
| **做产品取舍** | `关键词` 含「取舍/用户/产品」 | 产品类原则 |
| **不确定聊什么** | `距离=常驻` 那 9 条 + 用 `关键词` 全文搜 | 兜底 |

**三条使用要点**：

1. **一次定完**：查表时就把标签组合定齐（通常 2-3 个条件），**不要分批摘**。
2. **常驻是基线**：`距离=常驻` 那 9 条**无论如何都带上**——它不是一次检索步骤，是自动附带的。
3. **先窄后宽**：先按话题筛；命中太少才放宽（去掉 `项目`，或改用 `关键词` 全文搜）。

**一次摘几条**：**先报命中总数，再取前 3 条**；不够再取 3 条。**不要一次全取**——全取既爆上下文，又稀释注意力。

> **报总数**：说一句「共命中 N 条」。还有没展开的，再补一句「另有 N 条命中未展开，要不要看」。
> 主子才知道后面还有多少，要不要接着看由他定。

### ⭐ 问句指向某个时间段 → 叠加 `时间` 列的范围筛

**「上周那个」「10 月 7 号定的」** 这类问句 → **在标签筛之上，再按 `时间` 列取该范围的行**。

| 步骤 | 做法 |
|---|---|
| ① | 按上表先筛一遍（照旧） |
| ② | 再按 `时间` 列取该范围的行 |
| ③ | 两者**取交集**——标签命中但时间不在窗内的，**不算** |

**⚠️ 克制条款（必须守）**：

| 不按时间筛的情形 | 为什么 |
|---|---|
| 只是**顺口提到时间**（「今天在吗」「今晚做什么菜」） | 那是闲聊，不是检索条件 |
| **日期范围**（「10 月 1 号到 7 号」） | 范围太宽，筛了等于没筛 |
| **跨度超过三天** | 同上 |
| **未来日期** | 记忆只记发生过的，未来时间筛不出东西 |
| `9999-12-31` 这类**占位日期** | 那是占位符，不是真时间 |

**一句话**：**只有「指向某一次具体的事」的时间词才筛**，其余一律当普通词看。

### ⭐ 筛完还没有 → 就说没有

**按标签筛完 + `关键词` 全文搜完，仍然无命中** →

1. **直接答「记忆库里没有这条」**
2. **说明筛了哪些标签**（如「筛了 `项目=AI_treaning` + `深度=语义`，无命中」）
3. **不得拿常驻条目充数**——常驻是基线，不是答案
4. **这次失败记进台账**（库里的 `store/misses.md`，召回失败台账），下次整理时按第八节 ② 补标签

> 理由：**检索错记忆往往比不检索更糟。** 拿不相干的条目顶上，比说「没有」危害大得多。

## 一、核心：`类型` + 三个维度（各自回答一个问题）

> **原则**：分类规则或升降级规则**相同或相近的，合并**。
> 否则「召回时几维筛出来总是一样」，多写一套解释就白写了。

| 维度 | 回答的问题 | 取值 | 升降靠什么 |
|---|---|---|---|
| **`类型`** | **这是什么？**（**主开关**） | 原文 / 记忆 / 固定 | 不升降（写时定）|
| **`深度`** | **能不能当规律用？** | 情景 / 语义 / 程序 | **认识**在动（想明白了） |
| **`稳定性`** | **该不该核对？**（信不信） | 稳定 / 观察 / 易变 | **环境**在动（世界变了） |
| **`距离`** | **要不要进上下文？**（读不读） | 常驻 / 按需 / 深藏 | **使用**在动（用得多不多） |

**激活规则**：`深度` **仅当 `类型=记忆`** 时用。

**为什么是这几个**——各家架构拆开对比见 `three-axes.md`。要点：

| 合并 / 拆分的是什么 | 结果 |
|---|---|
| 原「原文层 / 经验沉淀 / 固定规则」 | 合成 **`类型`**（原文 / 记忆 / 固定），做**主开关** |
| 用户「三层」+ 旧「时效」 | 都问「会不会变」→ 合成 **`稳定性`** |
| CoALA「四层」 | 形态三层 → **`深度`**；工作记忆层 → `距离` |
| mnemon「三层到达方式」+ auto-memory「详细度」 | 都问「怎么到达模型」→ 合成 **`距离`** |
| meow 的 soul/user/project | 并入 `角色`/`项目`，**不单独成维度** |
| mneme 的 active/archived | 并入 `状态`，**不单独成维度** |

## 二、维度一：`稳定性`

| 取值 | 含义 | 什么时候打 | **什么时候调用 / 怎么用** |
|---|---|---|---|
| `稳定` | **不会变**：客观事实、成熟做法 | 写下时就知道它不会变 | **直接用**，不必核对 |
| `观察` | **还没定 / 拿不准**：待验证的做法 | 拿不准会不会变，或做法还没验证过 | **简单判断一下**再用 |
| `易变` | **会变**：版本相关、地址端口、临时状态 | 知道它会随环境变 | **着重核对**：这条现在还成立吗？ |

**判据**：**没意外会不会变？**

**升降**：**几乎不升**；降 = 发现它会变（`稳定`→`观察`→`易变`）。

**⚠️ `类型=原文 / 固定` 时 `深度` 留白**——非记忆类型不走升格链。

---

## 三、维度二：`深度`（**仅 `类型=记忆` 时用**）

| 取值 | 含义 | 什么时候打 | **什么时候调用** |
|---|---|---|---|
| `情景` | **具体事件**：某天发生了什么 | 「某次做了 X，结果 Y」 | 要**复盘 / 追溯经过**时 |
| `语义` | **一般规律**：从若干情景抽出来的 | 「由此得出原则 Z」 | 要**做判断 / 定方案**时 |
| `程序` | **做法**：怎么执行一件事 | 「下次遇到该这么做」 | 要**执行某个流程**时 |

**判据**：**事件→`情景`；规律→`语义`；做法→`程序`**。分不清就写 `情景`（宁细勿糊）。

**升降**：**有明确升格链**——
```
情景 →（同类 ≥3 个独立场合）→ 语义 →（多场景验证）→ 程序
```
> **一个案例不是规律，是噪声。** 支撑数不够不许升。

**⚠️ 数的是「独立场合」，不是「条数」**——见下节。

---

## 三点五、⭐ 独立见证人：升格判据到底数什么

**判据**：`情景` → `语义` 要的是 **≥3 个独立场合**，**不是 ≥3 条记录**。

| 情形 | 算几个场合 |
|---|---|
| **不同说话人**（用户说一次、另一个智能体说一次） | **各算一个** |
| **同一人在不同会话 / 不同时间** | **各算一个** |
| **同一个人在一次对话里说了多次** | **只算一个** |

**为什么**：数条数会把「有人一口气说了两遍」看成两个见证人。
要的是**两个人，或同一个人在两个不同场合**——不是同一段话里的两行。

> 例：用户在一轮对话里把同一件事强调了三遍 → **那是 1 个场合，不够升格**。

**升级时要在 `备注` 里写明每个场合是哪一次**——不写就数不清，也复核不了。
写法：`支撑：M-001（10-07 用户口述）、M-005（10-09 另一会话）、M-011（10-11 用户口述）`。

---

## 四、维度三：`距离`（召回优先级）

| 取值 | 含义 | 什么时候打 | **什么时候调用** |
|---|---|---|---|
| `常驻` | **每轮优先提请**（仍受其他维约束） | 高频通用、跨项目成立的原则 | 装配上下文时**只取这一层** |
| `按需` | **相关时才读** | 项目专属、特定场景 | 判断相关后**才去查** |
| `深藏` | **基本不读，查历史才看** | 已归档、久不用 | 追历史时才翻 |

**判据**：**多久用一次？**

**升降**：**按调用频率调**——常用的提到 `常驻`，久不用的降到 `深藏`。

**⚠️ `常驻` 不是「每轮必进上下文」**：它只是**候选第一位**，别的维仍能把它筛下去。
真正「每轮必进」= `常驻` **且** 其他维皆不限。**硬上限 10 条。**

## 五、其余标签（辅助定位，不是维度）

### `角色` —— **谁写入的**（工作环境标识）

**含义**：**这条记忆是哪个智能体、在哪个工作环境下写进来的。**

**用途（主子 2026-10-12 明确）**：**后期把多设备上的智能体记忆汇总时，区分每条记录出自哪个工作环境。**

| 取值 | 说明 |
|---|---|
| `<智能体名>`（如 `萧潇`） | 该智能体写的 |
| `临时智能体` | 新装、还没起名的 |
| `<智能体名>@<机器>` | 多设备时带机器名，如 `萧潇@工作机`，汇总时一眼分得清 |

**⚠️ 三个「不是」（都踩过坑）**：

| 不是 | 那该用什么 |
|---|---|
| 不是「**关于谁**」 | **没有这一维**；查「用户偏好」用 `关键词`（见第〇节映射表） |
| 不是「**来源等级**」（主子原话 / 智能体推断） | **用 `依据` 标签**，别动 `角色` |
| 不是「**谁交代的**」 | 用户交代的内容**也是智能体写进去的**，`角色` 仍写智能体名 |

**规矩（规则）**：

> **谁写入的条目就写谁。** 用户直接说的内容，也是智能体写入的 → `角色` 写智能体名；
> 是不是用户原话，**看 `依据`**。

**默认调用范围** = **全部**（当前只有一个存储者，不必筛）。
将来多个智能体、多台机器共用一个库时，才按 `角色` 筛。

**⚠️ 旧写法已废**：原来写 `marsma101`（表示"用户的通用记忆"）——
**这个用法取消了**，因为它跟「谁写入的」这个含义混了。

### `依据` —— **这话是谁说的**（2026-10-12 新增）

**含义**：这条结论**是怎么来的**。回答的是「**这是主子亲口说的，还是萧潇自己推的**」。

| 取值 | 含义 | 判据 |
|---|---|---|
| `原话` | **主子亲口说的** | 有原句、或是主子明确的决定 |
| `推断` | **萧潇总结、归纳、实测出来的** | 我跑脚本测的、我归纳的规律 |
| `外部` | **从别处抄的** | 抄文档、抄项目、抄别人的经验 |

**为什么单设一列**（而不是塞进 `角色`）：

> **`角色` 管「谁写入的」（工作环境），`依据` 管「这话是谁说的」——两回事，混了会两头都废。**

**什么时候打**：**写入时必打**（和 `状态` 同级必填）。
**什么时候调用**：**判断一条能不能当依据时**——
`原话` 可以直接当主子的意思用；`推断` **必须标明是推断**，不能冒充主子的话；`外部` 要留意出处是否还成立。

**为什么需要它**：库里早期条目**无法区分**哪些是用户说的、哪些是智能体推的。
主子的偏好、底线（`原话`）和我的归纳（`推断`）混在一起，**召回时会被同等对待**——这是当前最大的质量盲区。

### `项目` —— 哪儿的事

| 取值 | 什么时候调用 |
|---|---|
| `通用` | 任何项目都可能用上，**每次都查** |
| `<项目名>` | **只在那个项目里查** |

**判据**：换个项目还成立吗？

### `状态` —— 还有效吗

| 取值 | 调用时怎么处理 |
|---|---|
| `生效` | 正常使用 |
| `被取代` | **不读正文**，去看取代它的那条 |
| `已归档` | **默认不读**；追历史时才看 |

### `关键词` —— 兜底检索

自由填，逗号分隔。**标签筛完还不够/没结果时**，用它全文搜。

**另一项固定用法**：每条都带上**写入路由的类名**（`决策` / `交代` / `规矩` / `纠正`）——
同一类输入散在各处，靠它一筛就聚起来（详见 [entry-format.md](entry-format.md) 6.1）。

**例**：`PowerShell, BOM, JSONL, 编码`、`交代, 备份策略`

### `工具` —— 涉及哪个工具

`python` / `git` / `dsh` / `nowen-note` / `qoder` …

**例**：「python 装在哪」→ `类型=固定` + `工具=python`，以后需要 Python 时一查就到。

**大多数条目为空是正常的**——大部分记忆不绑定特定工具。

### `版本` —— 同事物不同版本（**冲突解决专用**）

`v1` / `v2` / 具体版本号。

**⚠️ 现在全空是对的，不是缺陷**（主子 2026-10-10 定，2026-10-12 重申）：

> 「咱现在是最初的，也算没有版本。后面如果我要更新版本了，
> 你再把旧的这些定成 v1，然后有 v2 的相应冲突记录你再标记 v2。」

**判据：什么时候才打**

| 情况 | 打不打 `版本` |
|---|---|
| 项目还在第一版，没有新旧之分 | **不打**（现在就是这状态） |
| 出现**冲突 / 重复**，需要区分「两条都对但适用版本不同」 | **这时才打**，把旧的那批定成 `v1`，新的标 `v2` |

**「全空」的含义是「还没有需要区分的版本」，不是「这个机制没做」。**
（2026-10-12 萧潇曾把「版本列全空」误报为缺陷，已纠正。）

**什么时候打**：**两条记忆都对，但适用版本不同**——**不要标「被取代」**，
而是**两条都留**，各打一个 `版本` 标签。

**什么时候调用**：遇到「这条跟以前说的不一样」时，**先查是不是版本差异**——
是的话，**两条都要**，别只取新的。详见 `conflict.md`。

### ⚠️ 不设 `来源` 列（规则）

**`环境` + `原因` 合起来就是来源**——

| 列 | 作用 |
|---|---|
| `环境` | **什么条件下用这条** |
| `原因` | **为什么要记它** |

**这两个合起来已回答「这条从哪来、为什么存在」**，再加一列 `来源` 是重复。

**写法要求**：`原因` 列要写清「为什么要记这一条」——**它就是这条记忆的出处说明**。
**以后记记忆都按这个方式**：来源不单列，写进 `环境` + `原因`。

## 六、打标签的度：最小充分

> **打够将来真能检索到它就行，多打是噪音。**

| 情形 | 打什么 |
|---|---|
| 文件位置、物理规律 | `类型=固定` —— **够了**（不打 `深度`） |
| 某项目的做法 | `类型=记忆` `深度=程序` `稳定性=稳定` `项目=X` `角色=X` `距离=按需` |
| 通用判断原则 | `类型=记忆` `深度=语义` `稳定性=稳定` `项目=通用` `距离=常驻` |

**不填的列留空。**

## 七、各维度的差异（为什么不会筛出一样的东西）

| 维度 | 典型筛法 | 拿到什么 |
|---|---|---|
| `类型` | 筛 `固定` / `原文` | **本机硬信息 / 原话原文** |
| `稳定性` | 筛 `稳定`+`观察` | **可信的**（能直接用的） |
| `深度` | 筛 `语义` | **规律**（能当判断依据的） |
| `距离` | 筛 `常驻` | **该进上下文的**（省 token 的关键） |

**举例**：同一个项目下
```
M-001  PrivHub v1 三栏布局   类型=记忆  深度=情景  稳定性=稳定  距离=按需
M-002  部署前查配置漂移       类型=记忆  深度=语义  稳定性=稳定  距离=常驻
M-003  python 安装路径        类型=固定  深度=（空） 稳定性=稳定  距离=按需
```
**筛「类型=固定」拿到 M-003；筛「深度=语义」拿到 M-002**——**完全不同的集合**。

## 八、整理时怎么用标签

```
① 翻对话，看哪些条目被调用过
     用对了 → 不动，可补 关键词
② 看有没有「用户提过、但没想起来」的
     有 → **补标签**，写明"下次在什么情况下该用它"   ← 最有价值
③ 该升：深度 情景→语义→程序（够**独立场合数**）
④ 该降：稳定性 降级 / 状态 改被取代
⑤ 该调距离：常用的提到 常驻，久不用的降到 深藏
⑥ 标签乱长 → 补进本文件，或清掉
```

**第 ② 步是核心**：**召回失败一次，就补一次标签**。

> 召回失败**当场**怎么答（说「没有」、报清筛了哪些标签、不许拿常驻充数）见第〇节「筛完还没有 → 就说没有」。
> 按时间段检索见第〇节「问句指向某个时间段」。

---

## 九、加/改标签的规矩

1. **加列**：CSV 表头**末尾追加**（不要插在中间——会错列），已有行留空
2. **登记进本文件**：写清三件事——**含义 / 什么时候打 / 什么时候调用**
3. **同步改 `lib/engine/tags.schema.json`**（机器可读版）——两份不一致时，程序会照 schema 判，等于白登记
4. **改列名**：同步改所有引用它的文档
5. 加完**告知用户**一句

**为什么必须登记**：**没登记的标签 = 以后想不起来用它**。召回不准，多半就出在这。

## 十、⭐ 标签从哪来：**按「存」和「读」的问题调整**（2026-10-12 定）

**这是本文件的总纲。** 标签不是凭空设计的，是**为了解决存和读的具体问题**长出来的。

### 规矩（主子 2026-10-12 明确）

> **根据「存」和「读」的问题，调整标签的添加规则、修改标签字典。**

### 怎么落：遇到问题 → 判断该不该加/改标签

| 哪一环出问题 | 具体表现 | 该怎么动标签 |
|---|---|---|
| **存** | 某类东西**存不进去 / 存进去说不清** | 加列，或改某列的取值 |
| **读** | 某类东西**筛不出来 / 筛错** | 补取值、改「什么时候打」的规则 |
| **整理** | 某类东西**不知道该留还是该降** | 加状态值，或明确升降判据 |

**三步走**：

```
① 先说清是什么问题（存不进？读不出？整理时判不了？）
② 再说清现有标签为什么解决不了它
③ 最后才决定：加新列 / 加取值 / 改判据 / 什么都不动
```

### ⚠️ 反面：不要「为了完整」加标签

**加标签的唯一理由是「现有标签解决不了某个具体的存/读问题」。**
- 说不出具体问题的 → **不加**
- 「别的系统有这一列」→ **不是理由**
- 「加了看起来更全」→ **不加**（多打是噪音，见第六节）

### 与第六节「最小充分」的关系

| | 管什么 |
|---|---|
| **第六节**（打标签的度） | **一条记忆该打几个标签**（最小充分） |
| **第十节**（本节） | **字典本身该不该加标签**（按问题驱动） |

**两条合起来**：字典按问题长，条目按最小打。

# 升降级规则

> **咱们的升降级 = 改标签**。他们的 = 搬数据 / 改强度 / 改状态。
> 本文先摆他们的做法，再定咱们的规则，最后说为什么这么定。

---

## 一、他们怎么做（实测查证）

| 插件 | 升 | 降 | 判据 |
|---|---|---|---|
| **dsh-mneme** | `merge` / `update` | `archive` / `supersede` | **类型化决策清单**：keep / merge / archive / conflict / update |
| **meow-memory** | 强化 +0.3；多项目验证→晋升 | 艾宾浩斯衰减 | 打分排序 |
| **旧插件** | 强化；**3 个不同项目**才晋升 | <0.1 归档候选 | **独立项目数** |
| **auto-memory** | 结晶（对话→技能） | 分层压缩 | 三层降级 |
| **memory-evolve** | AI 提议 → 用户确认 | 归档 | 「只提议，你确认」 |

**两条值得注意的**：

**① 「强化」≠「晋升」**

| | 触发 | 作用 |
|---|---|---|
| **强化** | 又被用到 | 强度 ↑，别被淘汰 |
| **晋升** | **多个不同项目**验证 | 适用范围扩大 |

**判据是「独立项目数」，不是「调用次数」**——同一项目用 100 次，仍然只是这个项目的规则。

**② 类型化决策**（mneme，最有参考价值）

不搞玄的自动升级，而是**列出有限几种动作**：
```
keep / merge / archive / conflict / update / supersede / differentiate
```

## 二、咱们的规则：升降级 = 改标签

| | 他们 | 咱们 |
|---|---|---|
| 升一级 | 迁表 / 改 strength / 合并文件 | **改某个维度的标签值** |
| 操作性质 | **数据操作**（迁移） | **元数据操作**（改字段） |
| 出错面 | 迁移可能丢数据 | 改标签不会丢 |
| 事务要求 | 要 | 不需要 |

**各维度有自己的升降规则，互不相同**：

| 维度 | 升 | 降 | 谁在动 |
|---|---|---|---|
| **`类型`** | 不升降（写时定）| —— | —— |
| **`稳定性`** | **几乎不升** | 发现会变 → 降级 | **环境**（世界变了） |
| **`深度`** | **有升格链**，够**独立场合数**才升 | 很少降 | **认识**（想明白了） |
| **`距离`** | 常用 → 提到 `常驻` | 久不用 → 降到 `深藏` | **使用**（用得多不多） |

---

## 三、维度一 `稳定性` 的升降

| 动作 | 触发 | 怎么改 |
|---|---|---|
| 降级 | 发现这条其实会变 | `稳定` → `观察` → `易变` |
| 升级 | **几乎不发生** | 除非发现「其实不会变」（罕见） |

**为什么几乎不升**：稳定性是**客观属性**——会不会变由世界决定，不由我们用得多不多决定。

**⚠️ `类型=原文 / 固定` 时 `深度` 留白**（非记忆类型不走升格链）。

---

## 四、维度二 `深度` 的升降（**唯一有明确升格链的维度**）

| 动作 | 触发 | 怎么改 |
|---|---|---|
| **升格** | 同类 `情景` **≥3 个独立场合** | **新建**一条 `语义`，`备注` 写明哪几次支撑 |
| **再升** | `语义` 在**多个场景**验证过 | **新建**一条 `程序` |
| **降级** | 很少发生 | 除非发现「这其实是特例」→ 退回 `情景` |

**关键规矩**：

> **一个案例不是规律，是噪声。** 支撑数不够，**不许升**。

### ⚠️ 数的是「独立场合」，不是「条数」

**同一个人在一次对话里说三遍，只算一个场合**——不能凑够 3 条就升格。

| 情形 | 算几个场合 |
|---|---|
| **不同说话人** | 各算一个 |
| **同一人在不同会话 / 不同时间** | 各算一个 |
| **同一个人在一次对话里说多次** | **只算一个** |

**为什么**：数条数会把「有人一口气说了两遍」看成两个见证人。
判据要的是**两个人，或同一个人在两个不同场合**——不是同一段话里的两行。

**升级时要在 `备注` 里写明每个场合是哪一次**，否则数不清也复核不了。

**「升格」是新建条目，不是改旧的**：
```
① 保留原情景条目（它们是证据）
② 新建一条语义条目
③ 新条目的 备注 里写「支撑：M-001（10-07 用户口述）、M-005（10-09 另一会话）、M-011（10-11 用户口述）」
   ← 每条后面注明「哪一次」，才数得出独立场合数
```

---

## 五、维度三 `距离` 的升降

| 动作 | 触发 | 怎么改 |
|---|---|---|
| **提上来** | 该条被**反复用到** | `按需` → `常驻`（或 `深藏` → `按需`） |
| **降下去** | 长期没被用到 | `常驻` → `按需` → `深藏` |

**判据**：**看它有没有被用到**，不是看时间。

**这是各维度里唯一由「使用情况」驱动的。**

---

## 六、整理时做哪几个动作（五选一）

照 mneme 的**类型化决策**，整理时**只做这五种**：

| 动作 | 什么时候用 | 怎么改 | 要问用户吗 |
|---|---|---|---|
| **keep** | 用对了，没毛病 | 不动（可补 `关键词`） | 不用 |
| **update** | 内容要补充/修正 | **改内容** | **要** |
| **merge** | 两条说的是一回事 | 合成一条，旧的 `已归档`，`备注` 写「已并入 M-xxxx」 | **要** |
| **supersede** | 新的推翻旧的 | 旧的 `被取代`，新的 `备注` 写「取代 M-xxxx」 | **要** |
| **differentiate** | **两条都对，适用范围不同** | **都留**，各补 `版本` 等标签 | 不用 |

**默认动作是 `differentiate`**——都留，补标签区分。**留着比删了安全。**

## 七、⭐ differentiate —— 前述那个情况

说明：

> 「并不是说以前的一定错了、新的就是对的……老的记忆是旧版本条件下的，新的是新版本条件下的……**两个都保存下来**。」

**这正是 mneme 的 `differentiate`**。

### 怎么落

```
❌ 错：把 v1 那条标"被取代"、删掉 → 丢了历史

✅ 对：两条都留，各补 版本 标签区分
   M-001  [PrivHub] v1 架构：三栏布局
          稳定性=稳定  距离=按需  项目=PrivHub  版本=v1  状态=生效
   M-002  [PrivHub] v2 架构：单栏+抽屉
          稳定性=稳定  距离=按需  项目=PrivHub  版本=v2  状态=生效
   ← 两条都生效，各自适用各自版本
```

### 什么时候 differentiate，什么时候 supersede

| 判据 | 用哪个 |
|---|---|
| 两条**都在各自条件下成立** | **differentiate**（都留） |
| 新的**彻底否定**旧的 | **supersede**（旧的降权） |
| 分不清 | **先按 differentiate 处理** |

> **宁可多留，不可误删。** 记忆不可再生。

## 八、为什么这么定（对比他们的）

| 他们的问题 | 咱们的解法 |
|---|---|
| **搬数据有风险**——迁移可能丢、可能半途失败 | **改标签**，不动数据 |
| **自动升降级容易跑偏** | **判断动作，不是自动动作**：升格前先问用户 |
| **冲突自动裁决可能裁错** | **不自动裁决**：能区分的都留，真冲突报用户 |
| **衰减靠时间，不看用处** | **不看时间，看有没有被用到** |
| **层级写死在表结构里** | **维度是标签值**，加一层/改一层都是加个值 |

**一句话**：他们用**代码逻辑**管升降，咱们用**标签 + 判断**管升降。
**代码逻辑省人力但可能跑偏；标签 + 判断费点事但不会跑偏。**

---

## 九、整理时的完整流程

```
① 翻本轮对话，看哪些条目被调用过
     用对了 → keep（可补 关键词）
② 看有没有「用户提过、但没想起来」的
     有 → 补标签，写明"下次在什么情况下该用它"   ← 最有价值
③ 深度该升的 → 情景→语义→程序（够**独立场合数**）
④ 稳定性该降的 → 稳定→观察→易变
⑤ 距离该调的 → 常用的提常驻，久不用的降深藏
⑥ 冲突的 → differentiate（都留）或 supersede（旧的降权）
⑦ 标签乱长 → 补进 tags.md 或清掉
```

**全程不删行**——只改标签值。

# 冲突解决方案

> **第一原则**：**更新的不一定更真，旧的不一定是错的。**
> **第二原则**：**宁可多留，不可误删**——记忆不可再生。
> **第三原则**：**能区分的就都留，真冲突的报用户。**

---

## 一、先分清：这是不是「冲突」

**很多看着像冲突的，其实不是冲突。**

| 看着像 | 其实是什么 | 怎么处理 |
|---|---|---|
| 两条说的不一样 | **作用域错配**——本来就不是同一个场景 | **不是冲突**；补标签区分（改 `项目`/自定义列） |
| 两条都对但结论不同 | **版本/条件不同** | **differentiate**：都留，补标签 |
| 新的推翻旧的 | **真取代** | **supersede**：旧的标 `被取代` |
| 有一条记错了 | **记录错误** | 标 `已归档` + 写明原记录有误 |

**判据**：**这两条，能不能各自找到"在什么条件下成立"？**
- **都能找到** → **不是冲突**（differentiate，都留）
- **只有一个能找到** → **是真取代**（supersede）
- **都找不到** → 问用户

---

## 二、四种处理方式

### 2.1 differentiate —— 都留（**默认选它**）

**适用**：两条都在各自条件下成立。

**做法**：
```
① 两条都保持 状态=生效
② 各补一个区分标签（如 版本=v1 / 版本=v2）
③ 各自在 环境 列写清"在什么条件下适用"
④ 在 备注 里互相引用：「与 M-xxxx 是不同版本下的做法」
```

**例**（典型 PrivHub 那个）：
```
M-001  [PrivHub] v1 架构：三栏布局
       项目=PrivHub  版本=v1  稳定性=稳定  状态=生效
       环境=PrivHub v1 版本、需要一眼看全上下文时
       备注=适用于 v1。v2 改为单栏+抽屉，见 M-002

M-002  [PrivHub] v2 架构：单栏 + 抽屉
       项目=PrivHub  版本=v2  稳定性=稳定  状态=生效
       环境=PrivHub v2 版本、移动端优先时
       备注=适用于 v2。与 M-001 是不同版本下的设计，非取代关系
```

**为什么默认选它**：**留着比删了安全**。将来问「当初 v1 为什么那样设计」，答得上。

### 2.2 supersede —— 旧的降权

**适用**：新的**彻底否定**旧的（旧的是错的，不是条件不同）。

**做法**：
```
① 旧的：状态 改「被取代」
② 新的：备注 写「取代 M-xxxx」
③ 旧的正文一个字不改
```

**关键**：
> **旧记录降权而非删除——万一新证据后来被证伪，旧的还能恢复。**

### 2.3 归档 —— 失效但留痕

**适用**：确定没用了，但想留个记录。

**做法**：`状态` 改 `已归档`。**默认不读**，追历史时才看。

### 2.4 报用户 —— 拿不准就交出去

**适用**：
- 两条都找不到成立条件
- 分不清是「取代」还是「不同版本」
- 涉及用户偏好、底线这类主观判断

**做法**：**列出来，说明各自依据，让用户拍板**。不擅自裁决。

## 三、⚠️ 一条硬规矩：不擅自改已有条目

| 动作 | 要不要先问用户 |
|---|---|
| **新增**一条记忆 | **不用**（追加不改动已有数据） |
| **改已有条目**（内容/标签/状态） | **要**——先说改什么，等用户确认 |
| **标记冲突** | 不用（只是标出来） |
| **裁决冲突** | **要**——除非用户已授权某类自动处理 |

**为什么**：本系统要求「**AI 只提议，你确认**」。
**改已有条目风险更高**——可能改错、可能覆盖。

## 四、冲突检查怎么做

### 4.1 什么时候查

| 时机 | 查什么 |
|---|---|
| **写入新条目时** | 查有没有同 `项目` + 同主题的旧条目 |
| **整理记忆时** | 全库扫一遍，找结论矛盾的 |
| **用户说「这条跟以前不一样」时** | 针对性查 |

### 4.2 怎么查（脚本）

```javascript
// conflict-check.mjs —— 找潜在冲突
import { readFileSync } from 'node:fs'

function parseCSV(t) {
  const rows = []; let row = [], cell = '', q = false
  for (let i = 0; i < t.length; i++) {
    const c = t[i]
    if (q) { if (c === '"') { if (t[i+1] === '"') { cell += '"'; i++ } else q = false } else cell += c }
    else if (c === '"') q = true
    else if (c === ',') { row.push(cell); cell = '' }
    else if (c === '\n') { row.push(cell); rows.push(row); row = []; cell = '' }
    else if (c !== '\r') cell += c
  }
  if (cell || row.length) { row.push(cell); rows.push(row) }
  return rows.filter(r => r[0])
}

const rows = parseCSV(readFileSync(process.env.DSH_HOME + '/tag-memory/store/memory.csv', 'utf8'))
const H = rows[0], idx = (n) => H.indexOf(n)
const data = rows.slice(1).filter(r => r[idx('状态')] === '生效')

// 同项目 + 同深度 的条目，人工看内容有无矛盾（`成熟度` 列 = 字典的 `深度`）
const groups = {}
for (const r of data) {
  const k = `${r[idx('项目')]}||${r[idx('成熟度')]}`
  ;(groups[k] ||= []).push(r)
}
for (const [k, list] of Object.entries(groups)) {
  if (list.length < 2) continue
  console.log(`\n【${k}】${list.length} 条，检查有无矛盾：`)
  for (const r of list) {
    console.log(`  ${r[idx('id')]}  ${(r[idx('内容')] || '').split('\n')[0].slice(0, 50)}`)
    console.log(`      环境: ${r[idx('环境')]}`)
  }
}
```

**机器只能「把可能相关的摆到一起」，判断矛盾要靠人（或问用户）**。

## 五、用户那个例子的教训

用户说：

> 「我明明记得咱做了一个用 nowen-note 去存记忆条目的插件，结果你找不着。」

**这件事本身就是一个「记忆冲突」案例**：

| | 用户的记忆 | 本插件查到的 |
|---|---|---|
| 内容 | 有个插件把记忆写进 nowen-note | 没找到这样的插件 |
| 实际情况 | **是 MCP 包**（`nowen-mcp`），不是 DSH 插件 | 本插件按「插件」找，方向错了 |

**两条都不是「错」**——是**描述的角度不同**（前述是功能，本插件找的是形态）。

**按咱们的新规则，该怎么处理**：
```
① 不判谁对谁错
② 补标签区分：
   用户的记忆 → 关键词加「nowen,插件,MCP,记忆存储」
   本插件的发现 → 单独一条，关键词加「nowen-mcp,MCP,包位置」
③ 两条都留，各自写清「从什么角度看」
```

**这个教训写进规则**：

> **找不到不等于不存在。** 找的时候要**换角度**（插件 / 技能 / MCP / 脚本 / 配置），
> 一个角度找不到，不代表没有。

---

## 六、速查

| 情况 | 动作 | 要问用户吗 |
|---|---|---|
| 两条都在各自条件下成立 | **differentiate**（都留，补标签） | 不用 |
| 新的彻底否定旧的 | **supersede**（旧的标被取代） | **要** |
| 确定没用了 | **归档** | 不用 |
| 记错了 | 归档 + 写明有误 | **要** |
| 拿不准 | **报用户** | **要** |

**默认动作是 `differentiate`**——都留，补标签区分。**留着比删了安全。**
